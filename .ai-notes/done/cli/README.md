## Что сказал владелец (близко к тексту)

> «Давай сделаем на Kotlin консольное приложение с разными функциями, которые нам будут нужны. Это
> каркас CLI-приложения, в котором можно, например, сгенерировать QR-код или расшифровать данные.
> Функции тоже будут называться приложениями, только там это команды: в арсенале разные команды с
> разными параметрами, и всё внутри выбирается и работает. Посмотри репозиторий, какие вещи там
> есть. В итоге нужен абстрагированный пакет, который мы потом будем использовать в Kotlin.
> Папка — `/prj/unitool/unitool-cli/`».
>
> «Консольное приложение на Kotlin не должно быть точь-в-точь как для телефона, надо только
> некоторые функции».
>
> «Надо назвать по-другому ту часть, которая будет улетать в общую часть. То есть если код уже есть
> в CLI или в мобильном приложении, мы будем абстрагировать его в `unitool-kit` и публиковать
> отдельным пакетом библиотеки, чтобы использовать и там, и там».
>
> «Общий код надо выносить в отдельную либу, а не копировать туда-сюда всё время. Либо перенести CLI
> в репозиторий самого Unitool, не делать отдельный репозиторий, а сделать прямо в этом монорепо.
> Тогда не надо будет делать отдельный пакет, а можно как-то переиспользовать файлы. Суть в том, что
> нам нужна единая кодовая база, чтобы мы не разошлись».

## Короткий ответ

1. **Монорепозиторий** (D280). Всё живёт в `/prj/unitool`:

   ```
   /prj/unitool/
     unitool-kit/     :unitool-kit          ← общий код: телефон и CLI зависят от него
     unitool-cli/     :unitool-cli:*        ← консольное приложение
     services/ssh     → project(":unitool-kit")
     apps/twofa       → project(":unitool-kit")
     composeApp, apps/*, services/*  — как сейчас
   ```

   Правка kit, телефона и CLI — это один коммит и один прогон `./scripts/verify.sh`. Версий kit нет,
   поэтому разойтись нечему. Симлинк `unitool-cli` уступает место настоящей папке (D285).
2. **Переиспользование — через модуль, а не через общие файлы** (D281). Kit — обычный модуль, как
   `services/*`, и потребители пишут `project(":unitool-kit")`. Один и тот же файл не подключается в
   два модуля через `srcDir`: он скомпилировался бы дважды.
3. **Правило, что уходит в kit** (D273): код, который нужен обеим сторонам, или код, который уже есть
   у одной и понадобился другой. Код одной стороны остаётся у неё. QR через ZXing нужен только CLI;
   связка ключей, агент, vault и UI — только телефону. Если модулю CLI понадобился код из `apps/*`
   или `services/*`, этот код переезжает в kit, а зависимость от телефонного модуля не заводится.
   Это проверяет `verify.sh` (D283).
4. **Первая партия переноса** (D277, подробно в 02 §3). Файлы переезжают через `git mv`, и история
   сохраняется (D282):
   - из `services/ssh`: age, ключи OpenSSH, SSHSIG и криптография;
   - из `apps/twofa`: TOTP и перенос из Google Authenticator.
5. **От Superizer в CLI берётся одна идея** (D263): приложение — это слово в командной строке с
   заголовком и набором команд. Ни активаций, ни секретных приложений, ни deep links, ни жизненного
   цикла.
6. **В первой версии CLI — только генерация QR** (D288, ответ на 132): `qr encode` в терминал, PNG
   или SVG. `qr decode` и `age` — кандидаты (01 §5). Поэтому kit пока не создаётся (D289).
7. **Коммит только про CLI не выкатывает alpha** (D284): в `android-play.yml` добавляется
   `paths-ignore: ['unitool-cli/**']`. Правка kit выкатывает, потому что меняет телефон.

API каркаса, приложения CLI и тесты — в [01-design.md](01-design.md). Модуль kit, перенос и
проверки границ — в [02-unitool-kit.md](02-unitool-kit.md).

## Решения

| № | Решение |
|---|---|
| D263 | CLI — самостоятельный маленький каркас, а не Superizer для терминала. Из телефонного хоста взята только модель «приложение = id + заголовок + команды». Что сознательно не взято — в 01 §1 |
| D264 | ~~Репозиторий `/prj/unitool-cli` со своим git.~~ **Заменено D280:** CLI — модули `:unitool-cli:core` (каркас), `:unitool-cli:apps:qr`, `:unitool-cli:apps:age`, `:unitool-cli:app` (бинарь) в монорепозитории Unitool. Приложения CLI зависят от `core`, `:unitool-kit` и своих библиотек (ZXing) |
| D265 | Параметры команд объявляются делегатами (`argument`, `option`, `flag`) в порядке объявления. Одно объявление даёт разбор argv, `--help`, интерактивные вопросы и строку «то же одной командой». Разбора хватает на соглашения GNU: `--opt=v`, `--opt v`, `-o v`, `--`, `-` = stdin |
| D266 | Первая версия CLI — только `qr` (encode, decode) и `age` (decrypt, encrypt). Кандидаты на потом — в 01 §5 |
| D267 | ~~Логика age, SSH и криптографии копируется в `libs/ssh-age`.~~ **Отменено в 1.1:** копий нет |
| D268 | ~~CLI — Kotlin/JVM (`kotlin("jvm")`), toolchain Java 21, плагин `application`.~~ **Заменено D291 в 1.4.** Kit мультиплатформенный, и CLI берёт его JVM-вариант. Команда `run` в каркасе — обычная функция, не `suspend`. `suspend` из age вызывается через `runBlocking` в `apps/age`. Сети хватает `java.net.http` |
| D269 | Правила вывода взяты из `remote-progress/03 §2`. В stdout идёт только результат (QR, расшифрованные байты), всё для человека — в stderr. Поэтому `unitool age decrypt … \| unitool qr encode` работает без фильтров |
| D270 | Коды выхода: 0 — успех, 1 — команда не смогла (неверный ключ, битый файл), 2 — ошибка использования (нет параметра, неизвестный флаг), 130 — Ctrl-C или Ctrl-D в меню. **Добавлено в 1.3:** 141 и ни слова, если читатель stdout ушёл (`\| head`), как у процесса, убитого SIGPIPE. Иначе JDK печатал бы «Broken pipe» как внутреннюю ошибку |
| D271 | `unitool` без аргументов в терминале открывает меню: приложение → команда → вопросы по параметрам → запуск, в конце — та же команда одной строкой. Без терминала (pipe, CI) печатается справка с кодом 2 |
| D272 | Пароль ключа — не параметр. Его спрашивает команда через `io.secret()` без эха, а без терминала берёт из `UNITOOL_PASSPHRASE`. В argv пароля не бывает: иначе он попадёт в историю shell и в `ps` |
| D273 | Общий код живёт в `unitool-kit`. Правило переноса — в п. 3 «Короткого ответа». Копий нет: перенесённое у источника удаляется. ~~Отдельный репозиторий `/prj/unitool-kit`~~ — **заменено D280** |
| D274 | Kit — один модуль с пакетами `cx.m42.unitool.kit.crypto`, `.ssh`, `.age`, `.otp`. Почти всё нужно каждому потребителю, поэтому дробить незачем. Отдельный модуль появляется, когда часть кода приносит свою зависимость. Цели — те же, что у `services/ssh` сегодня: `androidTarget`, `jvm("desktop")`, `iosArm64`, `iosSimulatorArm64`, `wasmJs`; `explicitApi()`. ~~Координаты `cx.m42.unitool:unitool-kit`~~ — **не публикуется, D286** |
| D275 | В kit нет сети, Superizer, Compose и coroutines. Единственная зависимость — `kotlinx-serialization-core` для `@Serializable TotpAccount`. Типы Superizer заменяются на границе: `KeyId` → `String` (отпечаток), `ImportRefusal` → свой `KeyFileRefusal`. Обратно их переводит `services/ssh` |
| D276 | ~~`includeBuild("../unitool-kit")`, `UNITOOL_KIT_FROM_MAVEN`, версия в `libs.versions.toml`, CI выкачивает kit.~~ **Заменено D281** |
| D277 | Первая партия переноса (02 §3). Из `services/ssh`: `crypto/*` с `actual` для четырёх платформ, `wire/*`, `SshPublicKey`, `SshSig`, `SecretBytes`, `Age`, `key/OpenSshKeyFile`, `key/SoftwareOps`. Из `apps/twofa`: `Totp.kt`, `GoogleMigration.kt`, `HashAlgorithm`; второй SHA и HMAC из `twofa/Crypto.kt` удаляются. Нужное соседям из `internal` становится `public` |
| D278 | ~~Порядок: kit → Unitool → CLI в трёх репозиториях.~~ **Заменено D287** |
| D279 | Каркас команд — `:unitool-cli:core`, пакет `cx.m42.unitool.cli`. Он не входит в kit, пока второй потребитель не появится. Слово «kit» означает только `unitool-kit` |
| D280 | **Монорепозиторий.** `unitool-kit/` и `unitool-cli/` — папки в корне `/prj/unitool`, модули включаются в общий `settings.gradle.kts`. Отдельных git-репозиториев, публикации и версий kit нет. Причина — слова владельца: «единая кодовая база, чтобы мы не разошлись». Изменение kit вместе со всеми потребителями — один коммит, его проверяет один `verify.sh`, рассинхрон невозможен по построению |
| D281 | Потребители подключают kit как проект: `implementation(project(":unitool-kit"))`, как сегодня `services/*`. Общие `srcDir` между модулями запрещены. Правило «только Maven-координаты» остаётся правилом для Superizer: kit — не внешняя библиотека, а часть этого репозитория |
| D282 | Перенос и перевод потребителей — **один коммит**, файлы переезжают через `git mv`. История видна через `git log --follow`, и ни в одном коммите нет двух копий одного кода |
| D283 | Границы проверяет `scripts/verify.sh`: (а) в дереве зависимостей `:unitool-kit` нет `cx.m42.superizer`, `org.jetbrains.compose`, `io.ktor`, `kotlinx-coroutines`; (б) модули `:unitool-cli:*` не зависят от `composeApp`, `apps/*`, `services/*` и Superizer; (в) тесты CLI и сборка `installDist` идут в том же прогоне, что и телефон |
| D284 | `android-play.yml`: `paths-ignore: ['unitool-cli/**']`. Коммит, меняющий только CLI, не выкатывает alpha; правка kit выкатывает. Отдельного workflow для CLI нет: его проверяет `verify.sh` |
| D285 | Симлинк `unitool-cli → ../unitool-cli/` и строка `unitool-cli` в `.gitignore` (незакоммиченная правка владельца) убираются, на их месте — настоящая папка. Пустой `/prj/unitool-cli` удаляется |
| D286 | Kit не публикуется. Если он понадобится проекту вне этого репозитория, к `:unitool-kit` добавляется `maven-publish`. Модуль и так не зависит от Superizer, так что переносить ничего не придётся |
| D287 | Одна ветка `cli`, шаги в 02 §6 и 01 §8: (1) kit и перевод телефона одним коммитом; (2) каркас; (3) `qr`; (4) `age`; (5) CI и README. В `main` — только по слову владельца: push туда выкатывает alpha. **Уточнено D289/D290:** шаги (1) и (4) отложены |
| D288 | Первая версия CLI — только `qr encode` (ответ на 132: «только qr генерация пока»). D266 сужено: `qr decode` и `age` — кандидаты (01 §5) |
| D289 | ~~`unitool-kit` в первой версии не создаётся.~~ **Отменено D293 в 1.5.** Кодировщика QR у телефона нет, так что общего кода нет, и пустой модуль ничего не защищал бы. Правило D273 и порядок D282 остаются в силе. Kit появляется одним коммитом вместе с первой командой CLI, которой нужен код телефона (`age`, `otp`): тогда же переезжает партия D277 и телефон переходит на kit |
| D290 | Изменения 1.3 лежат в рабочем дереве, ветка `cli` не создавалась. Текущая ветка владельца `ssh-keyring` несёт шесть незапушенных коммитов, и переключать её без спроса нельзя. Коммит и ветку делает владелец или исполнитель по его слову |
| D291 | **CLI — нативный бинарь Kotlin/Native `linuxX64`** (слово владельца: «всю программу надо билдить в бинарь»). Модули CLI — Kotlin Multiplatform: `commonMain` для всего кода, `linuxX64` для бинаря, `jvm` для тестов, которым нужны JVM-библиотеки. Бинарь — один файл примерно в 1,4 МБ, старт за 30 мс. Он подключает только системные glibc 2.19+ и libz, то есть **не статический**: `-static` с glibc из toolchain Kotlin/Native линкуется в гибрид, который падает при старте (проверено). **Уточнено 2026-10-26:** падение — это слабые ссылки статического glibc 2.19 на pthread, рантайм вызывал адрес 0. Полностью статический бинарь собирает `:unitool-cli:app:installStatic` через `app/static-ld.sh` (`-static`, `crtbeginT.o`, `--whole-archive -lpthread`). CI (`cli.yml`) выкладывает его артефактом вместе с SHA-256. Обычный `install` остаётся динамическим.
