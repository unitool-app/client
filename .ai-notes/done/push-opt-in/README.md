# push-opt-in — пуши только для приложений, которым они нужны

> v1.2, 2026-10-10. **Построено** 2026-10-10 (см. §«Что построено» ниже). Решения **D417–D430**, вопросы **187–191** (все закрыты).
> v1.1 — правки владельца: скрытое приложение спрашивает при первом входе, восстановленные из
> бэкапа push-приложения сразу считаются используемыми и спрашивают, объяснений нет, спрашиваем
> сразу, как приложением начали пользоваться (D418–D420 переписаны, вопросы 187 и 191 закрыты).
> v1.2 — ответы на 188–190: при пустом `used` PUT `apps: []` (D427), у конвертера пушей нет вообще
> (D428), сервер знает `apps` и шлёт только им (D429); телефон сам отбрасывает пуш приложению вне
> `used` (D430). Следующие свободные — **D431 / 192**.

Задача владельца: не спрашивать разрешение на уведомления сразу. Спросить, когда человек
включит приложение, которое через Superizer объявило, что работает с пушами.

## Что есть сейчас (проверено по коду)

- Разрешение **никто не запрашивает**. `PushService.requestPermission()` вызывает только
  bench-приложение Superizer (`apps/test-app/.../TestAppInstance.kt:209`). В Unitool вызовов нет.
- Зато **FCM-токен появляется при каждом старте**, хотя пуши никому не нужны:
  - Android: `PushTransport.android.kt`, в `init { refreshToken() }`, плюс авто-инициализация
    Firebase Messaging;
  - iOS: `iOSApp.swift:36`, где `registerForRemoteNotifications()` вызывается в
    `didFinishLaunching`.
- `DeviceRegistrar` (`PushRouter.kt:261`) получает токен и пишет в лог 12 символов, на сервер
  ничего не отправляет.
- Манифест про пуши знает только `pushTopics`. Он есть у одного приложения (по D428 уйдёт): currency-converter
  объявляет `rates`, но `subscribe` нигде не вызывает.
- `AppHandler.enable` — это `setup()` при старте для **всех** зарегистрированных приложений.
  Человек тут ничего не включает, поэтому это событие не годится для триггера. Для человека
  «включить» значит добавить на Home (каталог добавляет, long press убирает, D48) или
  разблокировать активацией (D8 тоже кладёт приложение на Home).

## Решения

| № | Решение |
|---|---|
| D417 | В манифесте новое поле `push: PushUse` = `None` (по умолчанию) / `Silent` / `Alerts`. Значение не `None` требует `minHostContract = 5`, по тому же правилу, что D138. Поля с объяснением нет |
| D418 | Хост ведёт множество `used: StateFlow<Set<AppId>>` — push-приложения (`push != None`), которыми человек начал пользоваться. Хранится в `host.push.used`. Входит: добавил на Home из каталога; первый запуск приложения (любым путём: тайл, каталог, ссылка, пуш-тап); восстановление из бэкапа. Выходит: убрал с Home, сброс приложения (D35) |
| D419 | Когда приложение входит в `used`. Каталог → Home: сразу. Скрытое: при первом входе в него, а не на экране активации (раскрытие по D8 кладёт на Home, но в `used` не вводит). Стартовый Home свежей установки: при первом открытии, при старте Unitool не спрашиваем. Восстановление из бэкапа: все push-приложения восстановленного Home сразу в `used`, вопрос — сразу после восстановления |
| D420 | Спрашиваем сразу системным диалогом, без своего листа и без объяснений. Если ОС уже разрешила — ничего не показываем. Каждое новое `Alerts`-приложение в `used` снова вызывает системный запрос; после окончательного отказа ОС сама перестаёт показывать диалог (Android 13+ после двух отказов, iOS после первого), тогда остаётся только строка в Settings (D424). Для `Silent` диалога нет |
| D421 | Пока `used` пусто, FCM не трогаем: без токена, без APNs-регистрации, без запросов в Google. Авто-инициализацию выключаем, вместо неё `PushTransport.activate()` |
| D422 | `DeviceRegistrar` ходит на сервер только при непустом `used`: первый раз POST `/devices`, при старте и ротации токена PUT `/devices/me`, на 401 регистрируется заново. Список `apps` = `used` |
| D423 | Топики подписываются у транспорта, только пока приложение в `used`. Если убрать приложение с Home, топики снимаются у FCM, но остаются в `TopicStore`. Если вернуть, они подписываются снова |
| D424 | В Settings хоста раздел «Уведомления»: какие приложения с Home шлют пуши и в каком состоянии разрешение. Если отказ системный, кнопка ведёт в настройки ОС |
| D425 | `runtime.push.requestPermission()` остаётся (повторный запрос из самого приложения), но работает только при `push = Alerts`. Иначе возвращает false и пишет предупреждение в лог |
| D426 | Superizer 0.6.0 / contract 5. Unitool переходит на эту версию одним коммитом |
| D427 | Когда `used` опустело, телефон делает PUT `/devices/me` с `apps: []`. Запись, `d_…` id, секрет и токен остаются, сервер этому устройству ничего не шлёт. Вернулось приложение с пушами — PUT с новым списком, id прежний. DELETE `/devices/me`, `deleteToken()` и стирание `ds_…` только при полном сбросе хоста |
| D428 | У currency-converter пушей нет: `push = None`, `pushTopics` убираются из манифеста. Deep link `rate` остаётся. В Unitool после этого нет ни одного приложения с пушами: никто не спрашивает, токена нет, сервер пуст, пока не появится первое настоящее (sudo-approve / подтверждения SSH) |
| D429 | Телефон передаёт `apps` (= `used`) в POST и каждом PUT. Сервер хранит их и в `unitool.sendPush` по умолчанию шлёт только устройствам, у которых `appId ∈ apps`; в ответе — сколько пропущено. `ignoreApps: true` — только для отладки |
| D430 | Роутер на телефоне отбрасывает **данные** пуша (не тап) приложению, которого нет в `used`, с причиной `NotUsed` (после `Disabled`). Тап пропускается: это вход в приложение той же дверью, что ссылка, а видимое уведомление Android в фоне рисует сам из блока `notification`, мимо роутера, — отбросить тап значило бы сломать уже показанное уведомление. Сейчас он проверяет только `handler.isEnabled`, а это верно для любого зарегистрированного приложения. Существующие установки: после обновления `used` пусто, приложение на Home войдёт в него при первом открытии (D419), миграции не нужно |

## Что построено (2026-10-10)

- **Superizer 0.6.0 / contract 5** — `4555765` (contract-3 = master). `PushUse`, `PushPort`,
  `PushGate`, `DeviceRegistrar` + `NetworkDeviceApi`, `PushControl`, `PushTransport.activate /
  permission / openSettings`, `secureRandomBytes`, раздел «Уведомления» и «Устройство для пушей».
  Тесты: `PushOptInTest` (11), `DeviceRegistrarTest` (7), `PushRouterOptInTest` (2),
  `AppRegistryTest.pushAsksForContractFive…`. `verify.sh` PASS.
- **Сервер** — `781d815` в unitool-app/server: колонка `apps` (TEXT с JSON-массивом, а не
  `text[]`: по умолчанию сервер на SQLite), фильтр в `sendPush`, `skipped`, `ignoreApps`.
- **Unitool** — `43f5b6b` (main = ssh-keyring): auto-init FCM выключен (Android meta-data, iOS
  `FirebaseMessagingAutoInitEnabled`), APNs-регистрация ушла из `didFinishLaunching` в
  `activate()`, `pushServer("https://unitool.m42.cx")`, у конвертера пушей нет, PRIVACY и
  описания для магазина переписаны.

Отличия от проекта:
- D430 сужено: `NotUsed` отбрасывает только данные, тап проходит (видимое уведомление в фоне
  рисует сама ОС из блока `notification`, мимо роутера).
- Свои ключи хоста: `host.push.used`, `host.push.device` (`d_…`, `ds_…` запечатан хостовым
  хранилищем секретов, SHA-256 токена, что последний раз отправлено). На Android ещё
  `host.push.asked` — чтобы отличать «не спрашивали» от «отказано навсегда».
- Полного сброса хоста нет, поэтому DELETE `/devices/me` не вызывается нигде.
- Проверка на телефоне: единственное приложение с пушами — тестовое (`push = Alerts`), вход по
  промокоду. Первый вход → системный запрос → токен → POST на сервер с `apps=["test-app"]`.

Хвосты: проверка на настоящих Android и iPhone; Play Console Data safety и App Store App Privacy —
задекларировать идентификатор устройства, который получает наш сервер; описания магазина в консоли
не обновлены (CI их не выкладывает).
