# 01 — схема: разделение секрета

> **Версия:** 1.1 · **Дата:** 2026-10-08 · Решения D359–D361, D364, D369

## 1. Как это называется (D359)

| Термин | Что значит | Где встречается |
|---|---|---|
| разделение секрета (secret sharing) | секрет делится на части; из заданного числа частей он восстанавливается, из меньшего — нет | общее название |
| secret splitting, аддитивное деление | n из n: части складываются, XOR или сложением по модулю 256 | Шнайер, «Прикладная криптография», гл. 3 |
| схема Шамира | k из n: секрет — свободный член случайного многочлена степени k−1, части — его значения в разных точках | Shamir, 1979; HashiCorp Vault, SLIP-39 |
| одноразовый блокнот (шифр Вернама) | XOR со случайным ключом той же длины, который не повторяется; абсолютная стойкость | почему одна часть из 2-из-2 — шум |
| split knowledge / dual control | ключ на компонентах у разных хранителей, ни один не знает его целиком | NIST SP 800-57, PCI |

«Вычитание» владельца — аддитивное деление 2 из 2:

```
D = C − M        C = D + M        (побайтно, по модулю 256; с XOR то же самое)
```

Если M случайна, той же длины и не повторяется, D и M по отдельности — шум. Это и есть одноразовый
блокнот: стойкость доказана, а не просто «пока никто не взломал».

## 2. Почему делится ключ, а не текст (D360)

Исходная идея — зашифровать текст в C и делить C. Предлагаю делить ключ K, которым зашифрован
текст. Оба шага владельца при этом остаются: шифрование ключом и разделение.

| | делить шифротекст C | делить ключ K |
|---|---|---|
| размер части | как весь текст | 48 байт всегда |
| часть в QR | только у короткого текста | всегда |
| «основная часть» | тоже обязательная часть, ещё одна точка отказа | контейнер; без k частей бесполезен, его можно копировать сколько угодно |
| переход на «k из n» | каждая часть растёт вместе с текстом | контейнер не меняется |
| целостность | XOR пластичен: владелец части переворачивает любой бит C, ничего не зная | MAC заголовка `ucrypt` и AEAD содержимого |

Ключ K:
- 32 байта из CSPRNG ОС, тот же источник, что ключ файла `ucrypt` (crypt/02 §1);
- новый на каждый `make`;
- целиком нигде не хранится и обнуляется сразу после работы.

## 3. Шамир над GF(2⁸) (D361)

- Поле GF(2⁸) с многочленом x⁸ + x⁴ + x³ + x + 1 (`0x11B`). Это поле AES, его же берут Vault и
  SLIP-39.
- Каждый из 32 байтов K делится отдельно:
  - случайный многочлен f степени ≤ k−1;
  - f(0) — байт ключа;
  - остальные коэффициенты — из CSPRNG.
- Часть номер x (1…n) — 32 значения f(x), по одному на байт ключа.
- Сборка — интерполяция Лагранжа в точке 0 по любым k частям с разными x.
- Умножение — 8 шагов со сдвигами и масками, без таблиц. Время не зависит от секретных байтов.
  Обратные элементы нужны только для x, а x не секретны.
- Пределы:
  - в формате 2 ≤ k ≤ n ≤ 255;
  - CLI даёт n и k от 2 до 5, k ≤ n (D369);
  - k = 1 запрещено: каждая часть была бы самим ключом.
- «2 из 2» по Шамиру: f(1) = s + a, f(2) = s + 2·a. Каждая часть по отдельности равномерна, как
  при XOR. Поэтому отдельного кода под XOR нет: 2 из 2 идёт тем же путём.

## 4. Что схема защищает и что нет

| Что случилось | Что получает посторонний |
|---|---|
| утекла одна часть: сфотографировали QR, потерян листок | ничего, если k ≥ 2 |
| утекли k−1 частей | ничего. Это не «трудно взломать», а нечего взламывать: любой ключ одинаково возможен |
| утёк контейнер | ничего без k частей: ключ 256 бит |
| утекли контейнер и k частей | всё. Это и есть ключ |
| владелец части подменил её | ничего не узнаёт. Собранный ключ не сходится с MAC заголовка, `join` отвечает «части не подходят к файлу». При n > k `join` перебирает наборы из k частей и называет подменённую |
| потеряно больше n−k частей | данные потеряны навсегда. Восстановления нет по замыслу. Поэтому мастер предлагает «2 из 3» (D369) |
| заражено устройство, на котором делают `make` или `join` | не защищает: там текст и ключ в открытом виде |

Правила, без которых таблица неверна:
- **Каждый `make` даёт новый K и новые части.** Части разных наборов не смешиваются: их различает
  `set_id`.
- **Части лежат в разных местах и у разных хранителей.** Две части в одном месте — это одна часть.
- **Каждый напечатанный QR считается известным** тому, кто мог его сфотографировать или
  отсканировать. Защита держится на k, а не на том, что QR никто не видел.

## 5. Почему не найденные QR (D364)

Владелец хотел брать ключами обычные найденные QR со ссылками. Это не работает:

1. **Содержимое публично.** QR на плакате, упаковке или сайте видят все. Ключ должен быть секретным
   и случайным, а в ссылке вроде `https://shop.example/menu` случайности почти нет.
2. **Секретом остаётся только выбор QR.** В криптографии считают, что противник знает схему
   (принцип Керкгоффса). Зная её, он переберёт QR с ваших фотографий, из мест, где вы бываете, с
   популярных сайтов. По сути это короткий пароль.
3. **Публичная часть в счёт k не идёт.** Если одна из двух частей — найденная ссылка, её знают
   все. Тогда вторая часть одна открывает ключ, и разделения нет.
4. **QR пропадает.** Плакат снимут, ссылку поменяют, и данные потеряны навсегда.

Что берётся от идеи — внешний вид: свои части выглядят как обычные ссылки (02). Их случайность
полная, поэтому ни один пункт выше к ним не относится.

Пароль как дополнительный фактор («k частей и пароль») возможен потом: в `ucrypt` для этого
зарезервирован получатель-пароль `0x0005` с Argon2id (crypt/01 §2.3). В первую версию не входит.
