# 02 — часть, ссылка, запись в контейнере

> **Версия:** 1.2 · **Дата:** 2026-10-08 · Решения D362, D363, D365, D372 · 1.1: адрес задаёт генератор, §5 про вопрос 171 · 1.2: принят `ucrypt`, ядро первым

## 1. Часть по байтам (D362)

| Смещение | Размер | Поле | Что |
|---|---|---|---|
| 0 | 1 | `version` | 1 |
| 1 | 8 | `set_id` | случайный id набора; тот же лежит в контейнере |
| 9 | 1 | `k` | сколько частей нужно |
| 10 | 1 | `n` | сколько частей всего |
| 11 | 1 | `x` | номер части, 1…n |
| 12 | 32 | `share` | f(x) для каждого из 32 байтов ключа (01 §3) |
| 44 | 4 | `check` | первые 4 байта SHA-256(`"ucrypt/1 split part"` ‖ байты 0…43) |
| | **48** | | итого |

- **`check`** ловит опечатки, обрезанную ссылку и случайно вставленный чужой текст. Это не защита
  от подделки: подделавший легко пересчитает `check`. Подделку ловит MAC контейнера (01 §4).
- **`set_id`** — 64 случайных бита, случайного совпадения у одного человека не будет. `join`
  сверяет его с контейнером до всякой криптографии: «эта часть от другого набора».
- **`version`** другая → отказ: «part version 2, this unitool reads 1; update unitool».
- **Честно о виде:** часть не неотличима от случайных данных, ведь `k`, `n` и `x` — маленькие
  числа. Цель — чтобы для человека это была обычная ссылка, а не стеганография.

## 2. Ссылка (D363)

```
<base>#<base64url(48 байт), ровно 64 знака, без '='>

https://example.com/p#AXq8Zr0m…
```

**`base` задаёт генератор** (вопрос 172): шаг мастера или `--base` у `make`. Своего адреса по
умолчанию нет ни в kit, ни в CLI. Проверка: абсолютный `http://` или `https://` адрес без `#`;
query можно.

### 2.1. Почему фрагмент

- Фрагмент — часть после `#` — браузеры и HTTP-клиенты на сервер не отправляют (RFC 3986 §3.5).
  Если чужой человек отсканирует QR обычной камерой, сервер `base` увидит только `GET /s`.
- При редиректе браузер переносит фрагмент на новый адрес, но и туда его не отправляет.
- Так же ключ в ссылке держали Firefox Send, Bitwarden Send и MEGA.

### 2.2. Оговорки

- **Скрипт страницы видит фрагмент** через `location.hash`. Поэтому страница по `base` должна быть
  статической, без JavaScript, аналитики и чужих скриптов. Мастер говорит это на шаге с адресом:
  > `The page at this address must not run scripts: a script there can read the part after '#'.`

  Если адрес чужой и там аналитика, она может записать полный адрес. Ущерб — одна часть
  (01 §4), но это всё же часть.
- **У того, кто отсканировал, адрес остаётся в истории браузера.** Значит, часть у него есть. Это
  то правило из 01 §4: каждый напечатанный QR считается известным.

### 2.3. Размер

Длина ссылки — длина `base` + 1 + 64. Версия QR зависит от адреса (уровень M):

| `base` | ссылка | версия QR |
|---|---|---|
| до 19 знаков (`https://ex.com/p`) | до 84 | 5 |
| до 41 знака | до 106 | 6 |
| до 57 знаков | до 122 | 7 |

- Если кодировщик добавит ECI, пороги сдвинутся на пару знаков. Точно решает `Qr.capacity`
  в kit.
- С коротким адресом плотность как у обычного QR на упаковке.

## 3. Как Unitool узнаёт часть

`SplitLink.parse(text)`:
1. Обрезать пробелы и переводы строк по краям.
2. Если есть `#`, взять всё после последнего `#`. Если нет — весь текст: голая строка тоже
   принимается.
3. Ровно 64 знака base64url → ровно 48 байт.
4. `version` = 1, `check` сходится, 2 ≤ `k` ≤ `n`, 1 ≤ `x` ≤ `n`.
5. Иначе `null`: «это не часть».

- **Домен не проверяется.** Работает ссылка на любом домене. Чтобы случайная чужая ссылка сошлась,
  нужны ровно 64 знака во фрагменте и 32-битный `check` — вероятность около 2⁻³².
- Телефон пока не трогаем (D371). Как Unitool на телефоне будет сканировать части и нужны ли
  App Links — в будущей заметке про телефон (вопросы 175, 176). `SplitLink.parse` лежит в kit,
  так что телефон возьмёт тот же разбор.

## 4. Запись в контейнере (D365)

Контейнер — `ucrypt` (crypt/01) версии 1.0 с новым типом записи. Ядро `ucrypt` делается первым,
и это его первый получатель (§5.3, D372):

| `type` | Имя | Критично | Тело |
|---|---|---|---|
| `0x0008` | ключ разделён | нет | 10 байт: `set_id` 8 · `k` 1 · `n` 1 |

- Ключ файла `ucrypt` (crypt/02 §1) и есть K, который делится. Из него, как обычно, HKDF выводит
  ключи содержимого, MAC заголовка и метаданных.
- Запись некритична, как все получатели (crypt/01 §2.1): читатель 1.0 скажет «ни один ваш ключ не
  подходит», а не «файл испорчен».
- **Чтение:**
  1. Есть `0x0008` → спросить `k` частей.
  2. Каждую часть сверить: `set_id` контейнера, разные `x`.
  3. Собрать K.
  4. Вывести `mac_key` и проверить MAC заголовка. Не сошлось → «parts do not match this file».
  5. Расшифровать.
- **Запись:** в файле с `0x0008` нет других получателей. Иначе один SSH-ключ открыл бы файл без
  частей. Смешивать можно будет потом, по отдельной просьбе.
- **Размер:**
  - короткий текст даёт контейнер около 150 байт плюс сам текст;
  - в арморе это около 200 знаков плюс текст × 4/3;
  - короткий текст в контейнере помещается в один QR (версия 40 держит до 2953 байт), так что
    «основную часть» тоже можно напечатать.

Строка для реестра в crypt/01 §2.3 добавлена.

## 5. `ucrypt` или свой формат (вопрос 171)

Владелец спросил: «в чём разница?» Ответ ниже. Решение владельца: «делай сразу нормально,
надолго, централизованно» → `ucrypt`, ядро первым (§5.3, D372).

Содержимое контейнера в обоих случаях одно и то же:
- текст, зашифрованный ключом K;
- `set_id`, `k` и `n`, чтобы `join` знал, какие части просить.

Стойкость тоже одна: AEAD с ключом 256 бит. Разница не в безопасности, а в обёртке: сколько
форматов Unitool будет поддерживать всегда.

### 5.1. Сравнение

| | `ucrypt` | свой маленький формат |
|---|---|---|
| что это | общий формат Unitool для всего шифрования: файлы ключам GitHub, ключам телефона (usb-sign/06) и теперь частям | формат только для частей: магия, версия, `set_id`, `k`, `n`, nonce, текст под XChaCha20-Poly1305 |
| код | ядро около 400 строк: преамбула, записи, MAC заголовка, куски, армор | около 100 строк |
| когда начать | ядро — после ответов crypt 139 и 140 (§5.3); весь `ucrypt` 1.0 — после 139–145 | сразу после переноса cli/02 §3.1 |
| большие файлы | кусками по 64 КиБ, память не растёт, можно читать любой кусок | целиком в памяти: для текста неважно, для файла в сотни МБ плохо |
| имя файла | есть, в зашифрованной записи | нет, или придумывать заново |
| потом | один разбор, один `inspect`, одни эталонные файлы. «Части или ключ телефона», «части и пароль» — просто ещё записи | два формата навсегда: два разбора, две схемы версий, два набора эталонов. Слить нельзя: старые файлы надо читать всегда |
| риск | формат `ucrypt` ещё не утверждён; если ревью crypt его поменяет, split подождёт | обвязку (версии, MAC, строгий разбор) пишем второй раз |

### 5.2. Короче

- `ucrypt` — дольше до первого результата, но один формат на всё.
- Свой формат — быстрее, но второй формат, который придётся поддерживать вечно, и без больших
  файлов.

### 5.3. Ядро `ucrypt` первым (принято, D372)

Частям из `ucrypt` нужно только ядро:
- преамбула, записи, MAC заголовка, куски STREAM, армор, метаданные;
- HPKE, RSA-OAEP, сеть до GitHub (crypt, вопрос 143) и стойкость RSA (вопрос 145) не нужны.

Поэтому:
1. Ядро `ucrypt` 1.0 делается первым, и `0x0008` — его первый тип получателя, уже в 1.0.
2. SSH-получатели `0x0001` и `0x0002` приходят следом, когда будут ответы crypt 141–145. Номера
   типов не меняются. Если ядро к тому времени уже выпущено, они просто войдут в 1.1: реестр это
   допускает (crypt/01 §5.2).
3. Из вопросов crypt для split тогда нужны только 139 (имена и магия) и 140 («сколько бит»).
