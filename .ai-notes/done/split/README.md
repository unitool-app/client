## Что сказал владелец (близко к тексту)

> «Нам нужно консольное приложение в связке с приложением в телефоне. Оно берёт текстовую
> информацию и сначала шифрует её каким-то ключом. Потом в бинарном виде вычитает из неё другую
> информацию, которая есть в другом месте. Так мы их разделяем: основная часть уходит в одно
> место, другая хранится где-то ещё. Когда соединяем, ещё надо расшифровать. Сначала провернуть
> всё в консоли, но писать так, чтобы потом переиспользовать в мобильном.»
>
> «Это будет надёжное хранилище? Как это называют в криптографии?»
>
> «Я бы хотел использовать в качестве ключей обычные найденные QR-коды со ссылками или подобные,
> которые не выглядят подозрительно.»
>
> На ответ «найденные QR ключами быть не могут, а свои QR в виде обычных ссылок — могут»:
> «Да, запиши.»

## Короткий ответ

1. **Это называется разделение секрета** (secret sharing).
   - «Вычесть одно из другого» — схема 2 из 2. Каждая часть по отдельности — шум: по ней о
     секрете нельзя узнать ничего, при любой вычислительной мощности.
   - Обобщение — схема Шамира «k из n». Любые k частей восстанавливают секрет, k−1 частей не дают
     ничего (01 §1).
2. **Делится ключ, а не текст** (D360).
   - Текст шифруется случайным ключом K в 256 бит. Получается контейнер — «основная часть». Его
     можно хранить где угодно: файл, сервер, облако.
   - На части делится только K. Часть — 48 байт при любом размере текста.
   - Контейнер — `ucrypt` из `.ai-notes/crypt` с новой записью «ключ разделён» (D365). Неверно
     собранный ключ виден по MAC заголовка ещё до расшифровки.
3. **Деление — Шамир над GF(2⁸)**, как в HashiCorp Vault и SLIP-39 (D361).
   - «2 из 2» владельца — частный случай с той же стойкостью.
   - Сколько частей всего и сколько нужно, выбирается от 2 до 5 (D369). Мастер предлагает
     «2 из 3»: тогда одну часть можно потерять.
4. **Часть — QR с обычной ссылкой** (D362, D363):
   ```
   https://<домен из генератора>/<путь>#AXq8Zr0m…   ← 64 знака после «#»
   ```
   - Адрес задаёт тот, кто генерирует части, своего по умолчанию нет (D363).
   - Часть стоит во фрагменте, после `#`. Браузер не отправляет фрагмент на сервер. Если QR
     отсканирует посторонний, часть не попадёт в логи сервера. Так же ключи в ссылках держали
     Firefox Send, Bitwarden Send и MEGA.
   - Unitool разбирает ссылку сам, без сети, и узнаёт часть по фрагменту, а не по домену.
   - QR выходит версии 5–6, такой же плотности, как QR на упаковке.
5. **Найденные QR ключами не бывают** (D364).
   - Их содержимое публично. Секретом остаётся только выбор QR, а это короткий пароль.
   - От идеи берётся внешний вид: свои части выглядят как обычные ссылки.
   - Части всегда генерирует программа из CSPRNG.
6. **Где код** (03). Сейчас только библиотека и CLI, телефон потом (D371).
   - Всё, кроме терминала, — в `unitool-kit` (D373):
     - `kit.crypt` — `ucrypt`, единый формат шифрования Unitool. Ядро делается первым, части —
       его первый получатель, запись `0x0008` уже в 1.0 (D372);
     - `kit.split` — Шамир, часть, ссылка и правила мастера (`SplitPlan`). Телефон потом возьмёт
       тот же код и те же правила.
   - Одно приложение CLI `split`: только вопросы и экраны. В терминале `unitool split` открывает
     мастер, шаг за шагом, с пояснениями (D370). Команды `make`, `join`, `inspect` с параметрами
     остаются для скриптов и тестов.
   - В первой версии шифруется текст, файлы — следующим шагом. Формат к ним уже готов (D374).

## Решения

| № | Решение |
|---|---|
| D359 | Схема — разделение секрета (secret sharing). «Вычитание» владельца — аддитивное деление 2 из 2. Оно входит в схему Шамира «k из n» как частный случай (01 §1) |
| D360 | Делится ключ K, а не текст и не шифротекст (01 §2):<br>• K — 32 байта из CSPRNG ОС, новый на каждый `make`;<br>• текст шифруется под K в контейнер — это «основная часть»;<br>• контейнер без k частей бесполезен, его можно копировать и хранить где угодно;<br>• части постоянного размера и помещаются в QR |
| D361 | Шамир над GF(2⁸) с многочленом `0x11B`, как в AES, Vault и SLIP-39 (01 §3):<br>• каждый байт K делится отдельно;<br>• коэффициенты — из CSPRNG;<br>• части в точках x = 1…n;<br>• умножение без таблиц, время не зависит от данных;<br>• в формате 2 ≤ k ≤ n ≤ 255, CLI даёт от 2 до 5 (D369);<br>• k = 1 запрещено;<br>• отдельного кода под XOR нет: 2 из 2 идёт тем же путём |
| D362 | Часть — 48 байт (02 §1): `version` 1 · `set_id` 8 · `k` 1 · `n` 1 · `x` 1 · `share` 32 · `check` 4. `check` — первые 4 байта SHA-256 от остального с меткой. Он ловит опечатки и обрезку, а не подделку: подделку ловит MAC контейнера |
| D363 | Часть как ссылка: `<base>#<base64url(48 байт)>`, 64 знака без `=` (02 §2–§3):<br>• часть только во фрагменте;<br>• `base` задаёт генератор: шаг мастера или `--base`. Своего адреса по умолчанию нет ни в kit, ни в CLI (**пересмотрено в 1.1**, вопрос 172);<br>• читатель принимает любой `base` и голую строку из 64 знаков;<br>• страница по `base` не должна запускать скрипты: скрипт страницы видит фрагмент. Мастер говорит это на шаге с адресом |
| D364 | Найденные и вообще общедоступные QR, ссылки и тексты не бывают ни частью, ни ключом (01 §5). Публичная часть известна всем и в счёт k не идёт. Все части генерирует программа. Пароль как дополнительный фактор — потом, через зарезервированную запись `0x0005` из crypt/01 §2.3 |
| D365 | Контейнер — `ucrypt` 1.0 с записью `0x0008` «ключ разделён»: `set_id` 8 · `k` 1 · `n` 1 (02 §4; **пересмотрено в 1.2**, D372):<br>• ключ файла `ucrypt` и есть K;<br>• запись некритична, как все получатели;<br>• писатель не смешивает её с SSH-получателями, иначе один SSH-ключ открыл бы файл без частей |
| D366 | Приложение CLI `split` (03 §2):<br>• мастер (D370), а под ним команды `make`, `join`, `inspect`;<br>• текст и части не берутся из argv (как D272), только stdin, файл части или ввод без эха;<br>• части показываются по одной на экран и стираются (`showScreens`);<br>• в файлы каждая часть пишется отдельно, с правами 0600;<br>• две части никогда не попадают в один файл или на один экран |
| D367 | Тесты (03 §3):<br>• умножение в GF(2⁸) против табличной реализации на всех 65 536 парах;<br>• все подмножества частей для k, n ≤ 5;<br>• точная равномерность одной части;<br>• независимая реализация Лагранжа в `jvmTest`;<br>• порча каждого байта и каждого знака части;<br>• разбор ссылок;<br>• `join` с частью из чужого набора и с подменённой частью;<br>• команды на `FakeIo`;<br>• нативный бинарь против JVM |
| D368 | Порядок (03 §4, **пересмотрено в 1.2**):<br>• ответы crypt 139 и 140;<br>• перенос cli/02 §3.1;<br>• `kit.split`;<br>• ядро `ucrypt` 1.0 с `0x0008`;<br>• CLI `split` с мастером;<br>• файлы;<br>• телефон — потом, отдельной заметкой |
| D369 | Число частей n и порог k выбираются от 2 до 5, k ≤ n. Мастер спрашивает сначала n, потом k и предлагает «2 из 3». В команде — `-n` и `-k`, оба обязательны. Формат части по-прежнему допускает до 255 (D361), предел 5 — только в CLI |
| D370 | Мастер (03 §2.1):<br>• `unitool split` в терминале открывает мастер, а не общее меню каркаса (D271);<br>• шаги с номером («Step 2 of 6»), пояснением и проверкой ответа; в конце сводка и `y/n`;<br>• в конце печатается та же команда одной строкой, без секретов, как в D271;<br>• под мастером те же `make`, `join`, `inspect`: мастер не делает ничего, чего не умеет команда;<br>• без терминала `unitool split` печатает справку с кодом 2;<br>• правила шагов (пределы, проверка адреса, k ≤ n) берутся из `SplitPlan` в kit (D373), у CLI только тексты и экраны |
| D371 | Сейчас только библиотека (`unitool-kit`) и CLI. Телефон — сканер частей, `join`, хранение части, App Links — потом, отдельной заметкой (вопросы 175, 176) |
| D372 | Контейнер — `ucrypt`, единый формат шифрования Unitool, без второго формата (02 §5). Делается ядром вперёд (02 §5.3):<br>• ядро `ucrypt` 1.0 — преамбула, записи, MAC заголовка, куски STREAM, армор, метаданные — и получатель `0x0008`;<br>• SSH-получатели `0x0001` и `0x0002` — следом, по ответам crypt 141–145, с теми же номерами;<br>• от вопросов crypt для начала нужны 139 и 140 |
| D373 | Всё, кроме терминала, — в `unitool-kit`:<br>• `kit.crypt` — `ucrypt`;<br>• `kit.split` — `Shamir`, `SplitPart`, `SplitLink` и `SplitPlan`: пределы n и k, проверка адреса, проверка набора частей, сводка как данные;<br>• в CLI остаются вопросы, тексты по-английски и экраны.<br>Будущий мастер телефона берёт те же правила и не расходится с CLI |
| D374 | Файлы — следующим шагом после текста. Формат уже готов: `ucrypt` шифрует кусками, имя файла лежит в зашифрованных метаданных. Тогда добавятся `make -i FILE`, `join -o` с именем из контейнера и пункт «файл» в мастере. В первой версии мастер спрашивает только текст |
