## 1. Что спросил владелец

Расшифровка голосовых, без слов-паразитов:

> «Надо предусмотреть, чтобы у нас были ещё и скрытые приложения: их нигде в плюсе не показывают,
> их никак нельзя увидеть. Только когда вводишь определённый код, они появляются, и после этого
> зайти в него обратно можно только по коду. Это ещё один тип приложений: код может активировать,
> а может вот так отдельно держать.»

> «Выглядеть это будет так. Человек заходит, нажимает на промокод, и у него открывается
> приложение. Когда он вышел, приложения уже не видно, оно опять полностью скрытое. Когда он
> опять хочет его открыть, он опять вводит промокод. А есть другой вариант, который добавляет
> приложение по промокоду: нажимаешь промокод, и приложение добавляется в список выбранных. То
> есть два типа: скрытое и доступное по промокоду.»

«Плюс» — это плитка «+» на Home, то есть каталог «Все приложения» (`ShellDestination.Catalog`).

## 2. Короткий ответ

1. **Второй тип уже есть.** «Доступное по промокоду» — это сегодняшнее скрытое приложение: в
   каталоге его нет, код его разблокирует и кладёт на Home (D8 + D48). Пример — `test-app` по коду
   `TEST-2026`. Его не трогаем.
2. **Первый тип наполовину есть.** Код может нести `Activation(unlock = false)`. Тогда хост
   открывает скрытое приложение и не разблокирует его, так что на Home оно не попадает. Но
   гарантий нет: тот же экран можно открыть QR-кодом, который составит любой, кто знает id
   приложения. Оно протекает в настройки, в журнал, в Service Menu и в «Хранение и безопасность»
   (§4). «Секретное» — это `unlock = false` плюс гарантии, которые даёт хост.
3. **Секретность — свойство приложения, а не кода** (D248): `AppMetadata.secret = true`. Дальше
   хост сам обеспечивает, что ни один путь, кроме кода, это приложение не откроет и не покажет.
4. **Магазины ставят жёсткое условие** (§6). И Apple (2.3.1), и Google (Deceptive Behavior)
   дословно запрещают «hidden, dormant, or undocumented features». Поэтому секретное приложение
   скрыто от **экранов человека**, но не от **магазина**. В описании сказано, что часть
   инструментов открывается кодом приглашения, а ревьюеры получают коды. Без этого секретный тип
   в сборку из магазина не ставим (вопрос 124).
5. **От кого прячем.** От того, кто открыл приложение или держит в руках разблокированный
   телефон, — да. От того, кто разобрал APK, — нет: код приложения лежит в сборке. Коды можно
   хранить хэшами, чтобы `strings` их не печатал (§5.5). По-настоящему закрытое содержимое
   возможно только с сервера (01/04).
6. **Оценка:** около 3 дней. Шаг 0 (§11) закрывает утечки, которые есть и у сегодняшних скрытых
   приложений, и выходит патчем без смены контракта.

Остаётся и мягкий вариант (D260). Код с `unlock = false` для **обычного скрытого** приложения
открывает его один раз и не кладёт на Home. Это «попробовать, потом решить», без гарантий
секретного: QR его всё равно разблокирует.

## 4. Что есть сегодня и где протекает

Как открывается приложение по коду. Экран «Активация» вызывает `ActivationService.fromPromo`. Тот
вызывает `PromoCodeResolver` (в Unitool это таблица `LocalPromoCodes` в `UnitoolHost.kt:116`),
затем `apply(activation)`. Если `unlock`, то `reveal` (разблокировать и положить на Home), потом
`handler.launch(force = true)` (`/prj/superizer/host/.../activation/Activation.kt:257`).
`force` и есть пропуск: скрытое приложение без разблокировки открывается только так.

Что мешает назвать это «секретным» уже сейчас:

|---|---|---|---|

закрывает шаг 0 (D259, §11) для «скрытого и не разблокированного», без смены контракта.
Остальное — новый тип.

Чего сегодня **нет**, и хорошо: через `?activate=` в браузере и `--activate=` на десктопе код не
принимается. Они идут через `fromDeepLink`, а там разбирается только QR-формат. Это сохраняем как
правило с тестом (D255): код из адресной строки остаётся в истории браузера.

## 5. Модель

### 5.1. Объявление (D249)

```kotlin
@Serializable
public data class AppMetadata(
    val title: Localized,
    val description: Localized? = null,
    val icon: AppIcon = AppIcon.Letter('?'),
    val hidden: Boolean = false,
    val category: String? = null,
    /**
     * Never listed, never unlocked, never on Home: only a code from the host's resolver opens it,
     * and only for one visit (done/idea/09). Must come with [hidden] = true and `minHostContract = 4`.
     */
    val secret: Boolean = false,
)
```

`AppRegistry.register` отклоняет манифест (`RegistrationRejected`) в четырёх случаях:

```kotlin
if (m.metadata.secret) {
    if (!m.metadata.hidden) reject("secret implies hidden")
    if (m.minHostContract < 4) reject("secret needs minHostContract = 4")
    if (m.deepLinks.isNotEmpty()) reject("a secret app serves no links")
    if (m.pushTopics.isNotEmpty()) reject("a secret app takes no pushes")
}
```

Почему так:
- **`hidden` обязателен вместе с `secret`.** Хост старше контракта 4 поля `secret` не знает. Для
  него такое приложение остаётся просто скрытым, а не видимым. То же правило, что D138 для
  `protection`, и поэтому `minHostContract = 4`.
- **Ссылки и пуши запрещены в манифесте, а не отрезаются молча.** Секретное приложение, которое
  объявило тему пушей, — ошибка автора, и лучше узнать о ней при регистрации, чем увидеть
  уведомление на заблокированном экране.
- **Логическое поле, а не `enum Visibility { Listed, Hidden, Secret }`.** Перечисление читалось
  бы лучше, но заменить `hidden: Boolean` в `AppMetadata` — двоичная несовместимость, а у
  Superizer BCV (D14). Поле только добавляется.
- **В манифесте, а не в коде.** Таблица кодов принадлежит хосту, а гарантия — приложению. Если бы
  секретность задавал код, QR с тем же id (L1) положил бы приложение на Home.

### 5.2. Единственная дверь — код (D250, D251)

| Путь | Что отвечает для секретного |
|---|---|
| `fromPromo(code)` | `Success(activation.copy(unlock = false))` и одноразовый талон (ниже) |
| `fromQr`, `activate`-ссылка, `?activate=`, `--activate=` | `Rejected(UnknownApp)`, как для несуществующего id |
| `fromDeepLink("unitool://app/<id>/…")` | `Rejected(UnknownApp)` (уже так для скрытых, остаётся) |
| пуш | невозможен (манифест); маршрутизатор на всякий случай отбрасывает с причиной `"unknown app"`, не `"Locked"` |
| `runtime.navigation.openApp(id)` | `NavigationError.UnknownApp`, не `Locked`: `Locked` сообщает, что такое приложение есть |
| `restoreLastSession` | снимка нет (§5.4) |
| Service Menu, «Разблокировать» | кнопки нет; в debug есть «Открыть» (`launch(force = true)`) |
| `addToHome`, `UnlockStore.unlock` | отказ и предупреждение в логе хоста |

**Одноразовый талон.** `apply` — публичный метод порта. Shell передаёт в него `Success` от любого
разборщика, а строку `source` выбирает сам (`"promo"` или `"qr"`), так что верить ей нельзя.
Поэтому `fromPromo` запоминает выданную `Activation` секретного приложения. `apply` принимает
секретное приложение только по **этому же объекту** (сравнение `===`) и тут же гасит талон.
Собранная вручную `Activation(AppId("secret-x"))` не откроет ничего.

```kotlin
private var ticket: Activation? = null

override suspend fun fromPromo(code: String): ActivationResult {
    // … service code first, as today (D20)
    val result = promo.resolve(code)
    if (result !is ActivationResult.Success || !isSecret(result.activation.appId)) return result
    val once = result.activation.copy(unlock = false)
    ticket = once
    return ActivationResult.Success(once)
}

override suspend fun apply(activation: Activation, source: String): Result<AppSession> {
    if (isSecret(activation.appId)) {
        if (ticket !== activation) return Result.failure(IllegalStateException("unknown app"))
        ticket = null
        return handler.launch(activation.appId, activation.config, force = true)  // no unlock, no event (§5.4)
    }
    // … as today
}
```

**Сборка, где приложение было скрытым, обновилась до секретного.** Запись в `host.unlocked` и
плитка в `host.home` остаются от прошлой версии. На старте хост вычищает секретные id из обоих
хранилищ. Shell и так фильтрует Home через `visible`, но `visible` смотрит на `unlocked`, поэтому
секретное исключается из `visible` явно.

### 5.3. Визит (D252)

Визит — это сессия. Её закрывает всё, что сегодня закрывает приложение: «назад», «Главная» в
меню, другое приложение из меню, смерть процесса. Следующий вход — снова по коду.

Уход в фон в том же процессе выходом **не** считается: человек переключился в мессенджер
скопировать что-то и вернулся — приложение на месте. Если у приложения есть замок (06), при
возвращении опускается занавес. Закрывать ли секретное после долгого фона — вопрос 126; по
умолчанию не закрываем.

Настройки, открытые из подвала меню, сессию не закрывают, как сегодня. Раздела секретного
приложения в них нет (§5.4), так что назад возвращаемся в него же.

Код может нести конфиг (`Activation(appId, config)`). Он действует на этот визит и не хранится:
провижининг из 16 (D51) случается только при `unlock = true`. Так два кода могут открывать одно
секретное приложение в двух режимах.

### 5.4. Никаких следов в оболочке (D253, D254)

| Утечка | Что делает хост для секретного |
|---|---|
| L3 разделы настроек | `AppHandler` не собирает `settingsSection` у секретного и пишет предупреждение в лог хоста. Настройки живут внутри приложения |
| L4 список замков | секретное не в списке. Его замок, если объявлен, работает как обычно |
| L5 снимок | не пишется ни при уходе в фон, ни при переходе в другое приложение; уже записанный стирается |
| L6 события | в `recentEvents` не попадают в релизе (в debug — да). Слушатели других приложений их не получают, собственный слушатель получает свои |
| L6 лог | строки логгера секретного приложения в общий буфер в релизе не идут (Service Menu их не покажет); в debug — как обычно |
| L7 `runtime.apps` | `list()` его не содержит, `get(id)` отвечает `null`, как для несуществующего |
| L8 диагностика | находки о его секретах не называют приложение: они складываются в общую строку хоста («секреты приложений: N запечатано»). Проверка идёт, имени нет |
| L9 резервная копия | данные идут по его `BackupPolicy`, без строки в превью и в отчёте о восстановлении (вопрос 130) |
| L2 Service Menu | в релизе нет в списке. В debug есть, с пометкой «· secret» и «Открыть», без «Разблокировать» |
| экспорт конфигов (16) | пропускает: хранимого конфига у секретного не бывает |
| `DeviceRegistrar` | id остаётся в описи сборки, которую узнаёт наш сервер: это список приложений сборки, а не факт использования |

**Окно (L12, D254).** Пока секретное на экране, превью в «Недавних» скрыто, а снимки экрана — нет
(их запрещает только `secureWindow`, если приложение его объявило):
- **Android 13+** — `Activity.setRecentsScreenshotEnabled(false)`. Убирает картинку в
  «Недавних», `FLAG_SECURE` не ставит.
- **Android 12 и старше** — такого вызова нет. Превью прячется, только если приложение объявило
  `secureWindow`, тогда работает `FLAG_SECURE`.
- **iOS** — `PrivacyCover` из `SecureWindow.ios.kt` уже закрывает снимок для переключателя
  приложений. Берём его же.

В `ui/platform` рядом с `SecureWindow` появляется
`@Composable expect fun RecentsPreview(hidden: Boolean)`, `AppContainer` зовёт его с
`app.metadata.secret`. Поведение `setRecentsScreenshotEnabled` проверяется на устройстве (шаг 5).

**Поле кода (L11, D255)** — для всех кодов, не только секретных. `AppTextField` уже принимает
`keyboardOptions`, и поля секретов из 06 §7 передают `autoCorrectEnabled = false`, чтобы
клавиатура не подсказывала и не учила слово. Экран «Активация» сейчас этого не делает. Нужна одна
строка:

```kotlin
keyboardOptions = KeyboardOptions(
    capitalization = KeyboardCapitalization.Characters,
    // Neither suggested over nor learnt into the dictionary, as the secret fields of 06 §7.
    autoCorrectEnabled = false,
)
```

Проверить на Gboard и на iPhone, что набранный код потом не подсказывается. Если Gboard всё же
его выучит, следующий шаг — `KeyboardType.Password` без визуальной маскировки: поле пароля
клавиатура не запоминает. На iOS у этого типа есть цена: `secureTextEntry` и предложение
сохранить пароль.

### 5.5. Коды (D256, D257)

**Где кнопка.** Владелец говорит «нажимает на промокод». Сегодня это иконка QR в подвале меню,
которая ведёт на экран «Активация» с двумя полями. Людям, которые ищут новое приложение, место в
«+», поэтому предлагаю строку «Есть код?» внизу каталога и подпись кнопки в меню «Код или QR»
(вопрос 125). Ни секретного, ни намёка на него каталог не показывает: строка одна и та же для
всех кодов.

**Коды в APK хэшами.** `PromoCodeResolver` — `fun interface`, хост подставляет свою реализацию,
и в библиотеке ничего не меняется. В Unitool появляется:

```kotlin
/** Codes as hashes: the APK carries no code that `strings` would print (done/idea/09 §5.5). */
class HashedPromoCodes(
    private val salt: String,
    /** hex(sha256(salt + normalise(code))) → what the code does. */
    private val table: Map<String, ActivationResult>,
) : PromoCodeResolver {
    override suspend fun resolve(code: String): ActivationResult =
        table[sha256Hex(salt + LocalPromoCodes.normalise(code))]
            ?: ActivationResult.Rejected(ActivationResult.Reason.UnknownCode)
}
```

- SHA-256 в общем коде уже есть: `services/ssh/.../crypto/Sha.kt`. Но он `internal`, поэтому
  нужен публичный `sha256(bytes)` в каком-то модуле сервисов или резолвер рядом с ним.
- Хэш нового кода печатает `scripts/promo-hash.sh <код>`. Сами коды лежат в
  `.secrets/promo-codes.md` (вне git, как ключи подписи). CI ничего не нужно: хэши в исходниках.
- Честный предел. Хэш прячет **дверь**, а не **комнату**: код приложения в APK всё равно лежит.
  Короткий код перебирается за минуты, поэтому коды секретных — от 12 случайных символов
  (около 60 бит). Сегодняшние `SCI` и `TEST-2026` можно оставить: они ничего не прячут.
- `serviceCode("SERVICE")` — секрет того же рода, но библиотека принимает его строкой. Перевести
  его на резолвер можно отдельной правкой; в этой заметке не трогаем.

**Один код на всех (D257).** Код — свойство сборки, а не человека. На одном телефоне данные
секретного приложения видит любой, кто знает код: жена, коллега, тот, кто подсмотрел. Для
приложения с личными данными правильная пара — `secret` + `LockPolicy.Required` из 06: код нужен,
чтобы найти приложение, отпечаток — чтобы войти. Хост этого не навязывает, решает автор
приложения. Личные коды, отзыв кода и ограничение попыток возможны только с сервера (D261).

### 5.6. Чего не закрываем

- Разбор APK: код приложения, его id, хэши кодов (короткий код переберут).
- Root или криминалистика: ключи prefs `app.<id>.*` и префиксы запечатанных секретов называют id.
- Чужие глаза, пока код набирают.
- Человек, который знает код и держит разблокированный телефон, если у приложения нет замка.

## 6. Магазины (D258)

Дословно, на 2026-10-05:

> **Apple, App Review Guidelines 2.3.1.** «Don't include any hidden, dormant, or undocumented
> features in your app; your app's functionality should be clear to end users and App Review. All
> new features, functionality, and product changes must be described with specificity in the Notes
> for Review section of App Store Connect (generic descriptions will be rejected) and accessible for
> review. … is grounds for removal of your app from the App Store … and termination of your
> developer account.»

> **Google Play, Deceptive Behavior.** «Your app's functionality should be reasonably clear to
> users; don't include any hidden, dormant, or undocumented features within your app.» … «All
> features available to the user should be clear and documented in your store listing.» … «Make
> sure your app behaves identically for a regular user and for a Google Play reviewer.»

> **Apple 3.1.1.** «Apps may not use their own mechanisms to unlock content or functionality, such
> as license keys, augmented reality markers, QR codes …» — в контексте платного открытия:
> подписки, уровни, премиум-контент.

Что из этого следует для Unitool:

1. **Скрыто от экранов, не от магазина.** Описание в `play/listing/description-*.md` и в App Store
   говорит общими словами: «часть инструментов доступна по коду приглашения, его выдаёт
   организация или автор инструмента». Сегодня в описании о кодах ни слова, хотя `test-app`, режим
   `SCI` и Service Menu по коду уже есть. Это уже небольшой долг.
2. **Ревьюер получает каждый код.** Apple — в Notes for Review, со списком секретных приложений и
   тем, что они делают. Google — в Play Console, App content → App access → «All or some
   functionality is restricted», с инструкцией и кодами. Внешний TestFlight проходит Beta App
   Review по тем же правилам.
3. **Ревьюер и человек получают одно и то же.** Никакого сервера, который во время ревью
   отключает код.
4. **За кодом нет ничего, что не прошло бы ревью само.** Код — способ не показывать инструмент
   всем, а не способ провезти то, что магазин отклонил бы.
5. **Коды не продаются.** Платное открытие по коду — 3.1.1, тогда нужна встроенная покупка.
   Бесплатный код приглашения для инструмента организации — обычная модель B2B.

Строка в `RELEASING.md`: «если в сборке есть секретное приложение или новый код — обновить Notes
for Review и App access». Можно добавить проверку в `play/check-listing.py`: если в таблице кодов
есть записи, в описании должна быть фраза о кодах.

Риск, который владелец должен принять сознательно (вопрос 124). По 2.3.1 Apple может удалить
приложение и закрыть аккаунт разработчика. Раскрытие ревьюеру этот риск снимает, если за кодом
честный инструмент. Если раскрывать не хотим, секретный тип живёт только в сборке вне магазина
(debug, внутреннее распространение).

## 9. Связь с другими заметками

- **06 (замок).** Независимы и хорошо складываются: `secret` + `LockPolicy.Required` (D257).
  Занавес при возвращении из фона работает и для секретного.
- **07 (иконка на рабочем столе).** Закрепить секретное — значит раскрыть его. `requestPinShortcut`,
  Quick Actions и всё, что появится по 07, для `secret` отказывают (D262).
- **16 (хранение конфига, экспорт).** Секретное не провижинится (`unlock` всегда false), экспорт
  его пропускает (D262).
- **01/04 (сервер).** Серверный документ не может сделать секретное видимым: `secret` сильнее поля
  `visible` из 01. Личные коды, отзыв и ограничение попыток — `RemotePromoCodes` поверх привязки
  01 (D261). Секретная *сборка* из кирпичей (04) — единственный способ, при котором содержимое не
  лежит в APK. Это отдельная работа, после v1.

## 10. Приёмка

1. Свежая установка. Секретного нет в каталоге «+», на Home, в меню, в настройках, в «Хранение и
   безопасность», в Service Menu релизной сборки.
2. «Есть код?» → код → приложение открылось. Назад → Home, приложения нигде нет. Снова код →
   открылось, данные прошлого визита на месте.
3. `unitool://activate?a=<id>`, `unitool://app/<id>`, QR JSON с этим id → тот же текст, что для
   несуществующего приложения.
4. В секретном нажал «домой» → в «Недавних» вместо экрана пусто (Android 13+, iPhone) → вернулся,
   приложение на месте. Процесс убит → запуск → Home, приложения нет.
5. Код типа «в выбранные» → приложение открылось, осталось на Home и в каталоге.
6. После ввода кода в любом другом поле клавиатура код не подсказывает.
7. Сборка, где приложение было скрытым и разблокированным, обновилась до секретного → плитка
   исчезла, разблокировки нет.

## 12. Решения (продолжают нумерацию; последнее было D247 в `../done/ssh-new/09`)

- **D248.** Два вида «по коду»: «в выбранные» — сегодняшнее `hidden` (D8 + D48), без изменений;
  «секретное» — новое. Секретность — свойство приложения, а не кода.
- **D249.** `AppMetadata.secret: Boolean = false`. Регистрация требует `hidden = true` и
  `minHostContract = 4` и запрещает ссылки и темы пушей. Перечисление вместо логического поля
  отвергнуто из-за BCV.
- **D250.** Единственная дверь — `fromPromo`. QR, `activate`-ссылка, `app/<id>`, пуш, `openApp`,
  снимок отвечают как на несуществующее приложение. `apply` принимает секретное только по
  одноразовому талону, который выдал `fromPromo`.
- **D251.** Секретное никогда не разблокируется и не попадает на Home. Остатки в `host.unlocked`
  и `host.home` вычищаются на старте.
- **D252.** Визит = сессия. Выход закрывает его, фон в том же процессе — нет. Снимок сессии
  секретного не пишется.
- **D253.** Следов в оболочке нет: разделы настроек, список замков, события (в релизе), буфер
  лога (в релизе), `runtime.apps`, диагностика (без имени), превью резервной копии, экспорт
  конфигов, Service Menu (в релизе). `DeviceRegistrar` не меняется.
- **D254.** Пока секретное на экране, превью в «Недавних» скрыто: Android 13+
  `setRecentsScreenshotEnabled(false)`, iOS `PrivacyCover`, Android 12 и старше — только через
  `secureWindow`. Снимки экрана не запрещаются.
- **D255.** Поле кода не учит клавиатуру — для всех кодов. Код не принимается из `?activate=`,
  `--activate=` и ссылок; правило закреплено тестом.
- **D256.** Коды в Unitool хранятся хэшами (`HashedPromoCodes`, SHA-256 с солью), открытые коды —
  в `.secrets/`. Коды секретных — от 12 случайных символов. Библиотека не меняется.
- **D257.** Код один на всех, и данные секретного видит каждый, кто знает код. Для личных данных
  рекомендуем `secret` + `LockPolicy.Required`; хост этого не навязывает.
- **D258.** Магазины: скрыто от экранов, не от магазина. Описание упоминает коды приглашения,
  ревьюеры получают коды (Notes for Review, App access), поведение одинаковое, коды не продаются.
- **D259.** Шаг 0 закрывает L3, L4, L7, L8, L9 для скрытого и не разблокированного приложения
  патчем 0.4.2 без смены контракта.
- **D260.** Мягкий вариант остаётся: код с `unlock = false` для обычного скрытого приложения
  открывает его один раз, без гарантий секретного.
- **D261.** Личные коды, отзыв и ограничение попыток — только через сервер (`RemotePromoCodes`
  поверх 01), не в v1. Серверный документ не может сделать секретное видимым.
- **D262.** Ярлык на рабочем столе (07) и экспорт конфигов (16) для секретного отказывают.

## 14. Реализация (1.1)

Сделано 2026-10-05, не закоммичено. Superizer — 0.5.0, контракт 4, `CHANGELOG.md`. Unitool переведён
на 0.5.0 (`libs.versions.toml`).

### 14.1. Отличия от §5–§11

- **Один выпуск вместо двух.** Шаг 0 (0.4.2) не выделялся: всё вошло в 0.5.0.
- **Кнопки «Есть код?» в каталоге нет** (ответ на 125). Зато на экране активации есть кнопка
  «Сканировать QR-код», если у хоста есть камера: `ActivationPort.canScan` / `scan()` в `core`,
  `SuperizerBuilder.qrScanner { … }` в `host`. Прочитанный текст сразу идёт в `fromQr`, как
  вставленный. В Unitool за кнопкой та же камера, что у 2FA (`tools.qr`). На десктопе и в вебе
  камеры нет, и под полем написано «Камеры здесь нет — вставьте текст».
- **Предел фона — в сборщике хоста, а не в манифесте**: `secretBackgroundLimit(millis)`, по
  умолчанию 5 минут. Секретное приложение, вернувшееся из фона после предела, закрывается, хост
  шлёт `ShellCommand.Close`, и оболочка уходит на Home. Короткая отлучка его не трогает.
- **Диагностика.** Находки о секретах секретного приложения из отчёта убраны целиком, а не
  свёрнуты в общую строку. Само приложение получает их через `runtime.diagnostics`.
- **Резервная копия.** При восстановлении данные секретного приложения добавляются к выбранным
  всегда: выбрать их нельзя, строки нет. В отчёте о восстановлении их тоже нет.
- **`Activated`** для секретного приложения выпускается как обычно. В релизе его отсекает фильтр
  журнала Service Menu, а другим приложениям его не отдаёт фильтр событий.
- **Хэши кодов (D256) сделаны** — владелец попросил сразу, 2026-10-05 (v1.2):
  - `HashedPromoCodes(salt, table)` лежит в библиотеке (`host/activation`), а не в Unitool, как
    было в §5.5. Причина — SHA-256 пришлось писать на чистом Kotlin в `commonMain` (проверен по
    стандартным векторам), а `services/ssh/crypto/Sha.kt` остаётся `internal`.
  - Код Service Menu стал строкой той же таблицы: `хэш → HostCommand(OpenServiceMenu)`, а не
    `serviceCode("SERVICE")` открытым текстом.
  - Соль — `PROMO_SALT = "unitool:"`. Хэш даёт `scripts/promo-hash.sh` (нормализация та же, что
    у `LocalPromoCodes`).
  - Открытые коды и что они открывают — в `.secrets/promo-codes.md`, вне git. В исходниках они
    остаются только в тестах, а `PromoCodesTest` проверяет, что каждый выданный код совпадает со
    своей строкой.
- **Шаг 0 сделан частично.** Разделы настроек и строки замков скрытого, но не разблокированного
  приложения больше не видны (L3, L4). А `runtime.apps`, диагностика и резервная копия по-прежнему
  показывают **скрытые** приложения (L7–L9 для `hidden`). Тестовое приложение специально видит
  всех, а `openApp` скрытого и так отвечает `Locked`. Для **секретного** закрыто всё.
- **Android 12 и старше:** превью в «Недавних» прячется, только если приложение объявило
  `secureWindow`, как и было в D254.

### 14.5. SSH-ключи по коду `{ssh-keys}` (1.3)

Владелец: «надо сделать, чтобы настройка SSH-ключей была по промокоду ssh-keys и в настройках
приложения их не было… лучше даже так — в фигурных скобках». Сделано так:

- **В библиотеке** новый вид ответа на промокод — `ActivationResult.OpenHostScreen(id)`. Хост
  регистрирует такие экраны через `SuperizerBuilder.hostScreen(screen)`, и их видно в
  `Superizer.codeScreens`. Экран активации открывает такой экран, а «назад» с него ведёт на Home, как
  с приложения, открытого кодом. Код к экрану, которого в сборке нет (тестовый хост без слоя
  безопасности), отвечает как неизвестный код.
- **В Unitool** раздел «SSH-ключи» больше не секция настроек (`SshKeysSection`), а экран
  `SshKeysScreen` с id `ssh-keys`. В таблице хэшей появилась строка `{ssh-keys}` →
  `OpenHostScreen("ssh-keys")`.
- **Код в скобках — точный (1.4).** Владелец попросил: «сделай для этих промокодов точное
  совпадение `[ssh-keys]`».
  - `PromoCode` в библиотеке: код в `{…}` или `[…]` сравнивается как написан, включая регистр,
    скобки и дефисы. Игнорируются только пробелы вокруг, которые ставит клавиатура. Остальные коды
    нормализуются по-прежнему.
  - Если код в скобках не нашёлся точно, он пробуется и нормализованным, так что `[SCI]` всё ещё
    открывает `SCI`. Наоборот не бывает: нормализованной строки у точного кода в таблице нет.
  - В таблице две точные строки, `[ssh-keys]` и `{ssh-keys}`: владелец писал код в квадратных
    скобках, а говорил «в фигурных». `ssh-keys`, `SSH KEYS`, `[SSH-KEYS]` и `[ssh keys]` ничего
    не открывают.
  - `scripts/promo-hash.sh` хэширует такие коды так же и помечает их «(exact)».
- **Исправления из «Хранения и безопасности» оставлены.** Кнопки «Добавить SSH-ключ» или «Сменить
  пароль ключа» у находки ведут прямо в мастер или на карточку ключа, без кода. Они появляются,
  только когда что-то не так — например, секреты лежат открытым текстом на десктопе, — и без них
  человек остался бы с предупреждением, которое нечем исправить. Списка ключей в настройках нет.
- **Тексты, отсылавшие в «Настройки → SSH-ключи», переписаны:** подсказка восстановления копии и
  импорт файла в 2FA. Теперь они говорят «добавьте ключ на это устройство», не называя код.
- **Тесты.**
  - Библиотека: `HashedPromoCodesTest` — код открывает экран, только если он есть. `HostSlotsTest`
    — экрана нет в настройках, а код открывает его, и «назад» ведёт на Home.
  - Unitool: `PromoCodesTest` и `KeysScreensTest` (в настройках ключей нет, по коду — есть);
    `KeyLevelChoiceTest` и скриншоты 26–33 и 41 ходят через код.
  - `SecureWindowTest` на устройстве: мастер не снимается скриншотом, а список ключей снимается.
