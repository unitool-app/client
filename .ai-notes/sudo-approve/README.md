## Что сказал владелец (близко к тексту)

> «Сервер приложения не должен знать ключи из `authorized_keys`. Мы отправляем только хэш открытого
> ключа, даже сам открытый ключ не отправляем, и дальше запросы идут тоже по хэшу. Приложение
> сообщает свои хэши: этот девайс содержит такие-то хэши, и на этот девайс мы отправляем запросы.
> Запрос приходит пушем, пуш лежит в системе. Человек отвечает, а агент ждёт какое-то время, пока
> запрос разрешится. Мини-апп: указываем, какие ключи публикуем (какие хэши), сервер unitool знает,
> что вот этот девайс содержит этот ключ, и шлёт запрос на него. Хэш — SHA-256 или что-то такое.»

Из предыдущих сообщений того же разговора:

> «На хосте — агент, он шлёт запрос на HTTP REST сервер, сервер шлёт пуш в приложение, я подписываю
> SSH-ключом в приложении, ответ идёт на сервер, сервер отдаёт агенту, агент выдаёт sudo.
> sudo должен даваться на какое-то время или пока не будет logout. sudo должен ждать ответа хотя бы
> 2 минуты.»

Сообщение 2026-10-10 (голосом, близко к тексту):

> «Сервер, который под sudo, каждый раз, когда кто-то пытается получить sudo и оно не разблокировано,
> делает запрос к нам. Наш сервер шлёт пуш на телефон, телефон разблокирует sudo через подпись. На
> телефоне лежат настоящие SSH-ключи. Запрос sudo уходит по всем authorized_keys, которые есть на
> хосте; в нём написано, какая команда собирается выполниться. Ключи хэшируются, и по ним идёт
> запрос на backend. Backend знает, что приложение тоже сделало хэширование своих ключей и
> отправило хэши на сервер, то есть знает device id и шлёт запрос на конкретный девайс. Если
> состыковалось — приходит пуш с командой, оператор на телефоне подписывает команду, подписанная
> команда улетает обратно, и мы проверяем публичным ключом, тот ли клиент подписал. Если ключ есть в
> authorized_keys — разрешаем sudo, если нет — не разрешаем. Напиши план действий и положи в
> ai-notes, потом попозже запустим.»

Как это прочитано:
- «Хэширование своих закрытых ключей» — это хэш **открытой половины** каждого ключа, который лежит
  в кольце телефона (D405). Хост знает только открытые ключи, поэтому совпасть может только такой
  хэш. От закрытого ключа с телефона не уходит ничего.
- «По каждому из них делает запрос» — один запрос со списком всех хэшей. Сервер сам раскладывает
  его по устройствам, первый ответ побеждает (D395). Для человека это то же самое, а гонок нет.
- «Пуш с командой» — пуш будит телефон, а команду человек видит на экране запроса. В тексте
  уведомления её нет: оно видно на заблокированном экране (D388).
- Схема 1.0 с этим совпадает. Версия 1.1 ничего в ней не отменяет, а раскладывает её на шаги.

## 0.2. Что изменилось в 1.2

Владелец, 2026-10-10 (близко к тексту):

> «Надо предусмотреть, чтобы у серверной части, которая делает запрос под sudo, была возможность
> зайти по паролю. Изначально sudo без пароля используем, но если я потерял телефон или что-то
> произошло — чтобы я мог зайти по паролю от локального аккаунта.»
> «185 — нет, так только по паролю. 186 — на время да.»

1. **Вход по паролю** (D411, 04 §13). sudoers остаётся `NOPASSWD`. Пароль спрашивает и проверяет
   сам агент через PAM (на Alpine без PAM — `crypt` по `/etc/shadow`).
   - Во время ожидания телефона человек нажимает «p» и вводит пароль своего аккаунта.
   - Если телефон недоступен, пароль спрашивается сразу (D412, `fallback = "password"` по умолчанию;
     это заменяет D399).
   - Без терминала пароля нет.
   - Верный пароль даёт грант на 15 мин, как обычный sudo (D414).
2. **Честная цена.** Пароль — второй равноправный вход, а не второй фактор. Кто знает пароль, тот
   пройдёт без телефона. Поэтому:
   - о каждом входе по паролю телефон получает пуш `sudo-notice` (D416);
   - `doctor` требует, чтобы у каждого из группы был рабочий пароль (D415), иначе потеря телефона
     означает потерю sudo;
   - строгим хостам — `password = "off"`.
3. **Оболочка только по паролю** (D413, ответ на 185). `sudo -s`, `sudo -i` и любая команда из
   `/etc/shells` на телефон не уходят, гранты на них не действуют. Поле `shell` из R убрано, D404
   отменено.
4. **Грант «на время» — на всю логин-сессию** (ответ на 186).
5. Отказ на телефоне остаётся окончательным для этого запроса: пароль после него не предлагается.
6. «Потерял телефон» — порядок действий в 04 §13.5.
7. Оценка ≈ 19–20 дней (+1 день на пароль).

7. **Канонический JSON** — свой, строгий, в `kit.sudo` (D403); фикстуры делают настоящие `ssh-keygen`,

## Короткий ответ

1. **Три части.**
   - **`unitool-sudo`** — агент на хосте: sudo approval plugin на C и бинарник на Kotlin/Native из
     этого монорепозитория (1.1, D401; было — Go).
   - **unitool-server** — новые ручки `/api/unitool/v1/sudo/*` и модель клиента-хоста `c_`.
   - **Мини-апп `apps/sudo-approve`** в Unitool. Она стоит на уже готовом `SshKeyring`: подпись
     SSHSIG делается с биометрией, `Age.encrypt` — чистая функция.
2. **Сервер знает только хэши** (D376): `keyHash = hex(SHA-256("unitool-sudo/v1\0" ‖ blob))`.
   - Ни открытый ключ, ни подпись на сервер не попадают: ответ телефона зашифрован age **на ключ
     хоста** (`/etc/ssh/ssh_host_ed25519_key`), и сервер видит непрозрачный блоб (D380).
   - Хэш — псевдоним, а не секрет. Кто знает открытый ключ (например, с `github.com/<login>.keys`),
     посчитает его хэш сам (§3.1, вопрос 177).
3. **Решение принимает только хост.** Сервер — почтовый ящик. Агент сам проверяет подпись по
   `/root/.ssh/authorized_keys` и `/etc/unitool-sudo/authorized_keys`, оба файла принадлежат root
   (D378, D379). Взломанный сервер может отказать или задержать, но не выдать sudo.
4. **Срок решает человек на телефоне** (D383): один раз · 15 мин · 1 ч · до выхода. Срок входит в
   подписанные данные. «До выхода» привязано к логин-сессии (`/proc/self/sessionid`) и гаснет с
   её концом, с потолком 12 ч.
5. **Ожидание по умолчанию — 180 с, максимум 300 с** (D385). Агент делает long-poll по 25 с до
   дедлайна, показывает в терминале код `K7QX` и обратный отсчёт, Ctrl+C отменяет запрос.
6. **Пуш лежит в системе, но источник правды — входящие на сервере** (D388). Приложение при каждом
   открытии и возврате на экран забирает `GET /sudo/inbox`: пуш может потеряться, запрос — нет.
7. **Оценка ≈ 18–19 рабочих дней** (1.1, 00-TASK §4; в 1.0 было ≈ 14, §10). Сюда входит шаг 0: регистрация устройства на сервере. Её в
   Unitool до сих пор нет, `DeviceRegistrar` только пишет в лог.

## 1. Схема

```
 хост (root)                         unitool-server                       телефон (Unitool)
 ───────────                         ──────────────                       ─────────────────
                                                           ┌── PUT /sudo/keys {hashes}   ◀── мини-апп:
                                                           │   (устройство d_… держит        «получать запросы
                                                           │    хэши H1, H2)                  по этому ключу»
 $ sudo apt upgrade                                        │
 sudo ─▶ approval plugin ─▶ unitool-sudo check             │
   1. есть живой грант этой сессии? ─ да ─▶ разрешить      │
   2. R = {host, hostKey, user, runas, argv, cwd,          │
          tty, session, nonce, iat, exp, code}             │
   3. POST /sudo/requests ───────────────────────────▶ находит устройства с Hi
        {keyHashes:[H(k) для k ∈ allowed], request:R}       │ ─── пуш (видимый) ─────────▶ 🔔 «sudo · K7QX»
   4. 🔐 Подтвердите на телефоне [K7QX]… 2:59               │                               │ тап / открыли
      GET /sudo/requests/{id}?wait=25 ◀─ long-poll ─┐      │ ◀── GET /sudo/inbox ─────────┤
                                                    │      │ ──▶ [R …] ───────────────────▶ экран запроса:
                                                    │      │                                 хост, команда, срок
                                                    │      │                                 [Отклонить] [1 раз]
                                                    │      │                                 [15 мин] [1 ч] [до выхода]
                                                    │      │                               keyring.sign(SSHSIG,
                                                    │      │                                 ns sudo-approve@superizer,
                                                    │      │                                 A = {sha256(R), срок})
                                                    │      │                               sealed = age(A‖sig → hostKey)
                                                    └──────│ ◀── POST /sudo/requests/{id}/answer {sealed}
   5. расшифровать sealed ключом хоста                      │
   6. sha256(R) совпал, подпись верна ключом из             │
      allowed, хэш ключа ∈ keyHashes, не истекло            │
   7. записать грант (если не «один раз») ─▶ разрешить     │
```

## 2. Угрозы и что от них защищает

| Кто атакует | Что может | Что не может |
|---|---|---|
| Взломанный или любопытный unitool-server | видеть хэши, метку хоста, IP, время, текст запроса в v1 (вопрос 176); отказать; задержать | выдать sudo: нет закрытого ключа. Подменить команду: телефон подписывает `sha256(R)`, агент сверяет со своим `R`. Увидеть подпись и открытый ключ: ответ зашифрован на ключ хоста |
| Тот же сервер, активная атака: подменяет `hostKey` в `R` на свой | расшифровать ответ и узнать открытый ключ (не закрытый) | выдать sudo: в подписанном `sha256(R)` чужой `hostKey`, агент отклонит. Телефон помнит ключ хоста при первой встрече (TOFU, D390) и показывает красное «ключ хоста изменился» |
| Пользователь хоста без root (или вредонос под ним) | слать запросы; пользоваться грантом своей сессии, пока он жив (как у обычного sudo-timestamp) | дописать свой ключ: файлы ключей принадлежат root, `~/.ssh` вызывающего не читается (D379). Подменить команду в запросе: телефон показывает ровно `argv` из `R` |
| Спам и «усталость от MFA» (как Uber, 2022) | слать много запросов | не больше 3 ожидающих на хэш и 6 в минуту на хост (D387); после трёх отказов подряд телефон предлагает заглушить хост на 10 мин (как D354). Для нового хоста экран отличается |
| Повтор старого ответа | — | `nonce` и `exp` в `R`, `sha256(R)` в подписи, ответ зашифрован на ключ конкретного хоста |
| Украденный телефон | — | каждая подпись идёт через системный промпт (уровни 1–2) или пароль ключа (уровень 3), как в `ssh-new` |
| Сеть между хостом и сервером | — | только HTTPS. Даже без него подделать ответ нельзя (подпись), можно только сорвать |

Предел честно указан в `docs/review/2026-09-26`: код с root на хосте или внутри процесса телефона в
момент подтверждения этим не останавливается.

## 3. Ключи и хэши

### 3.1. Хэш (D376, D377)

```
keyHash = lowercase_hex( SHA-256( "unitool-sudo/v1" ‖ 0x00 ‖ blob ) )      // 64 символа
blob    = открытый ключ в wire-формате SSH (то, что base64 во второй колонке authorized_keys)
```

- Доменная строка нужна, чтобы хэш **не совпадал** с обычным отпечатком `SHA256:…`. Записи сервера
  не сопоставляются напрямую с отпечатками из логов sshd, GitHub или бэкапа Unitool.
- Это не секрет. Кто знает открытый ключ, посчитает хэш сам и узнает, что у этого ключа есть
  телефон с Unitool. Если это недопустимо, есть «перец»: общий секрет, который вводится в мини-апп
  и в `/etc/unitool-sudo/config.toml` на каждом хосте. Это вопрос 177. В v1 перца нет, поле в
  формате под него зарезервировано: `"unitool-sudo/v1"` → `"unitool-sudo/v1p"`.
- Одна реализация в Kotlin (`services/ssh`, рядом с `SshPublicKey.fingerprint`) и одна в Go. Общие
  фикстуры лежат в `unitool-sudo/testdata/keyhash.json`: 4 типа ключей → ожидаемые хэши.

### 3.2. Какие ключи хост считает своими (D378, D379)

- `/root/.ssh/authorized_keys`. Ключ оттуда и так даёт root по SSH, поэтому разрешение sudo с ним
  не добавляет нового доступа.
- `/etc/unitool-sudo/authorized_keys`: ключи, которые дают только sudo, без входа root. Владелец
  root:root, права 0644.
- Никогда не читается `~/.ssh/authorized_keys` вызывающего пользователя: он сам может туда писать.
- Агент проверяет владельца и права обоих файлов и всех каталогов до `/`. Если что-то записываемо
  не-root, отказ с понятным сообщением.
- Типы: `ssh-ed25519`, `ecdsa-sha2-nistp256/384/521`, `rsa-sha2-*` (RSA ≥ 2048). `sk-*` и DSA
  пропускаются, как в D154.
- Опции строки разбираются, учитывается только `restrict`/`no-sudo-approve`. Строка с опцией
  `no-sudo-approve` в выборку не попадает.

### 3.3. Ключ хоста (D380)

- Ответ телефона шифруется age на `ssh_host_ed25519_key.pub`, а агент расшифровывает его закрытой
  половиной. age умеет SSH-ключи ed25519 и RSA напрямую. В Unitool это `Age.encrypt(…,
  listOf(hostKey))`, чистая функция без промпта.
- Если на хосте нет ed25519 host key, агент отказывается запускаться: `unitool-sudo doctor` скажет,
  как его создать.

## 4. Протокол

### 4.1. Запрос `R` (собирает агент)

Канонический JSON: ключи по алфавиту, без пробелов, UTF-8. Передаётся как base64 строки байтов, и
`sha256` считается от **этих байтов**, без повторной сериализации.

```json
{"argv":["/usr/bin/apt","upgrade"],"code":"K7QX","cwd":"/root","exp":1791612525,
 "host":"mu6","hostKey":"ssh-ed25519 AAAAC3Nz…","iat":1791612345,"nonce":"b64url-16-байт",
 "runas":"root","session":4182,"tty":"/dev/pts/3","uid":1000,"user":"dev0","v":1}
```

- `code` — 4 символа из `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`. Он показывается в терминале и в пуше,
  чтобы не перепутать два одновременных запроса.
- `argv` — после разбора sudoers, то есть с полным путём команды. Не больше 4 КБ, иначе обрезается
  с пометкой `"argvTruncated":true`. Обрезанный запрос нельзя подтвердить на «один раз» вслепую:
  телефон пишет «команда обрезана».
- `exp` = `iat` + `timeout` из конфига (180 по умолчанию, 30–300).

### 4.2. Ответ `A` (собирает телефон)

```json
{"decision":"session","req":"<hex sha256(R)>","until":1791655545,"v":1}
```

- `decision`: `once` | `ttl` | `session`.
- `until`: для `ttl` — сейчас + 900/3600; для `session` — сейчас + 12 ч (потолок); для `once` — `exp`
  из `R`.
- Подпись: `keyring.sign(key, "sudo-approve@superizer", bytes(A))` → армированный SSHSIG (sha512).
  Namespace — собственный namespace приложения по 02 §3.2, его разрешает обычный грант.
- `sealed = age_armor( age_encrypt( {"a": base64(bytes(A)), "sig": "<SSHSIG>"} , [hostKey] ) )`.

Отказ не подписывается и не шифруется: `{"decision":"deny"}`. Отказ может подделать и сервер, но
это ничего не даёт сверх того, что он может и так.

### 4.3. Проверка на хосте (D381)

Все пункты обязательны, порядок любой:
1. `age -d` ключом хоста прошёл.
2. `A.req == sha256(R)`, где `R` — байты, которые агент отправил сам и держит в памяти.
3. `SSHSIG verify(sig, bytes(A), "sudo-approve@superizer", K)` для ключа `K` из подписи, при этом
   `K` ∈ allowed (§3.2) и `keyHash(K)` ∈ `keyHashes` запроса.
4. `now ≤ R.exp`, а для `ttl`/`session` ещё и `A.until ≤ now + 12 ч`.

Иначе — отказ с кодом в журнале (§6.5).

## 5. unitool-server (`/prj/layers-fw/unitool-server`, слой `app-unitool`)

Сервер следует контракту README сервера: ошибки `{error:{code,message}}`, zod, `handle()`, тесты
через `createTestDb()`.

### 5.1. Клиент-хост `c_` (D382)

У сервера пока есть только устройства. Добавляется минимальный клиент по
`remote-progress/01` §1, чтобы не делать идентичность второй раз:

| | |
|---|---|
| id | `c_` + 12 base58 |
| секрет | `cs_` + 32 base58, рождается на хосте (`unitool-sudo enroll`), сервер хранит SHA-256 |
| auth | `Authorization: Bearer c_….cs_…` — слот, который `DeviceService.authenticate` уже отвечает 403 |
| ручки | `POST /clients {label, secretHash}` → `201 {clientId}` (без auth, лимит по IP как у `/devices`); `GET/PATCH/DELETE /clients/me` |

`label` — имя хоста, его видно в пуше. Пейринга и грантов из remote-progress здесь нет: адресат
определяется хэшем ключа, а не тем, какие телефоны знает клиент.

### 5.2. Ручки `/api/unitool/v1/sudo/*` (D384)

**Устройство** (`Bearer d_….ds_…`):

| Метод | Путь | Тело → ответ |
|---|---|---|
| PUT | `/sudo/keys` | `{hashes: [hex64, …≤32]}` → `200 {hashes}`. Заменяет набор целиком; `[]` — отписаться |
| GET | `/sudo/keys` | → `{hashes}` |
| GET | `/sudo/inbox` | → `{requests: [Req…], serverNow}` — ожидающие по моим хэшам, не истёкшие, не отвеченные |
| GET | `/sudo/requests/{id}` | → `Req` (тоже только если хэш мой), в любом состоянии, пока строка жива |
| POST | `/sudo/requests/{id}/answer` | `{decision:"deny"}` или `{decision:"approve", sealed}` → `200`; `409 conflict` — уже отвечено; `410 gone` — истёк или отменён |
| PUT | `/sudo/mutes/{clientId}` | `{until}` → `200`; не слать этому устройству пуши от хоста до `until` (во входящих запрос всё равно есть) |

`Req = {id, code, client:{id,label}, keyHashes (только мои), request (base64 R), createdAt,
expiresAt, state}`.

**Хост** (`Bearer c_….cs_…`):

| Метод | Путь | Тело → ответ |
|---|---|---|
| POST | `/sudo/requests` | `{keyHashes:[hex64, …≤16], request: base64 ≤ 8 КБ, code, ttlSeconds 30–300}` → `201 {id, expiresAt, devices}`; `404 no_device` — ни у одного устройства нет этих хэшей (агент сразу отказывает, без ожидания) |
| GET | `/sudo/requests/{id}?wait=0..30` | → `{state: pending\|approved\|denied\|expired\|cancelled, sealed?}`. При `pending` держит соединение до `wait` с и возвращает раньше, как только состояние сменилось |
| DELETE | `/sudo/requests/{id}` | → `204`; состояние `cancelled` (Ctrl+C) |

Ответ `sealed` отдаётся хосту **один раз**, после чего обнуляется в БД (D386).

### 5.3. Модели и миграции

- `UnitoolClient` (`unitool_clients`): `id`, `label`, `secretHash`, `createdAt`, `lastSeenAt`.
- `UnitoolSudoKey` (`unitool_sudo_keys`): `deviceId`, `keyHash`. Уникальный индекс по
  `(deviceId, keyHash)`, индекс по `keyHash`, каскад при `DELETE /devices/me`.
- `UnitoolSudoRequest` (`unitool_sudo_requests`): `id` (`sr_` + 12), `clientId`, `keyHashes` JSON,
  `request` TEXT, `code`, `state`, `sealed` TEXT, `answeredBy` (deviceId), `createdAt`,
  `expiresAt`, `answeredAt`.
- Каждая модель получает свою миграцию umzug, запись в `migrations/index.ts` и в `test/db.ts`.
- **Вычистка (D386).** Сторож раз в минуту переводит просроченные в `expired` и обнуляет `request`
  и `sealed` у всего, что старше `expiresAt` + 60 с. Строки без полезной нагрузки удаляются через
  7 дней. В админке видны только `id`, `client`, `code`, `state` и время, без `request` и `sealed`.
- В логах — ни `request`, ни `sealed`, ни хэшей целиком (`tokenTail`-подобный хвост из 8 символов).

### 5.4. Long-poll (D385)

- Ожидающие лежат в `Map<requestId, Set<resolve>>` на `Symbol.for('unitool.sudo.waiters')`
  (AGENTS.md: модуль может загрузиться дважды). `answer`, `DELETE` и сторож будят ждущих.
- Сервер однопроцессный, как и лимитер, и это записано как ограничение. Для нескольких процессов
  понадобится Postgres `LISTEN/NOTIFY` — не v1.
- `wait` ≤ 30 с, потому что у прокси перед сервером таймаут должен быть ≥ 35 с: это пункт для
  выкладки. Node по умолчанию держит `requestTimeout` 300 с, менять не надо.

### 5.5. Пуш (D387, D388)

Пуш уходит из `SudoService.create`, не через MCP:

- `appId: "sudo-approve"`, `link: unitool://app/sudo-approve/request?id=sr_…`, `title: "sudo · K7QX"`,
  `body: "<label>: подтвердите на телефоне"`, `data: {"v":1,"kind":"sudo","id":"sr_…"}`.
- Команда в пуш не попадает: её видно только на экране после открытия.
- `ttlSeconds` — остаток жизни запроса. `collapseKey` и `tag` — id запроса.
- Канал Android `unitool.sudo` с высокой важностью; iOS `interruption-level: time-sensitive`
  (вопрос 182).
- `buildUnitoolMessage` расширяется необязательными `channelId` (уже есть) и `interruptionLevel`.
  Тест, который пинит ключи, обновляется вместе с ним.
- Когда запрос отвечен с другого устройства, истёк или отменён, устройствам, которым ушёл пуш,
  отправляется тихий пуш `{"kind":"sudo-gone","id"}`. Приложение снимает уведомление по тегу, если
  процесс жив. Это best-effort: входящие и так покажут правду.
- **Пределы:**
  - не больше 3 запросов в состоянии `pending` на один `keyHash`;
  - не больше 6 в минуту на клиента;
  - `POST /clients` — 30 в час на IP;
  - ответ `429 rate_limited` с `Retry-After`.

### 5.6. Тесты сервера

- Цикл целиком через HTTP: регистрация устройства и клиента, `keys`, `create`, `inbox`, `answer`,
  long-poll (просыпается сразу после `answer`, а не по таймауту), `sealed` отдаётся один раз.
- Чужое устройство не видит запрос, если хэш не его (404, не 403 — чтобы не раскрывать
  существование).
- `no_device`, `409`, `410`, отмена, вычистка (поля обнулены), пределы, `mutes`.
- **Приватность.** Тест ищет по всей БД и по захваченным логам строки `ssh-ed25519`, `AAAA` и
  `BEGIN SSH SIGNATURE` и не должен их найти. Для этого в фикстурах `R` содержит только `hostKey`, а
  `sealed` — непрозрачная строка.
- Пуш через `LogPushProvider`: ключи `data`, канал, `interruptionLevel`, TTL.

## 6. Агент `unitool-sudo` (хост)

### 6.1. Состав (D389, вопрос 178)

> (1.1) Подробно — [04-host-agent.md](04-host-agent.md). Бинарник — Kotlin/Native (D401), а не Go;
> `fallback = "password"` заменён на `"allow"` (D399). Ниже — текст 1.0 для истории.

- **`sudo_approve.so`** — approval plugin на C для sudo ≥ 1.9, примерно 150 строк. Он передаёт
  контекст (`user`, `runas`, `command`, `argv`, `cwd`, `tty`) бинарнику через `execve` с
  наследованным stderr и ждёт код выхода: 0 — разрешить, иначе отказ.
  Подключение в `/etc/sudo.conf`: `Plugin sudo_approve sudo_approve.so`.
  - python_plugin не годится: не на всех хостах sudo собран с ним (проверить по хостам
    m42cx-network). Есть и хосты на Alpine/OpenRC (mu6). Там нет `loginctl`, а без `pam_loginuid`
    `/proc/self/sessionid` пуст — «до выхода» там работает только после включения PAM в sshd,
    иначе доступно только «один раз» (проверяет `doctor`).
  - PAM не годится: он не видит команду.
- **`unitool-sudo`** — статический бинарник на Go:
  - `check` — вызывает плагин;
  - `enroll --server URL --label NAME` — `POST /clients`, секрет в `/etc/unitool-sudo/client.key`
    (0600 root);
  - `status` — гранты, клиент, ключи и их хэши;
  - `revoke [--all]` — отозвать грант этой сессии;
  - `doctor` — права файлов, host key, версия sudo, связь с сервером;
  - `keyhash <файл|->` — печатает хэши для сверки с приложением.
- **Конфиг** `/etc/unitool-sudo/config.toml`:
  - `server`, `timeout = 180`;
  - `fallback = "deny" | "password"` (D391);
  - `max_session = "12h"`;
  - `exempt_users = []` — для автоматики, которой нужен sudo без человека: явный список, по
    умолчанию пусто.

### 6.2. Гранты (D383)

- Хранятся в `/run/unitool-sudo/grants/<uid>-<sessionid>.json`: каталог 0700 root, `tmpfs`, пропадает
  при перезагрузке. В файле — `A`, подпись, `R` и данные лидера сессии.
- **Сессия** — `/proc/self/sessionid` (аудит, ставит `pam_loginuid`, наследуется всеми процессами
  логина). Если там `4294967295` (сессии нет: cron, systemd-сервис, sshd без PAM), гранты типа
  `session` и `ttl` не выдаются, только `once`.
- **«До выхода»**:
  - при выдаче запоминаются PID лидера сессии (`loginctl show-session -p Leader` или поиск по
    `/proc/*/sessionid`) и его `starttime` из `/proc/<pid>/stat`;
  - при каждом `check` они сверяются: лидер умер или PID переиспользован — грант недействителен;
  - дополнительно, если есть PAM в sshd: `session optional pam_exec.so /usr/libexec/unitool-sudo/logout`
    удаляет файл сразу;
  - потолок — `max_session`.
- **«На время»**: тот же файл, проверяется `until`; привязан к той же сессии.
- Перед использованием гранта агент перепроверяет подпись в файле. Подложить файл не-root всё равно
  не может, но так `/run` не становится единственной точкой доверия.

### 6.3. Ожидание (D385)

- Терминал (stderr):
  `🔐 sudo: подтвердите на телефоне [K7QX] — mu6, apt upgrade … 2:47`.
  Строка перерисовывается раз в секунду, если stderr — tty.
- Long-poll по 25 с до `R.exp`; при сетевой ошибке — повтор через 2 с до дедлайна.
- SIGINT/SIGTERM → `DELETE /sudo/requests/{id}` → отказ. Нужно проверить, что sudo доставляет SIGINT
  дочернему процессу плагина. Если нет, плагин ловит его сам и шлёт дочернему SIGTERM.
- `no_device`, `401` клиента, нет связи до дедлайна — работает `fallback`:
  - `deny` — «телефон недоступен»;
  - `password` — обычный запрос пароля sudo. Для этого политика sudoers не должна быть
    `NOPASSWD`, см. D391.

### 6.4. sudoers и аварийный вход (D391, вопрос 181)

> (1.2) Аварийный вход теперь — пароль локального аккаунта, который проверяет сам агент (D411,
> 04 §13). Флага `--i-have-break-glass` нет: `doctor` проверяет, что пароль у каждого из группы
> рабочий (D415). Ниже — текст 1.0 для истории.

Рекомендация v1: телефон **вместо** пароля (`NOPASSWD` для группы `sudo-approve`) и
`fallback = "deny"`. Аварийный вход:
- консоль провайдера под root;
- либо пользователь из `exempt_users` с длинным паролем, записанным в `keys/` через age.

Перед включением на хосте `doctor` требует подтвердить, что аварийный вход проверен
(`--i-have-break-glass`).

### 6.5. Журнал

`/var/log/unitool-sudo.log` и syslog `authpriv`: время, пользователь, команда, `code`, `id`,
результат (`approved:once|ttl|session`, `denied`, `expired`, `cancelled`, `grant-hit`,
`verify-failed:<причина>`), отпечаток ключа, которым подписано.

### 6.6. Тесты агента

- Хэши по общим фикстурам.
- Подписи настоящим `ssh-keygen -Y sign`: агент принимает правильные и отклоняет подмену `argv`,
  `hostKey`, `nonce`, чужой namespace, ключ не из allowed, ключ из allowed с хэшем не из запроса,
  просроченный `exp` и `until` больше потолка.
- age: блоб от `age -R host.pub` расшифровывается, чужой — нет.
- Права файлов: `authorized_keys`, записываемый группой → отказ.
- Гранты: сессия жива / лидер умер / PID переиспользован (подмена `starttime`) / `sessionid`
  отсутствует.
- Плагин: контейнер Debian и Alpine с sudo 1.9, поддельный сервер, сценарии «разрешить», «отказ»,
  «таймаут», «Ctrl+C».

## 7. Мини-апп `apps/sudo-approve` (Unitool)

### 7.1. Предусловие: устройство на сервере (шаг 0, D392)

> (1.1) Подробно — [05-app.md](05-app.md) §1: свой регистратор Unitool на `PushTransport.token`
> (D397), секрет в `HostSecrets`, URL из `unitool.server.url`.

Это общая работа хоста, не мини-аппа; она же нужна remote-progress (его шаг 6).
- `DeviceRegistrar` в Unitool делает то, что описано в README сервера: секрет `ds_` в
  `runtime.secrets`, `POST /devices`, `PUT /devices/me` на каждом старте и при смене токена,
  перерегистрация на 401.
- Unitool просит разрешение на уведомления, когда приложению с `pushTopics` оно впервые нужно.
- Новый сервис хоста `services/unitool-server` (контракт в Unitool, Superizer не меняется):

  ```kotlin
  interface UnitoolServer {
      val device: StateFlow<DeviceState>            // NotRegistered | Registered(deviceId) | Failed(code)
      suspend fun call(method: String, path: String, body: ByteArray? = null): ServerResponse
      companion object { val Key = ServiceKey<UnitoolServer>("unitool-server") }
  }
  ```

  Хост подставляет `Authorization` сам, и секрет устройства приложению не виден. `path` ограничен
  префиксом, который хост выдал приложению: для `sudo-approve` это `/sudo/`.
- Базовый URL — константа сборки (открытый вопрос 114 о домене).

### 7.2. Манифест (D393, вопрос 180)

```kotlin
AppManifest(
  id = AppId("sudo-approve"), minHostContract = 3,
  metadata = AppMetadata(title = "sudo", icon = …, hidden = true, category = …),
  requires = setOf(SshKeyring.Key, UnitoolServer.Key),
  deepLinks = setOf("request", "keys"), pushTopics = setOf("sudo"),
  protection = AppProtection(lock = LockPolicy.Required, secureWindow = true),
  backup = BackupPolicy.None,          // хосты (TOFU) и история — не секрет, но и не для чужого телефона
)
```

Скрытое приложение (`hidden`, но не `secret` — D396) открывается промокодом `{sudo}` (`promo-hash.sh`). Пока оно не открыто, пуши
отбрасываются (`Locked`, D25), и это правильно: хэши без открытого приложения никто не публикует.

### 7.3. Экраны

1. **Ключи.**
   - Список ключей, на которые у приложения есть грант (`keyring.keys`).
   - «Добавить ключ» → `keyring.choose(KeyPurpose.Sign("sudo-approve@superizer"))`.
   - Переключатель «Получать запросы sudo» у ключа; изменение → `PUT /sudo/keys` со всеми
     включёнными хэшами.
   - У ключа: отпечаток `SHA256:…`, хэш (первые 12 символов — для сверки с
     `unitool-sudo keyhash`), «Скопировать строку для authorized_keys» и подсказка с одной командой
     установки агента.
   - Предупреждение, если ключ уровня 3 (пароль) или если устройство не зарегистрировано на сервере.
2. **Входящие** — главный экран.
   - Ожидающие запросы из `GET /sudo/inbox`: код, хост, команда одной строкой, обратный отсчёт.
   - Обновляется при открытии, при возврате на экран, по пушу (`runtime.push.messages`) и раз в
     5 с, пока экран виден.
   - Ниже — история решений на этом телефоне (локально, последние 200).
3. **Запрос** (`unitool://app/sudo-approve/request?id=…`).
   - Показывает:
     - хост: `label`, `R.host` и отпечаток `hostKey` с бейджем: «известен» / «новый хост» /
       «⚠ ключ хоста изменился»;
     - `user → runas`, полный `argv` моноширинным шрифтом с переносами, `cwd`, `tty`, `session`;
     - код крупно и время до `exp`.
   - Кнопки: **Отклонить** · **Один раз** · **15 мин** · **1 ч** · **До выхода**.
   - «Ключ хоста изменился» блокирует кнопки до явного «Доверять новому ключу» с повторным
     подтверждением.
   - Ключ для подписи — тот из включённых, чей хэш есть в запросе. Если таких несколько, первый
     по порядку в списке «Ключи».
   - Цепочка: `sign` (системный промпт или пароль) → `Age.encrypt` → `POST answer` → «Готово, хост
     получил ответ». 409/410 → «Уже отвечено / истекло».
   - Перед `sign` приложение само сверяет `keyHash`, разбирает `R` и проверяет `exp`.
     Промпт кольца показывает только 8 символов дайджеста, поэтому смысл запроса — на этом экране
     (вывод из `ssh-new`).
4. **Хосты.**
   - Известные хосты (TOFU-пины: `R.host` + `hostKey` + `clientId`) лежат в `runtime.storage`.
   - «Заглушить на 10 мин / 1 ч» → `PUT /sudo/mutes/{clientId}`. «Забыть».
   - Три отказа подряд от одного хоста → лист «Заглушить этот хост на 10 минут?» (по образцу D354).

### 7.4. Поведение пуша (D388)

- Тап ведёт по deep link на экран запроса. Если приложение на экране, пуш (`kind: sudo`) сразу
  открывает лист запроса поверх.
- `sudo-gone` снимает уведомление по тегу и обновляет входящие.
- Кнопок «Разрешить» прямо в уведомлении нет и не будет: промпт Android требует активити на
  переднем плане, а подтверждать вслепую, не видя команды, нельзя (как D354).

   - отпечаток или пароль;
   - sudo проходит;
   - `sudo -k` не мешает (это грант агента, отзыв — `unitool-sudo revoke`).
3. **iPhone** — TestFlight, тот же сценарий. До D175 ключ уровня 3: пароль вместо Face ID.

## 9. Выкладка (не v1 кода, но нужно до живого использования)

- unitool-server должен где-то жить по HTTPS, с прокси-таймаутом ≥ 35 с и `TRUST_PROXY` (вопросы
  114/115 открыты).
- Роль Ansible `unitool-sudo` в m42cx-network:
  - бинарник, плагин, конфиг, `enroll`;
  - `authorized_keys` для sudo;
  - группа `sudo-approve` в sudoers;
  - pam_exec на logout.

  Включение на хосте — только после `doctor --i-have-break-glass`.
