## 2. e2e: `unitool-sudo/e2e`

### 2.1. Стенд

`unitool-sudo/e2e/compose.yaml`:

| Сервис | Образ | Что внутри |
|---|---|---|
| `server` | `Dockerfile` из `/prj/layers-fw/unitool-server` | `PUSH_PROVIDER=log`, SQLite в tmpfs, порт 17290 |
| `mitm` | `unitool-sudo/e2e/mitm` (маленький ktor-сервер из модуля e2e) | прозрачный прокси между хостами и сервером. По команде теста подменяет `request` в `POST /sudo/requests`, подставляет старый `sealed` или чужой `hostKey` |
| `debian` | `debian:12` + `sudo` + `openssh-server` + `make gcc` | плагин, агент из `build/dist`, `install.sh --enable`, пользователь `dev` в группе `sudo-approve` (`NOPASSWD`). `cap_add: AUDIT_CONTROL`, чтобы `pam_loginuid` выдал `sessionid` |
| `alpine` | `alpine:3.20` + `sudo` + `gcompat` | только «один раз» и «отказ» (вопрос 184) |

«Телефон» — класс `PhoneSim` в тестах модуля `:unitool-sudo:e2e`. Он играет роль `apps/sudo-approve`
на **том же** `kit.sudo` и `kit.ssh`: регистрирует устройство, публикует хэши, читает входящие,
подписывает программным ed25519 (`Ed25519.sign` + `SshSig.armor`), запечатывает и отвечает. Код
экранов он не повторяет, только протокол.

Тест заходит на `debian` по `ssh dev@…` (настоящий логин, настоящая сессия) и набирает `sudo …`
через `ssh -tt`, чтобы был tty. Ctrl+C — байт `0x03` в tty.

### 2.2. Сценарии

| # | Сценарий | Ожидание |
|---|---|---|
| E1 | `sudo id -u`, телефон: «один раз» | вывод `0`; журнал `approved:once`; повторный `sudo` снова спрашивает |
| E2 | телефон: «отклонить» | sudo завершается с ошибкой, `not approved`; журнал `denied` |
| E3 | «15 мин», потом второй `sudo` | второй — без запроса на сервере (`GET /sudo/requests` в MCP пуст), журнал `grant-hit` |
| E4 | «до выхода», выход из ssh, новый вход, `sudo` | снова запрос; файл гранта удалён (`pam_exec`) или отвергнут (лидер умер) |
| E5 | `docker exec debian su - dev -c 'sudo true'` (нет `sessionid`) | у R нет `session`; `PhoneSim` отвечает `ttl` → агент разрешает как `once`, гранта нет |
| E6 | телефон молчит, `timeout = 30` | через ~30 с отказ, состояние `expired` |
| E7 | Ctrl+C во время ожидания | состояние `cancelled`; ответ `PhoneSim` → `410` |
| E8 | `mitm` подменяет `argv` в R, телефон подписывает подмену | агент: `verify-failed:req-mismatch` |
| E9 | `mitm` подменяет `hostKey` в R на свой | телефон шифрует на чужой ключ, агент: `verify-failed:age`. Второй вариант: `mitm` открывает конверт своим ключом и перепечатывает его на настоящий ключ хоста. Тогда агент даёт `verify-failed:req-mismatch`, потому что подписан R с чужим `hostKey`. `mitm` узнаёт только открытый ключ (README §2) |
| E10 | `PhoneSim` подписывает ключом, которого нет в allowed | `verify-failed:key-not-allowed` |
| E11 | `mitm` отдаёт старый `sealed` от прошлого запроса | `verify-failed:req-mismatch` |
| E12 | ни у одного устройства нет хэшей, `fallback = deny` | сразу отказ, `no-device`; ожидания нет |
| E13 | то же, `fallback = password` (по умолчанию) | сразу «password for dev»; верный пароль → команда выполнилась, `password-ok` |
| E14 | сервер остановлен, `fallback = password` | после неудачных попыток связи — запрос пароля; без tty (`ssh` без `-t`) — отказ |
| E15 | `/etc/unitool-sudo/authorized_keys` с правами 0664 | отказ `perm:/etc/unitool-sudo/authorized_keys`, сервер не вызван |
| E16 | `sudo -s` и `sudo -i` | на сервер не уходит ни одного запроса; сразу «root shell: password required»; верный пароль → оболочка; живой грант от телефона не помогает |
| E17 | `alpine`: E1 и E2 | как там |
| E19 | во время ожидания байт «p» в tty, потом верный пароль | запрос на сервере `cancelled`; `PhoneSim` получает `sudo-notice`; второй `sudo` в течение 15 мин — без вопросов (`grant-hit`, грант `password`) |
| E20 | «p», потом три неверных пароля | отказ, `password-failed`; уведомления нет |
| E21 | телефон ответил «Отклонить» | отказ; пароль **не** предлагается; следующий `sudo` → «p» работает |
| E22 | `password = "off"` | строки «(p = use password)» нет; `sudo -s` → отказ; `doctor` даёт WARN; `fallback = password` → ошибка конфига |
| E23 | `doctor` у пользователя без пароля (`passwd -l dev`) | FAIL «has no usable password» |
| E18 | приватность: после E1–E16 выгрузить SQLite сервера и `docker logs server` | нет `ssh-ed25519`, `AAAA`, `BEGIN SSH SIGNATURE`, полного keyHash, `cs_`; после сторожа нет `BEGIN AGE` |

владельца; **C** — iPhone (TestFlight). Для B и C нужен сервер, доступный из интернета (⏸ вопрос
114), и настоящие пуши (⏸ вопрос 115). Хост — контейнер `debian` со стенда, выставленный наружу,

## 4. Критерии приёмки

1. Все команды §1 зелёные; e2e E1–E23 проходят.
2. Проход A ручного сценария — без ✗. Проходы B и C — без ✗ или с решениями владельца в
   `PROGRESS.md`.
3. Нигде нет `cs_`, `ds_`, `sealed`, открытых ключей или подписей в журналах сервера (E18) и в
   логах Unitool (`AppServerAccessTest`).
4. Протокол один: `KeyHash`, `SudoRequest`, `Verdict` существуют только в `kit.sudo`; агент и
   приложение их не копируют (grep по `unitool-sudo/agent` и `apps/sudo-approve` на
   `"unitool-sudo/v1"` находит только импорт константы).
5. Скриншоты в `docs/review/sudo-approve/` приняты владельцем.
