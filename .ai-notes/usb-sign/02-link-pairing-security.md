## 1. Слои

```
ssh, git, scp, ssh-add                         (обычный OpenSSH, без правок)
   │  SSH_AUTH_SOCK, протокол ssh-agent
   ▼
unitool agent run          — desktop, нативный бинарь CLI (03 §1)
   │  слой 3: потоки со службами (07 §2): ssh-agent — поток на каждого клиента, рядом файлы, бэкап
   │  слой 2: канал Noise_KK — кадры, шифрование, взаимная проверка
   │  слой 1: труба байтов — usbmux / AOA / позже TCP (01)
   ▼
телефон: канал → AgentServer (свой на каждый поток) → RemoteAgent (политика компьютера)
         → HostAgent → Keyring → чип + системный промпт
```

Слои 2 и 3 — общий код в `unitool-kit` (`kit.link`), один для CLI и телефона. Слой 1 у каждой
платформы свой.

## 2. Desktop — ретранслятор, а не второй агент (D309)

Протокол ssh-agent на телефоне уже есть: `AgentServer.handle(bytes) → bytes` и `HostAgent`,
проверенные настоящим `ssh-add` (ssh-new/02 §2). Второй реализации на desktop не будет:
- desktop пересылает сообщения ssh-agent телефону как есть, по одному потоку на соединение
  клиента с сокетом;
- на телефоне на каждый поток создаётся свой `AgentServer`. Значит, `session-bind` и следующий
  за ним `SIGN_REQUEST` попадают в одно состояние — ровно как в `ssh-agent` OpenSSH.

Desktop сам отвечает только на то, что телефону не нужно:

| От клиента | Что делает desktop |
|---|---|
| `REQUEST_IDENTITIES` | канал есть → пересылает. Канала нет, но телефон подключён кабелем → ключи из кэша (03 §1.4). Телефона нет → пустой список |
| `SIGN_REQUEST` | пересылает. Нет канала → ждёт телефон до 30 с и зовёт человека уведомлением на desktop (03 §1.5), потом `FAILURE` |
| `EXTENSION session-bind@openssh.com` | запоминает в состоянии клиента и отвечает `SUCCESS`. При открытии потока на телефоне сначала пересылает все запомненные `session-bind` |
| `EXTENSION query` | отвечает сам: `query`, `session-bind@openssh.com` |
| `ADD_*`, `REMOVE_*`, `LOCK`, `UNLOCK`, смарткарты | `FAILURE`. Ключами телефона управляет только телефон |

Телефон не верит desktop и повторяет те же запреты сам (§6, `RemoteAgent`).

## 3. Зачем свой канал поверх трубы (D310)

Бриф просит не делать своей криптографии без необходимости. Необходимость есть: ни одна труба не
проверяет, кто на другом конце.
- К сокету usbmuxd на desktop может подключиться любой локальный процесс: на Linux он `0666`
  (01 §2.3).
- Порт, который приложение слушает на loopback iPhone, доступен и другим приложениям телефона.
- Устройство AOA открывает любой процесс desktop с доступом к узлу USB.

Поэтому поверх трубы идёт **Noise Protocol Framework** (rev. 34) — стандарт, а не своя схема:
- сессия: `Noise_KK_25519_ChaChaPoly_SHA256`. Обе стороны знают статические ключи друг друга после
  сопряжения. Два сообщения рукопожатия, свежие эфемерные ключи на каждую сессию;
- сопряжение: `Noise_XXpsk3_25519_ChaChaPoly_SHA256` (§4);
- примитивы уже есть и проверены: X25519 (RFC 7748), ChaCha20-Poly1305 (RFC 8439), SHA-256,
  HMAC, HKDF. После переноса cli/02 §3.1 они в `kit.crypto`;
- реализация — около 300 строк, проверка — векторы cacophony для обоих шаблонов.

Что рассматривалось и отброшено:

| Вариант | Почему нет |
|---|---|
| TLS 1.3 с закреплёнными сертификатами | в нативном бинаре нет TLS: пришлось бы тянуть OpenSSL через `dlopen`, а на телефонах — три разных стека |
| SSH как канал (телефон — маленький sshd) | огромный код ради трубы |
| libsodium `secretstream` + свой обмен ключами | библиотека в бинарь и всё равно своя схема рукопожатия |
| без шифрования, только проверка «телефон сопряжён» | см. список выше: трубу слышат чужие процессы |

## 4. Сопряжение (D311)

```
desktop                                         телефон
unitool agent pair
  статический ключ desktop (создан один раз)
  psk = 32 случайных байта, живёт 5 минут
  QR в терминале ───────────── камера ───────►  «Добавить компьютер»
                                                 «Разрешить компьютеру laptop видеть
                                                  открытые ключи и просить подписи?
                                                  Отпечаток SHA256:…»
                                                 [Отмена] [Сопрячь]
  ждёт телефон на любой трубе ◄──── кабель ────►
  Noise_XXpsk3: desktop — инициатор, телефон — ответчик
  телефон сверяет статический ключ desktop с ключом из QR
  desktop запоминает ключ телефона после первого
  транспортного сообщения телефона (WELCOME): только тогда psk проверен
  «Сопряжено: iPhone Ивана»                      «Компьютер добавлен»
```

- QR: `unitool-pair:1:` + base64url(`static_pub` 32 ‖ `psk` 32) + `;name=<hostname>`. Около
  110 символов, QR версии 6–7, в терминале — `QrTerminal.ansi` из kit (уже есть).
- Камера на телефоне — сервис `services/qr-scanner` (уже есть, им пользуется 2FA).
- Отдельный код сверки (SAS) не нужен: QR и есть аутентичный канал. Чужой процесс на телефоне
  не видит экран компьютера, чужой процесс на трубе не знает psk.
- psk одноразовый и умирает через 5 минут или после успеха.
- Хранение:
  - desktop: `~/.config/unitool/agent/desktop.key` (0600) — свой ключ; `phones.json` — открытые
    ключи телефонов, имена, идентификатор USB-устройства (UDID или серийный номер), кэш открытых
    SSH-ключей;
  - телефон: свой статический ключ — в `runtime.secrets` (запечатан хостом); список компьютеров —
    открытый ключ, имя, когда сопряжён, когда был последний раз.
- Удаление с любой стороны (`unitool agent forget`, «Забыть компьютер») — вторая сторона узнает об
  этом при следующем рукопожатии: оно не сойдётся.

## 5. Сессия и сообщения (D312)

**(1.3)** Таблица ниже — первая версия. `OPEN` теперь несёт имя службы, `AGENT` заменён на `DATA`
потока службы `ssh-agent`, добавлены `WINDOW` и статус в `CLOSE` — 07 §2.

После рукопожатия KK — транспортные сообщения Noise. Кадр на трубе: `uint16` длина ‖ шифротекст
(предел Noise — 65535 байт). Внутри — сообщения в кодировке SSH wire (`SshWire`, уже есть):

| Сообщение | Направление | Поля |
|---|---|---|
| `HELLO` | desktop → | версия протокола, имя компьютера (не проверено), версия CLI |
| `WELCOME` | ← телефон | имя телефона, все ключи кроме спрятанных (blob + комментарий + уровень хранения + что умеет), 06 §7 |
| `OPEN s` | desktop → | новый клиент сокета; подсказка: pid, имя программы, argv (не проверено, §7) |
| `AGENT s m` | ↔ | одно сообщение ssh-agent без изменений |
| `CLOSE s` | ↔ | клиент ушёл / телефон отменил |
| `KEYS` | ← телефон | набор видимых ключей изменился |
| `REFUSED s code` | ← телефон | почему следующий `FAILURE`: `server-unverified`, `unknown-data`, `rejected`, `timeout`. Компьютер показывает это уведомлением, `ssh` получает обычный `FAILURE` |
| `PING` / `PONG` | ↔ | раз в 10 с; три пропуска — канал разорван |

- Сообщение ssh-agent в канале — не больше 60 КиБ. Данные для входа по SSH — меньше 1 КиБ,
  `ssh-keygen -Y sign` через агента передаёт хеш, а не файл. Больше → `FAILURE`.
- Повтор (replay): у каждой сессии свои эфемерные ключи, внутри сессии Noise считает номера
  сообщений. Записанный трафик не проигрывается ни в новой сессии, ни в старой. Номер запроса из
  брифа — это номер потока `s`: протокол ssh-agent строго «запрос — ответ» по порядку в потоке.
- Отмена: `CLOSE s` от desktop (клиент `ssh` прерван) закрывает лист на телефоне.
- Код слоёв 2–3 в kit — без ввода-вывода (sans-IO): байты внутрь → события и байты наружу, как
  `AgentServer.handle`. Desktop крутит его в своём цикле `poll`, телефоны — в корутинах. В kit
  по-прежнему нет coroutines (D275).

## 6. Политика на телефоне: `RemoteAgent` (D313)

Обёртка над `HostAgent` на одного сопряжённого компьютера:
- `identities()` — (1.2) все ключи связки, кроме спрятанных переключателем «Только на этом
  телефоне» (06 §7, D341). Открытый ключ не секрет;
- `sign()` — любой из этих ключей, но всегда через лист и биометрию. Перед промптом разбирает
  данные (§7) и передаёт разбор в `UseReason`, чтобы лист и системный промпт показали, что
  подписывается;
- службы `keys` и `decrypt` рядом со службой `ssh-agent` — для команд CLI (06 §5, 07 §2);
- `add`, `remove`, `removeAll`, `lock`, `unlock` → отказ;
- `extension("session-bind@openssh.com")` — проверяет и запоминает привязку в состоянии потока;
- не больше 4 открытых потоков и одного листа одновременно. Остальные запросы ждут в очереди,
  кнопка «Отклонить всё и отключить компьютер» закрывает канал.

Журнал ключа уже пишет `AgentSign` с хешем данных. Добавляется: какой компьютер, пользователь,
отпечаток ключа сервера, итог. Сами данные не пишутся.

## 7. Что телефон может показать честно (D314)

Бриф прав: hostname в подписываемых данных нет. Но кое-что подписано, а кое-что можно проверить.

### 7.1. Что приходит в `SIGN_REQUEST`

**Вход по SSH** (RFC 4252 §7):

```
string  session_identifier
byte    50                      SSH_MSG_USERAUTH_REQUEST
string  user
string  "ssh-connection"
string  "publickey" | "publickey-hostbound-v00@openssh.com"
bool    TRUE
string  algorithm
string  public key
string  server host key         только у publickey-hostbound-v00@openssh.com
```

С `publickey-hostbound-v00@openssh.com` (OpenSSH 8.9+ с обеих сторон: сервер объявляет его в
`EXT_INFO`, клиент предпочитает) **ключ хоста сервера входит в подписываемые данные**. Подпись,
выданная для одного сервера, на другом не годится.

**`session-bind@openssh.com`** (PROTOCOL.agent) `ssh` шлёт любому агенту, к которому
подключился, перед подписью, в тот же поток: `string hostkey ‖ string session_identifier ‖
string signature ‖ bool is_forwarding`. Подпись — ключом хоста сервера над хешем обмена ключами.
Агенту, который отвечает `FAILURE`, `ssh` это прощает (`authfd.c`), так что старые агенты не
ломаются. Телефон
проверяет подпись `session_identifier` ключом хоста — проверка подписей Ed25519, ECDSA и RSA уже
есть в `services/ssh`. Так телефон сам, без доверия к desktop, знает: этот вход — в сессию с
сервером, у которого вот такой ключ хоста.

**SSHSIG** (`ssh-keygen -Y sign`, подпись коммита git): `"SSHSIG" ‖ namespace ‖ reserved ‖
hash_alg ‖ H(message)`. Видно назначение (`git`, `file`, …) и хеш, но не содержимое.

**Что-то другое** — непонятные байты. Показываются как «неизвестные данные» и хеш (§7.3).

### 7.2. Таблица доверия

| Что на листе | Откуда | Доверие |
|---|---|---|
| Пользователь `deploy` | подписанные данные | **подписано**: подпись не годится для другого пользователя |
| Ключ сервера `SHA256:…` | hostbound в данных или проверенный `session-bind` | **проверено** |
| Имя сервера «prod» | список серверов на телефоне: ключ хоста → имя, которое дал человек | **имя человека** |
| «github.com» | встроенный список ключей хостов GitHub, GitLab, Bitbucket | **встроено в приложение** |
| Компьютер «laptop» | статический ключ Noise сопряжённого desktop | **проверено сопряжением** |
| «Компьютер сообщает: `ssh deploy@prod`» | pid и argv клиента сокета (03 §1.3) | **не проверено**, мелким серым |
| «Через пересланного агента» | `is_forwarding` в `session-bind` | проверено, показывается предупреждением |
| Назначение подписи `git` | подписанные данные SSHSIG | **подписано** |

### 7.3. Правила листа

- Первая встреча ключа хоста: «Новый сервер SHA256:…. Компьютер называет его `prod` (не
  проверено). Имя для телефона: [prod]». Имя сохраняется после подписи.
- Компьютер называет сервер `prod`, а ключ хоста не тот, что закреплён за `prod`, → красное
  предупреждение и «Подписать» только через долгое нажатие.
- **Сервер не проверен — отказ** (ответ 151, D327). Нет `session-bind` и нет hostbound (клиент
  OpenSSH старше 8.9, клиенты на Go, PuTTY) → телефон отвечает `FAILURE` без листа и без промпта.
  В карточке компьютера остаётся строка «Отказано: клиент не сообщил ключ сервера (нужен OpenSSH
  8.9+)», компьютер показывает то же уведомлением. Переключателя «всё равно подписать» нет.
- **Неизвестные данные — отказ**, тоже без переключателя (D327).
- **SSHSIG** (`ssh-keygen -Y sign`, подпись коммитов git) — не вход на сервер, сервера в ней нет.
  Подписывается с листом «Подпись: git» и хешем (вопрос 157).

## 8. Требования брифа и угрозы (D315)

| Требование брифа §10 | Как выполняется |
|---|---|
| 1. Закрытый ключ не покидает чип | ключ уровня 1 — никогда: созданный в чипе (P-256 в Secure Enclave; P-256 и другие в Keystore) и импортированный на Android под «только отпечаток» (ssh-new/09 §3, §9). Ключ уровня 2 (импорт на iPhone, импорт с паролем на Android) на миг раскрывается в памяти приложения на телефоне — честная надпись уровня из каталога (ssh-new/06 §6.1). На компьютер — никогда |
| 2. Взлом desktop не даёт ключ | у desktop только открытые ключи и свой ключ Noise |
| 3. Каждая подпись — Face ID / отпечаток | уже так: `UsePolicy.EveryUse`, ключ с аутентификацией на каждую операцию (ssh-new D245–D247) |
| 4. Телефон показывает запрос до подтверждения | лист §7 + текст системного промпта |
| 5. Сопряжение аутентифицировано | QR + psk + Noise (§4) |
| 6. Повтор | эфемерные ключи и счётчик Noise (§5), `session_identifier` SSH |
| 7. Заблокированный телефон не подписывает | Android: ключи чипа уже `setUnlockedDeviceRequired(true)`. iOS: `WhenUnlockedThisDeviceOnly`, а приложение в фоне не слушает вовсе (01 §2) |
| 8. Нет `exportPrivateKey()` | инвариант связки ключей: такого метода нет ни в одном интерфейсе (ssh-new I-инварианты), канал добавляет только `AGENT` |

Угрозы, которых нет в брифе:

| Угроза | Что происходит | Ответ |
|---|---|---|
| Другое приложение iPhone подключается к порту на loopback | не знает статического ключа сопряжённого desktop | KK не сходится, соединение закрывается |
| Чужой процесс desktop говорит с usbmuxd или с USB | то же | то же |
| Вредонос на desktop под тем же пользователем | может читать `desktop.key` и просить подписи | каждая подпись — лист и биометрия на телефоне. Он может дождаться, когда человек сам запускает `ssh prod`, и подсунуть свой запрос к тому же серверу. Отличить нельзя — это предел любого агента и любого аппаратного ключа с касанием. Лист показывает подсказку о процессе, но она не проверена |
| Поток запросов (спам) | лист за листом | очередь, один лист за раз, «Отклонить всё и отключить» (§6) |
| Украден ключ Noise телефона | можно выдать себя за телефон перед desktop | выдать подпись всё равно нельзя: ключа SSH нет. Ключ лежит в `runtime.secrets` |
| Компьютер шлёт в `decrypt@` произвольные байты, чтобы получить сырую операцию ключом (сырая RSA — это подпись) | обойти лист входа по SSH | телефон принимает только запись получателя `ucrypt` или age, снимает её сам и отдаёт лишь ключ файла, если тег или паддинг сошлись (06 §5.2, D339) |
| Пересылка агента (`ssh -A`) на чужой сервер | сервер просит подписи для дальнейших прыжков | `is_forwarding` → предупреждение на листе. Пересылку настраивает человек на desktop |

## 9. Решения этой заметки

| № | Решение |
|---|---|
| D309 | Desktop ретранслирует протокол ssh-agent телефону как есть, поток на клиента. На телефоне свой `AgentServer` на поток. Сам desktop отвечает только на `query`, запоминает `session-bind` и отказывает в управлении ключами (§2) |
| D310 | Канал поверх трубы — Noise: `KK` для сессий, `XXpsk3` для сопряжения, X25519 / ChaCha20-Poly1305 / SHA-256 из kit, векторы cacophony. Безопасность не зависит от трубы (§3) |
| D311 | (1.2) Сопряжение по QR в терминале: статический ключ desktop + одноразовый psk на 5 минут. Телефон сканирует существующим `qr-scanner`. Выбора ключей нет: компьютер видит все открытые (D341) (§4) |
| D312 | Сообщения канала в кодировке SSH wire: `HELLO`, `WELCOME`, `OPEN`, `AGENT`, `CLOSE`, `KEYS`, `REFUSED`, `PING/PONG`. Код слоёв 2–3 в `kit.link`, без ввода-вывода (§5) |
| D313 | (1.2) `RemoteAgent` на телефоне: видны все ключи, кроме спрятанных; каждая операция — лист и биометрия; управление ключами запрещено; один лист за раз, очередь и «отключить» (§6) |
| D314 | Лист разделяет подписанное, проверенное и сказанное desktop. Ключ хоста проверяется по hostbound или `session-bind`, имя сервера даёт человек на телефоне (TOFU телефона), встроены ключи GitHub, GitLab, Bitbucket (§7) |
| D327 | (1.1, ответ 151) Вход только на проверенный сервер: без `session-bind` и без hostbound — `FAILURE` без листа, с причиной в карточке компьютера и в уведомлении на компьютере. Неизвестные данные — отказ. Переключателей нет. SSHSIG подписывается (вопрос 157) (§7.3) |
| D315 | Требования брифа §10 закрываются существующими инвариантами связки ключей плюс канал (§8) |
| D316 | Журнал подписи для компьютера: компьютер, пользователь, отпечаток ключа сервера, итог. Без данных и без `session_identifier` (§6) |
