## 4. Тесты (D323)

### 4.1. kit и `services/ssh` (desktopTest)

- Noise: векторы cacophony для `Noise_KK_25519_ChaChaPoly_SHA256` и
  `Noise_XXpsk3_25519_ChaChaPoly_SHA256`. Если в наборе нет нужного шаблона — сверка со второй
  реализацией на JVM только в тестах.
- Канал: подмена любого байта любого кадра → канал закрыт; повтор кадра → закрыт; перестановка →
  закрыт; чужой статический ключ → рукопожатие не сходится.
- Сопряжение: просроченный psk, второй телефон с тем же QR, ключ desktop не тот, что в QR.
- `SignRequestView`: настоящие байты, записанные в S5 (`publickey` и hostbound), SSHSIG с `git`
  и `file`, мусор, обрезанные данные.
- `session-bind`: подписи ключом хоста Ed25519, ECDSA P-256, RSA-SHA2; чужой `session_identifier`;
  `is_forwarding`; ключ хоста в hostbound не совпадает с привязанным.
- Нативный бинарь против JVM — байт в байт, как `NativeBinaryTest` у QR.

### 4.2. Сквозной тест без телефона (desktopTest)

В одном процессе JVM:

```
ssh -F test_config -o IdentityAgent=<sock> -p <port> user@127.0.0.1 true
   → ретранслятор (код CLI на JVM) → труба в памяти → kit.link
   → RemoteAgent → Keyring на desktop-бэкенде (P-256, Ed25519, RSA) → подпись
sshd -D -f <config> -p <port>   (свой ключ хоста, свой authorized_keys, без root, UsePAM no)
```

Проверяется:
- вход проходит для всех трёх типов ключей;
- `ssh-add -L` видит только открытые компьютеру ключи;
- закрытого ключа нет в байтах трубы: канарейка `SUPERIZER-CANARY-ED25519-SEED-01` и `LeakScanner`
  (ssh-new/03);
- телефон «вынут» → `ssh` сразу идёт к следующему ключу; канал «пропал» → ожидание и `FAILURE`
  через тайм-аут (на время теста — 1 с);
- компьютер просит `ssh-add -D`, `ssh-add key`, `-x` → отказ, ключи телефона на месте;
- запрос входа без `session-bind` и без hostbound (собран тестом) и непонятные данные → `FAILURE`
  без промпта и `REFUSED` с причиной (D327);
- `unitool keys` видит ключи «телефона» живьём и из кэша; ссылки `phone:…`, `gh:…`, `file:…`,
  `agent` разбираются одинаково во всех командах;
- SSHSIG ключом «телефона» проверяется настоящим `ssh-keygen -Y verify`; `git commit -S` с
  `gpg.format=ssh` подписывает через агента (06 §5.1);
- (этап 9) файл `crypt`, зашифрованный ключу «телефона», открывается через `decrypt@`; в `decrypt@`
  произвольные байты, обрезанная или чужая запись получателя → отказ без промпта; сырой результат
  RSA или X25519 наружу не выходит ни в одном случае (06 §5.2);
- `git ls-remote` через `ssh` к тому же `sshd` (на сервере `git-upload-pack` есть при
  установленном git).

Без `ssh`, `sshd` или `git` в `PATH` тест пропускается, и `verify.sh` перечисляет пропуски — как
`AgentInteropTest`.

### 4.3. Телефон

- `RemoteAgent` и лист — на desktop-бэкенде в `composeApp/desktopTest` (как `KeysScreensTest`):
  компьютер A не видит и не подписывает ключ, открытый только компьютеру B; лист показывает
  «не проверено» для подсказки; красное предупреждение при чужом ключе хоста.
- Android: эмулятор не умеет AOA. Инструментальный тест на `unitool35` проверяет сервис, лист и
  `BiometricPrompt` (рецепт из idea/06) через тестовую трубу из `androidInstrumentedTest`; в
  выпускном коде её нет. Сам аксессуар — только на телефоне владельца.
- iOS: пункт самопроверки «слушатель на loopback открывается и закрывается вместе с экраном».
  Вход по SSH — вручную по чек-листу.

### 4.4. Ручной чек-лист (Definition of Done брифа §17)

1. Чистый компьютер: `unitool link pair`, QR, телефон, «Сопрячь».
2. `ssh-add -L` → `ecdsa-sha2-nistp256 AAAA… work (secure-enclave)`.
3. Ключ в `authorized_keys` сервера, на сервере ничего не ставится.
4. `ssh user@server` → лист на телефоне → Face ID / отпечаток → вход.
5. Кабель вынут → `ssh user@server` этим ключом не входит.
6. Каталог `~/.config/unitool/agent/` скопирован на другой компьютер → закрытого SSH-ключа в нём
   нет (проверка канарейкой). Копия может выдать себя за этот компьютер, но каждая подпись всё
   равно требует телефон на кабеле и биометрию. «Забыть компьютер» на телефоне отключает и копию.
7. Телефон заблокирован → лист не подписывает до разблокировки.

## 5. Риски

| Риск | Чем грозит | Что делаем |
|---|---|---|
| iOS только на переднем плане | человек каждый раз открывает Unitool | ожидание с уведомлением (03 §1.5); позже Bluetooth или пуш (01 §5) |
| Ревью App Store: слушатель на loopback | отказ в App Store (TestFlight внутренним тестерам ревью не нужно) | писать в заметках к ревью, зачем; прецеденты в 01 §2 |
| AOA на конкретных телефонах | Samsung и другие ведут себя по-своему | S2 на телефоне владельца; запасной трубы нет (ответ 147) |
| Play: foreground service `connectedDevice` | анкета в Play Console, иногда видео | заполнить при выпуске, текст — владельцу (вопрос 154) |
| Права на USB на Linux | без правила udev ничего не видно | S3; команда, печатающая правило |
| Android 16 Advanced Protection | при заблокированном телефоне USB-данных нет | подсказка «разблокируйте, потом кабель» |
| iPhone: USB Restricted Mode | после часа блокировки новых соединений нет | то же правило: Unitool всё равно открыт |
| `ssh` без `session-bind` (Go, PuTTY, OpenSSH < 8.9 на компьютере) | такие клиенты не входят вовсе (ответ 151) | причина видна в карточке компьютера и уведомлением; в README — «нужен OpenSSH 8.9+» (Ubuntu 22.04+) |
| Ansible, `git submodule` — десятки подписей подряд | десятки Face ID | вопрос 152 (окно доверия), не в v1 |
