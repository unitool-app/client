# 05 — Проверка: тесты, e2e, ручной сценарий, приёмка

> Часть задания [remote-progress](README.md). Владелец просил три вещи: «покрыть тестами юнит»,
> «прокликать», «попробовать, чтобы всё работало». Здесь сказано, как выполняется каждая и что
> считается готовым.

## 1. Слои проверки

| Слой | Где | Что ловит | Запуск |
|---|---|---|---|
| Юнит: протокол | `unitool-progress/protocol/test` | схемы и фикстуры, `health`, ID | `npm test` |
| Юнит и HTTP: сервер | `server/test` (02 §10) | движок, таймауты, рассыльщик, заглушка, синхронизация, безопасность журналов | `npm test` |
| Юнит и процессы: CLI | `cli/test` (03 §11) | команды, коды, `step -- cmd`, очередь, вычистка, пейринг | `npm test` |
| **e2e** | `unitool-progress/e2e` (§3) | настоящий сервер + собранный CLI + поддельный телефон: сценарии целиком, в том числе заготовки из `GUIDE.md` | `npm run e2e` |
| Юнит и UI: приложение | `apps/progress/src/desktopTest` (04 §8) | модели по фикстурам, синхронизация, заглушка, лента, экраны | `./gradlew :apps:progress:desktopTest` |
| Инструментальные | `composeApp/androidInstrumentedTest` на `unitool35` | каналы, номер уведомления, deep link из пуша | `./scripts/verify.sh` |
| **Ручной сценарий** | эмулятор, телефон на Android, iPhone (§5) | реальные пуши, шторка, убитый процесс, заглушка, iOS | по чек-листу, со скриншотами |

`scripts/verify.sh` в `unitool-progress` работает по образцу Unitool: сборка, `tsc --noEmit`, eslint,
все тесты, e2e, `npm pack --dry-run`. Итог — отчёт `build/verify/report.md` и код 0 только при PASS.

## 2. Общие фикстуры — контракт между TypeScript и Kotlin

```
protocol/fixtures/*.json ──zod──▶ тесты protocol, server, cli
          │
          └─ scripts/sync-progress-fixtures.sh ─▶ unitool/apps/progress/src/desktopTest/resources/fixtures
                                                   └─ FixturesTest (Kotlin) + сверка SHA256SUMS
```

Правило (01 §9): новое поле → фикстура → схема → код с обеих сторон. `health-cases.json` проверяют
обе стороны, поэтому сервер и телефон не могут разойтись в том, что считать «нет ответа».

## 3. e2e в `unitool-progress/e2e`

**Стенд** поднимает сам тест:
- сервер в dev-режиме: `PUSH_MODE=fake`, `DEV_ROUTES=1`, `MIN_TIMEOUT_S=1`, `SWEEP_INTERVAL_MS=200`,
  временная база;
- собранный `cli/dist/cli.js` с временным `UNITOOL_PROGRESS_HOME`;
- **поддельный телефон** `e2e/lib/phone.ts` — то же, что делает приложение, через API устройства:
  `register`, `preview`, `claim`, `sync`, `mute`, `read`, `hide`, `forget`. Пуши, которые «ушли» на
  этот телефон, он читает из `/dev/pushes`.

Поддельный телефон доступен и руками: `npm run phone -- claim '<ссылка из QR>'`, `npm run phone --
sync`, `npm run phone -- pushes`. Так весь путь CLI → сервер проверяется без телефона и без Firebase
(§5.1).

Сценарии. Каждый проверяет три вещи: вывод и код CLI, сообщения в `/dev/pushes` (заголовок, тело,
канал, `tag`, `silent`) и `sync` телефона (состояние, ошибка, лента).

| # | Сценарий | Ожидание |
|---|---|---|
| E1 | `login` → `pair` → два телефона сканируют | в `credentials.json` два токена; у обоих телефонов в `clients` — этот CLI |
| E2 | `notify "Бэкап готов" --level ok` | по пушу на каждый телефон, `unitool.results`, `silent=false`; в ленте обоих по записи |
| E3 | bash-заготовка из `GUIDE.md`, всё успешно | пуши: создано → 4 шага → итог; итог заменяет ход (тот же `tag`); `succeeded` |
| E4 | та же заготовка, команда шага 2 — `exit 1` | `failed(exit)`, шаг `test`, код 1, хвост лога; **один** итоговый пуш, хотя сработали и `step`, и ловушка `ERR` |
| E5 | ручной шаг, падает `false` внутри цикла | `failed(error)` «Строка N: false» |
| E6 | `exit 0` посреди скрипта | `failed(unclosed)` |
| E7 | SIGINT во время команды шага | `cancelled`, код скрипта 130 |
| E8 | SIGKILL скрипта при `--timeout 2s` | через ~2 с и один проход сторожа — `failed(timeout)`, пуш «нет ответа» |
| E9 | Python-заготовка, исключение на шаге 2 | `failed(error)`, `ValueError: …`, в логе traceback |
| E10 | телефон 2 заглушен на час, `notify` | пуш только на телефон 1; у телефона 2 запись в ленте с `silenced`; после `/dev/clock +3601` пуши снова идут |
| E11 | сервер остановлен → `new`, `step`, `done` | ID напечатан, коды 0, события в `pending`; сервер поднят → досыльщик дослал, итог `succeeded` |
| E12 | сервер лежит дольше таймаута задания | после подъёма льготный период: ложного «упало» нет |
| E13 | телефон отключает CLI (`DELETE /me/clients`) | `devices` у CLI: «отключён с телефона», токен удалён из файла; следующий `notify` на него не идёт |
| E14 | «Забыть устройство» | то же для всех CLI; `sync` старым ключом → 401 |
| E15 | 60 `update` за 10 с | на телефон уходит не больше 2–3 пушей счётчика, последний — с последним значением |
| E16 | вычистка | скрипт печатает поддельные `ghp_…`, `AKIA…`, `Bearer …` и значение `API_TOKEN` из окружения и падает: в логе на сервере — только `***` |
| E17 | журнал сервера после всех сценариев | ни одного `cs_`, `ds_`, `dt_`, `pt_` и FCM-токена |

Заготовки для E3–E9 **вырезаются из `cli/GUIDE.md`** по меткам блоков кода, а не хранятся копией.
Отказы подставляются окружением, которое заготовка передаёт командам шагов (`FAIL_AT=2`). Меняешь
инструкцию — меняется тест.

## 4. Ручная проверка приложения без сервера

Пока сервера нет, экраны и роутер можно проверить через Service Menu → «Симулировать пуш» (13 §7):
вставить `data` из `protocol/fixtures/push-*.json`. Это проверяет:
- роутер (`silent`, `link`);
- приём данных мини-аппом;
- переход по тапу.

Шторку это не проверяет: её рисует Firebase.

## 5. Ручной сценарий — «прокликать»

Три прохода: **A** — эмулятор `unitool35`, **B** — телефон на Android, **C** — iPhone через
TestFlight (`testflight`-метка на PR, `ios.yml`). В A и B сервер локальный: для эмулятора —
`http://10.0.2.2:8787` в debug-сборке, для телефона — туннель с HTTPS. В C — только HTTPS: туннель или
выложенный сервер. Настоящие пуши требуют `PUSH_MODE=gateway` и шлюза с сервисным аккаунтом
`unitool-b1529` (вопрос 115). До ответа A проходится с `PUSH_MODE=fake`: всё, кроме шторки, плюс §4.

Каждый шаг — отметка ✓/✗ и скриншот, где сказано 📷. Результаты — таблица в
`.ai-notes/remote-progress/PROGRESS.md` §3, скриншоты — в `docs/review/remote-progress/`.

## 6. Критерии приёмки этапа

Этап готов, когда выполнено всё ниже:

1. `unitool-progress/scripts/verify.sh` — PASS: протокол, сервер, CLI, e2e E1–E17, упаковка.
2. `unitool/scripts/verify.sh` — PASS: новые desktop-, UI- и инструментальные тесты из 04 §8 плюс
   всё, что было зелёным до этапа.
3. Ручной сценарий §5: A — целиком; B и C — M1–M33 без ✗, либо каждый ✗ записан в `PROGRESS.md` с
   причиной и решением владельца.
4. Скриншоты экранов (04 §8.2) и ручного сценария (📷) выложены и приняты владельцем.
5. Сервер работает по HTTPS-адресу (вопрос 114), пуши идут через шлюз с аккаунтом Unitool (вопрос
   115).
6. CLI опубликован в npm, `npx unitool-progress pair` работает с чистой машины (вопрос 116).
7. `play/PRIVACY.md`, Data Safety и App Privacy переписаны по собранному APK и приняты владельцем (04
   §7.4) — до выпуска Unitool с мини-аппом.

Пункты 5–7 зависят от владельца. Если ответов нет, этап закрывается на пункте 4 со статусом «готово к
выкладке», а 5–7 остаются ⏸ в `PROGRESS.md`.
