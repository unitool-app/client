# 01 — формат `ucrypt` 1.0

> **Версия:** 1.0 · **Дата:** 2026-10-06 · Решения D295–D297, D301, D302

## 0. Общий вид

```
┌──────────────────────────────── header (header_size bytes) ───────────────────────────────┐
│ preamble, 84 bytes │ record 1 │ record 2 │ … │ record N │ header MAC, 32 bytes             │
└────────────────────────────────────────────────────────────────────────────────────────────┘
┌──────────────── payload (payload_size bytes, starts at payload_offset) ────────────────────┐
│ chunk 0 │ chunk 1 │ … │ chunk n−1                                                          │
└────────────────────────────────────────────────────────────────────────────────────────────┘
```

- Все числа — big-endian, без знака. Строк в формате нет: только числа и байты.
- **Заголовок** — всё до `header_size`. Последние его 32 байта — HMAC-SHA-256 всего, что перед ними.
- **Записи** — получатели и метаданные, по одной на TLV.
- **Содержимое** — открытый текст кусками по `chunk_size`. Каждый кусок зашифрован
  ChaCha20-Poly1305 и несёт свой 16-байтовый тег.

Почему не текстовый заголовок, как у age: так попросил владелец. Размеры и место данных должны быть
числами на известных местах, читаться до расшифровки и давать прямой доступ к любому куску.

## 1. Преамбула — 84 байта (D296)

| Смещение | Байт | Поле | В 1.0 | Что значит |
|---|---|---|---|---|
| `0x00` | 8 | `magic` | `89 55 43 52 0D 0A 1A 0A` | `\x89UCR\r\n\x1a\n`, по образцу PNG. Байт `0x89` ловит передачу в 7 бит, `\r\n` — перевод строк, `\x1a` останавливает `type` в DOS |
| `0x08` | 1 | `major` | `1` | мажорная версия формата (§5) |
| `0x09` | 1 | `minor` | `0` | минорная версия формата (§5) |
| `0x0A` | 2 | `flags` | `0` | биты, которые читатель обязан понимать (§5). В 1.0 не определён ни один |
| `0x0C` | 4 | `header_size` | 832 в примере §9 | размер заголовка от байта 0 до конца MAC включительно |
| `0x10` | 8 | `payload_offset` | `= header_size` | где начинается содержимое |
| `0x18` | 8 | `payload_size` | | сколько байт содержимого в файле, теги включены |
| `0x20` | 8 | `plaintext_size` | | сколько байт получится после расшифровки (**полезные данные**) |
| `0x28` | 4 | `chunk_size` | `65536` | байт открытого текста в каждом куске, кроме последнего |
| `0x2C` | 2 | `record_count` | | сколько записей идёт после преамбулы |
| `0x2E` | 2 | `kdf` | `0x0001` | HKDF-SHA-256. Номер — из реестра HPKE, RFC 9180 §7.2 |
| `0x30` | 2 | `aead` | `0x0003` | ChaCha20-Poly1305. Номер — из реестра HPKE, RFC 9180 §7.3 |
| `0x32` | 2 | `key_bits` | `256` | длина ключа файла в битах (вопрос 140) |
| `0x34` | 32 | `file_salt` | случайные | соль HKDF и заодно идентификатор файла. `inspect` показывает первые 8 байт |

Байты `0x00`–`0x0F` одинаковы во всех версиях навсегда (§5). Остальная часть преамбулы относится к
мажорной версии 1.

Связи, которые читатель проверяет (после MAC, §6):

```
n            = max(1, ceil(plaintext_size / chunk_size))           — number of chunks
payload_size = plaintext_size + 16 · n
file length  = payload_offset + payload_size                        — no bytes after the payload
payload_offset = header_size                                        — in every 1.x
```

`payload_size` и `payload_offset` выводятся из остальных полей, и всё равно лежат в файле. Так
просил владелец: чтобы по заголовку сразу было видно, где данные и сколько их, без вычислений. Если
поля расходятся с формулами, файл испорчен.

## 2. Записи

Каждая запись: `u16 type` · `u32 size` · `size` байт тела. Записи идут подряд от `0x54` и
кончаются ровно на `header_size − 32`. Порядок записей покрыт MAC.

Бит 15 `type` — **критично** (§5). Незнакомую критичную запись читатель не пропускает: он
отказывается от файла.

### 2.1. Типы 1.0

| `type` | Имя | Критично | Тело |
|---|---|---|---|
| `0x0001` | получатель `ssh-ed25519` | нет | 112 байт: `fingerprint` 32 · `enc` 32 · `sealed` 48 |
| `0x0002` | получатель `ssh-rsa` | нет | `fingerprint` 32 · `u16 k` · `k` байт шифротекста OAEP |
| `0x0003` | метаданные | нет | `sealed`: ChaCha20-Poly1305 под `meta_key`, nonce из нулей, внутри TLV §2.2 |
| `0x0008` | получатель «ключ разделён» (split/02 §4, D365, D372) | нет | 10 байт: `set_id` 8 · `k` 1 · `n` 1. Ключ файла собирается из `k` частей по Шамиру |

Поля получателей:
- `fingerprint` — SHA-256 от blob SSH-ключа. Это тот же отпечаток, что `ssh-keygen -l` показывает
  как `SHA256:…`, только без Base64. Читатель по нему находит свой ключ, ничего не расшифровывая.
- `enc` — эфемерный открытый ключ X25519, то есть `enc` из HPKE.
- `sealed` — ключ файла (32 байта) под AEAD HPKE, плюс тег 16 байт.
- `k` — длина модуля RSA в байтах (256 для 2048 бит, 512 для 4096). Шифротекст имеет ровно эту
  длину.

Получатели не критичны. Незнакомый тип получателя значит ключ, которого у этого читателя нет, а
не испорченный файл. Хотя бы один получатель обязан быть.

Метаданные не критичны: без них теряется только имя файла.

### 2.2. Внутри метаданных

Внутри метаданных — последовательность `u8 tag` · `u16 len` · `len` байт. Незнакомые теги
пропускаются.

| `tag` | Что | Правила |
|---|---|---|
| `0x01` | имя файла, UTF-8 | только последний компонент пути, до 255 байт. При расшифровке не принимаются `/`, `\0`, `.` и `..` |
| `0x02` | время изменения | `u64`, секунды Unix |
| `0x03` | права | `u16`, только биты `0777`. Расшифровка всё равно пишет 0600 (D302), а права ставит, если попросили `--keep-mode` |

Имя лежит в зашифрованной записи, а не в преамбуле: имя файла — тоже тайна.

### 2.3. Зарезервировано на будущее (не в 1.0, D301)

| `type` | Что | Будущая версия |
|---|---|---|
| `0x0004` | получатель `ecdsa-sha2-nistp256`: HPKE DHKEM(P-256). Его могли бы открывать ключи Secure Enclave на iPhone | 1.x |
| `0x0005` | получатель-пароль: Argon2id → обёртка ключа файла | 1.x |
| `0x0006` | постквантовый получатель X-Wing (ML-KEM-768 + X25519), для ключей Unitool, а не SSH | 1.x |
| `0x0007` | подпись отправителя SSHSIG от `kit.ssh` (02 §5) | 1.x |
| `0x0010` | подсказка: логин GitHub, открытым текстом (вопрос 142) | 1.x |
| `0x8001` | сжатие содержимого перед шифрованием. Критично: без него содержимое не прочесть | 1.x |

## 3. Содержимое — STREAM

Конструкция — STREAM (Hoang, Reyhanitabar, Rogaway, Vizár), как в age. Порядок кусков нельзя
переставить, кусок нельзя отрезать или добавить.

```
chunk i plaintext  = plaintext[i·chunk_size … min((i+1)·chunk_size, plaintext_size))
chunk i ciphertext = ChaCha20-Poly1305(payload_key, nonce_i, plaintext_i, aad = ∅)   — len + 16
nonce_i            = i as 11 bytes big-endian ‖ (0x01 if i = n−1 else 0x00)
```

- Пустой файл — один кусок из одного тега (16 байт).
- Последний кусок может быть полным. Пустым он бывает, только если пусто всё содержимое.

**Где лежит кусок `i`** — без чтения файла целиком:

```
offset_i = payload_offset + i · (chunk_size + 16)
size_i   = chunk_size + 16                                        for i < n−1
size_n−1 = plaintext_size − (n−1) · chunk_size + 16
```

Отсюда прямой доступ: можно расшифровать любой диапазон байтов, прочитав только его куски.

## 4. Армор — текстовая форма

Чтобы файл прошёл через мессенджер или почту, есть текстовая форма:

```
-----BEGIN UCRYPT FILE-----
<the binary file in standard Base64 with padding, 64 columns>
-----END UCRYPT FILE-----
```

Её пишет `encrypt -a`. Читатель сам узнаёт армор по первым непробельным байтам. Все смещения
формата относятся к двоичной форме после снятия армора.

## 5. Версии (D297)

### 5.1. Что не меняется никогда

Байты `0x00`–`0x0F`: магия, `major`, `minor`, `flags`, `header_size`. Любой читатель любой версии
прочтёт их у файла из будущего и сможет сказать:

> `report.ucrypt: ucrypt 2.0, this unitool reads 1.0–1.3; update unitool`

### 5.2. Правила

| Поле | Когда меняется | Что делает читатель версии `R.r` с файлом `F.f` |
|---|---|---|
| `major` | меняется то, что старый читатель не может даже пропустить: раскладка преамбулы, STREAM, метки HKDF, порядок MAC | `F ≠ R` → отказ с номером версии, как в §5.1 |
| `minor` | добавляется то, что старый читатель может пропустить или опознать как незнакомое: тип записи, номер `kdf`/`aead`, бит `flags`, тег метаданных | `f ≤ r`: знает всё. Незнакомый тип записи значит испорченный файл, ведь писатель `f` не мог его использовать. `f > r`: незнакомые некритичные записи пропускаются; незнакомая критичная запись, бит `flags` или номер алгоритма → отказ с названием, чего не хватает |
| `flags` | новый режим, который меняет смысл всего файла | незнакомый поднятый бит → отказ |
| бит 15 `type` | ставится, если без записи файл нельзя правильно прочесть (сжатие) | незнакомый критичный тип → отказ |

- Метки HKDF и HPKE начинаются с `ucrypt/<major>`. Ключи разных мажорных версий никогда не
  совпадут, даже из одного ключа файла.
- **Писатель ставит минимальную достаточную версию.** Это наибольшая из версий, в которых
  появилась каждая возможность, использованная в файле. Файл только с Ed25519-получателями от
  unitool 1.3 будет помечен 1.0, и его откроет любой читатель 1.x.
- **Реестр номеров** — таблицы §2.1 и §2.3 и номера `kdf`/`aead`. Он живёт здесь и в коде одним
  `enum` на поле. Номер, однажды выданный, не переиспользуется.
- **Эталонные файлы навсегда.** Они лежат в `unitool-kit/src/commonTest/resources/ucrypt/<version>/`
  вместе с тестовыми ключами. Каждая версия добавляет свою папку, и тесты открывают все папки.
  Старые файлы читаются всегда.

### 5.3. Что какой версии потребует

| Изменение | Версия |
|---|---|
| новый тип получателя (P-256, пароль, X-Wing) | минорная, некритичная запись |
| новый тег метаданных | никакая: теги и так пропускаются |
| сжатие | минорная, критичная запись `0x8001` |
| новый AEAD, KDF или длина ключа | минорная, новый номер в преамбуле. Старые читатели отказываются с названием алгоритма |
| другая раскладка, другие метки, другая конструкция кусков | мажорная |

### 5.4. Журнал версий формата

| Версия | Что |
|---|---|
| 1.0 | эта заметка: HKDF-SHA-256, ChaCha20-Poly1305, ключ 256 бит, куски 64 КиБ, получатели `ssh-ed25519` и `ssh-rsa`, метаданные; получатель «ключ разделён» `0x0008` (split). Ядро и `0x0008` делаются первыми (split D372); если ядро выйдет раньше SSH-получателей, те войдут в 1.1 с теми же номерами |

## 6. Чтение (D302)

1. Прочесть 16 байт. Проверить магию и мажорную версию, `header_size` должен лежать в пределах
   §8.
2. Прочесть заголовок целиком и разобрать его строго:
   - `kdf`, `aead` и `key_bits` — известная комбинация (в 1.0 одна: 1, 3, 256);
   - `chunk_size` — степень двойки от 4 КиБ до 16 МиБ;
   - флаги, записи и типы — по §5.2;
   - записи кончаются ровно на `header_size − 32`;
   - есть хотя бы один получатель.
3. Найти записи получателей, чей `fingerprint` совпадает с одним из своих ключей. Открыть
   первую: закрытая операция, затем HPKE Open или OAEP. Если не открылась, перейти к следующей.
   Если подходящих нет — «ни один ваш ключ не подходит; файл для: SHA256:…, SHA256:…».
4. Вывести `mac_key` и сравнить HMAC заголовка за постоянное время. Если не совпал — «заголовок
   испорчен или подменён». **До этого шага размерам и метаданным никто не верит:** `inspect` без
   ключа показывает их с пометкой «не проверено».
5. Проверить связи §1, в том числе длину файла.
6. Расшифровывать куски по порядку и писать в `ИМЯ.part` (создаётся `O_EXCL`, права 0600). Ошибка
   тега на любом куске → удалить `.part`, код 1.
7. После последнего куска переименовать `.part` в итоговое имя и обнулить ключи.

## 7. Запись

1. Получатели: ключи с GitHub или из файла, только поддерживаемые; хотя бы один.
2. `plaintext_size` известен заранее: размер файла, или stdin, прочитанный целиком.
3. `file_key` и `file_salt` берутся из CSPRNG, из них выводятся ключи (02 §1).
4. Для каждого получателя — запись: свой эфемерный ключ или свой seed OAEP. Затем метаданные,
   преамбула и MAC.
5. Пишется заголовок, затем куски по одному: память не больше одного куска.
6. **Проверка записанного.** Если вывод — файл, он перечитывается с `file_key`, который ещё в
   памяти: MAC и каждый тег. Если вывод — pipe, проверки нет, и это сказано в `--help`.
7. Ключи обнуляются, `.part` переименовывается.

## 8. Пределы

| Что | Предел | Почему |
|---|---|---|
| `header_size` | от 116 (84 + 32) до 1 МиБ | Злой заголовок не заставит выделить гигабайты. Обязательная запись получателя проверяется отдельно, в §6 |
| `record_count` | до 1024 | |
| размер одной записи | до 64 КиБ | RSA-16384 — 2 КиБ |
| `chunk_size` | 4 КиБ…16 МиБ, степень двойки | память чтения — один кусок |
| `plaintext_size` | до 2⁶² | `Long` и nonce хватает с запасом: 2⁸⁸ кусков |

## 9. Пример

Файл `report.pdf`, 100 000 байт, для двух ключей: Ed25519 и RSA-4096.

| Часть | Смещение | Байт |
|---|---|---|
| преамбула | 0 | 84 |
| запись 1, `ssh-ed25519` | 84 (`0x54`) | 6 + 112 = 118 |
| запись 2, `ssh-rsa` 4096 | 202 (`0xCA`) | 6 + 32 + 2 + 512 = 552 |
| запись 3, метаданные: имя (3 + 10) и время (3 + 8) = 24, плюс тег 16 | 754 (`0x2F2`) | 6 + 40 = 46 |
| MAC | 800 (`0x320`) | 32 |
| кусок 0 | 832 (`0x340`) | 65 536 + 16 |
| кусок 1 | 66 384 | 34 464 + 16 |
| конец файла | 100 864 | = 832 + 100 032 |

```
00000000  89 55 43 52 0d 0a 1a 0a  01 00 00 00 00 00 03 40   magic · 1.0 · flags · header_size 832
00000010  00 00 00 00 00 00 03 40  00 00 00 00 00 01 86 c0   payload_offset 832 · payload_size 100032
00000020  00 00 00 00 00 01 86 a0  00 01 00 00 00 03 00 01   plaintext_size 100000 · chunk 65536 · 3 records · kdf 1
00000030  00 03 01 00 .. .. .. ..  .. .. .. .. .. .. .. ..   aead 3 · key_bits 256 · file_salt…
00000054  00 01 00 00 00 70 …                                record type 1, 112 bytes
000000ca  00 02 00 00 02 22 …  02 00 …                       record type 2, 546 bytes, k = 512
000002f2  00 03 00 00 00 28 …                                record type 3, 40 bytes
00000320  <HMAC-SHA-256, 32 bytes>
00000340  <chunk 0> <chunk 1>
```

`unitool crypt inspect report.pdf.ucrypt` показывает то же человеческими словами (03 §2.4).
