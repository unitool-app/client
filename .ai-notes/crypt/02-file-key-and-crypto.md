# 02 — ключ файла, обёртки, стойкость

> **Версия:** 1.0 · **Дата:** 2026-10-06 · Решения D298–D301

Владелец просил «методику очень стойкого общего ключа шифрования». Общий ключ здесь — **ключ
файла**: один на файл, одинаковый для всех получателей. Ниже — откуда он берётся, как живёт и что
защищает его в файле.

Конструкции только стандартные: HKDF, HPKE, RSA-OAEP, STREAM, HMAC. Своих нет. Реализации — свои,
из `services/ssh` (они переезжают в kit по cli/02 §3.1). Они уже сверены с JDK, `age` и
`ssh-keygen`, а новое (HPKE) сверяется с векторами RFC (03 §3).

## 1. Ключ файла (D298)

### 1.1. Источник

32 байта из CSPRNG операционной системы и ниоткуда больше:

| Платформа | Источник |
|---|---|
| linuxX64 (бинарь CLI) | `syscall(SYS_getrandom, buf, n, 0)` в цикле: короткое чтение и `EINTR` повторяются. Обёртка `getrandom()` появилась только в glibc 2.25, а sysroot Kotlin/Native — 2.19. Константа `SYS_getrandom` в `platform.linux` есть, это проверено. С флагом 0 вызов ждёт, пока пул ядра проинициализирован. Отступления на `/dev/urandom` нет: без `getrandom` (ядро старше 3.17) шифрование отказывается |
| JVM, Android | `SecureRandom()` |
| iOS | `SecRandomCopyBytes` |
| браузер | `crypto.getRandomValues` |

- `kotlin.random.Random` не годится: он для идентификаторов, а не для ключей. Platform.kt уже
  говорит это.
- **Проверка на поломку, а не на случайность:** 32 байта не все нули, и два подряд взятых ключа
  различаются. Это ловит заглушку или сломанный `actual`, а не слабый генератор. От слабого
  генератора защищает только выбор источника выше.

### 1.2. Правила

- **256 бит.** У age 128, и этого хватает против классического противника. 256 дают запас:
  - против атак сразу на много целей (multi-target);
  - против алгоритма Гровера: после него остаётся 128 бит.
- **Новый на каждый файл.** Повторное шифрование того же содержимого берёт новый ключ и новую
  соль.
- **Не выводится ни из пароля, ни из содержимого.** Ключ из содержимого (convergent encryption)
  выдал бы, что два файла одинаковы. Ключ из пароля был бы слабее 256 бит.
- **Нигде не лежит открытым.** Ни в файле, ни на диске, ни в логах, ни в argv. В файле есть
  только его обёртки для получателей (§2).

### 1.3. Вывод рабочих ключей

Ключ файла напрямую ничего не шифрует. Из него выводятся отдельные ключи на каждое дело:

```
prk         = HKDF-Extract(salt = file_salt, ikm = file_key)          — SHA-256, RFC 5869
payload_key = HKDF-Expand(prk, "ucrypt/1 payload", 32)
mac_key     = HKDF-Expand(prk, "ucrypt/1 header",  32)
meta_key    = HKDF-Expand(prk, "ucrypt/1 meta",    32)
```

- Один ключ — одно дело. Утечка одного выведенного ключа не даёт ни других, ни ключа файла.
- Соль файла (32 случайных байта в преамбуле) разводит выводы двух файлов, даже если ключи файлов
  совпали бы.
- `ucrypt/1` в метках — мажорная версия формата (01 §5.2).
- Сегодняшний `hkdfSha256` в `services/ssh` делает Extract и Expand одним вызовом. В kit он
  делится на `hkdfExtract` и `hkdfExpand`, которые нужны и HPKE. Старая функция остаётся
  обёрткой над ними.

### 1.4. Жизнь в памяти

- Ключ файла, выведенные ключи, эфемерные скаляры, seed OAEP и закрытые ключи лежат в
  `SecretBytes`. Их обнуляют в `finally` сразу после работы — то же правило, что D155.
- Честно о пределах: JVM и Kotlin/Native не дают `mlock`. GC может оставить копию, а память может
  уйти в swap. Защиты от противника на той же машине здесь нет и не обещается.

### 1.5. Проверка после записи

Пока ключ файла ещё в памяти, `encrypt` перечитывает записанный файл: MAC и каждый тег (01 §7).
Ошибку диска или файловой системы человек узнаёт сразу, а не через год, когда файл понадобится.

## 2. Обёртки для получателей

### 2.1. `ssh-ed25519` → HPKE (D299)

HPKE base mode, RFC 9180. Набор: DHKEM(X25519, HKDF-SHA256) `0x0020`, HKDF-SHA256 `0x0001`,
ChaCha20Poly1305 `0x0003`. Векторы — RFC 9180, приложение A.2.

```
pkR       = edwardsToMontgomery(ed25519 point)          — the same map as age: Curve25519.edwardsToMontgomery
info      = "ucrypt/1 ssh-ed25519" ‖ file_salt ‖ fingerprint
enc, ctx  = SetupBaseS(pkR, info)                       — fresh ephemeral X25519 key per recipient
sealed    = ctx.Seal(aad = ∅, file_key)                 — 32 + 16 bytes
```

Получатель:

```
dh        = X25519(skR, enc)                            — the only private operation
            reject if dh is all zero                    — low-order point, RFC 9180 §7.1.4
ctx       = SetupBaseR(enc, skR→dh, pkR, info)          — DHKEM Decap: ExtractAndExpand(dh, enc ‖ pkR)
file_key  = ctx.Open(aad = ∅, sealed)
```

- **Почему HPKE, а не рецепт age.** Рецепт age (`agessh`) делает то же самое, но это
  конструкция одного проекта. HPKE — стандарт IETF, у него есть доказательства стойкости и
  официальные векторы. Его закрытая операция та же — одна X25519. Поэтому всё, что сегодня
  открывает age, откроет и `ucrypt`:
  - `SoftwareOps` получает скаляр из seed;
  - на Android 13+ X25519-близнец ключа лежит в Keystore с `PURPOSE_AGREE_KEY` (ssh-new 01, P2).
- **Один ключ и для подписи, и для шифрования.** Ed25519 подписывает, а его X25519-образ
  принимает ключи. Так делает age для каждого SSH-ключа. У этой связки есть отдельный разбор
  стойкости (E. Thormarker, 2021). Отдельного ключа шифрования у пользователя GitHub нет, а
  задача — шифровать именно его ключами.
- Своего у нас здесь около сотни строк: `LabeledExtract`, `LabeledExpand`, DHKEM, ключевое
  расписание base mode и один `Seal`/`Open`. Всё это поверх уже проверенных X25519, HKDF и
  ChaCha20-Poly1305.

### 2.2. `ssh-rsa` → RSA-OAEP (D300)

```
label  = "ucrypt/1 ssh-rsa" ‖ file_salt ‖ fingerprint
c      = RSAES-OAEP-ENCRYPT((n, e), file_key, label)    — SHA-256, MGF1-SHA-256, RFC 8017 §7.1; c is k bytes
```

- Закрытая операция — «сырая» RSA, `m = c^d mod n`. OAEP снимает общий код
  (`Rsa.oaepDecode(em, label)`, он уже есть). Так устроено и у age: Keystore даёт RSA без
  дополнения, а метки OAEP он не умеет.
- Модуль — от 2048 до 16384 бит, `e` нечётная и не меньше 3. Короче 2048 — никогда.
- Любая ошибка OAEP даёт одно и то же «не открылась», без подробностей.

### 2.3. Зачем привязка к соли и отпечатку

`info` у HPKE и метка у OAEP содержат `file_salt` и `fingerprint`. Обёртку нельзя перенести в
другой файл или выдать за обёртку другого ключа: она просто не откроется. MAC заголовка поймал бы
это и так. Привязка — второй забор, и он бесплатный.

### 2.4. Что не поддерживается в 1.0 (D301)

| Тип | Почему | Что потом |
|---|---|---|
| `ecdsa-sha2-nistp256/384/521` | в kit нет своей арифметики P-256. В бинаре CLI нет и платформенной: JCA и Security.framework там недоступны | запись `0x0004`, HPKE DHKEM(P-256). Её откроет Secure Enclave iPhone, где все ключи P-256 |
| `sk-ssh-ed25519@openssh.com`, `sk-ecdsa-…` | ключ FIDO умеет только подписывать, согласования ключей у него нет | не будет |
| `ssh-dss` | устарел и отключён в OpenSSH | не будет |

## 3. Содержимое и заголовок

- **ChaCha20-Poly1305, а не AES-GCM.** AES в Kotlin своими руками — это таблицы, а таблицы
  подвержены атакам по времени кэша. ChaCha20 устроен на сложениях, сдвигах и XOR и выполняется
  за постоянное время без аппаратной поддержки. Ключ — 256 бит.
- **STREAM** (01 §3): номер куска и признак последнего входят в nonce. Переставить, отрезать или
  добавить кусок нельзя. Nonce не повторяется, потому что `payload_key` свой у каждого файла.
- **HMAC-SHA-256 заголовка.** Заголовок открыт, но покрыт MAC: размеры, соль, получатели, порядок
  записей. MAC сравнивается за постоянное время.
  - Зачем и MAC, и AEAD: AEAD защищает каждый кусок, а MAC — то, что не зашифровано.
  - Размерам верят только после MAC (01 §6, шаг 4).

## 4. Стойкость

| Слой | Чем | Бит против классического противника | Против квантового |
|---|---|---|---|
| ключ файла | 256 случайных бит | 256 | 128 (Гровер) |
| содержимое | ChaCha20-Poly1305, ключ 256 | 256 | 128 |
| заголовок | HMAC-SHA-256 | 256 | 128 |
| получатель Ed25519 | X25519 | ≈128 | ломается (Шор) |
| получатель RSA-2048 | OAEP | ≈112 (NIST SP 800-57) | ломается |
| получатель RSA-3072 | OAEP | ≈128 | ломается |
| получатель RSA-4096 | OAEP | ≈140 | ломается |

**Файл стоек ровно настолько, насколько стоек самый слабый выбранный получатель.** Ключ файла в
256 бит — самое прочное место файла, но не определяющее. Поэтому:
- список ключей в CLI показывает стойкость каждого в битах;
- при шифровании stderr называет самое слабое звено (вопрос 145);
- в 1.0 ни один путь не даёт меньше 112 бит.

## 5. Угрозы

**Защищено:**
- содержимое и имя файла от всех, у кого нет ни одного из выбранных закрытых ключей;
- любой изменённый байт заголовка или содержимого;
- обрезка, перестановка, вставка кусков;
- подмена или перестановка получателей;
- кусок или обёртка, перенесённые из другого файла.

**Видно без ключа:**
- что это `ucrypt` и какой версии;
- размер открытого текста (он есть в преамбуле, а по длине файла угадывался бы с точностью до 16
  байт на кусок);
- сколько получателей и их отпечатки (вопрос 142).

**Не защищено — и что с этим делать:**

| Угроза | Что делаем |
|---|---|
| ключи на GitHub подменены: захват аккаунта или перехват TLS | отпечатки показываются до шифрования, а в меню их подтверждают. Позже — память получателей `~/.config/unitool/recipients`: предупреждение, если набор ключей логина изменился с прошлого раза |
| отправитель не подтверждён: зашифровать для ключей с GitHub может кто угодно | так же и у age. Позже — подпись SSHSIG, запись `0x0007`; `kit.ssh` уже умеет SSHSIG |
| «собрать сейчас — расшифровать потом» квантовым компьютером | X25519 и RSA это не переживут, симметричная часть — переживёт. Решение — только постквантовый получатель (запись `0x0006`), но SSH-ключи GitHub его не дают |
| заражённая машина отправителя или получателя | вне модели |
| память и swap (§1.4) | вне модели |
