## Что сказал владелец (близко к тексту)

> «Добавь новую функцию: зашифровать файл публичным ключом GitHub-юзера.
>
> То есть создаём контейнер и кладём в него случайный ключ шифрования. Выбираем пользователя на
> GitHub и из списка его ключей те, которыми хотим зашифровать общий для всех ключ. При обратном
> процессе можно расшифровать любым из этих ключей, а потом общим ключом расшифровать файл.
>
> Надо вынести это в kit и сделать в приложении утилиту для шифрования и расшифровки.
>
> Опиши структуру такого файла. Надо, чтобы по хедеру файла сразу было понятно, сколько байт
> занимает полезная дата, сколько будет бит и где она находится в файле, чтобы расшифровка была
> наша.
>
> И опиши методику очень стойкого общего ключа шифрования.
>
> Придумай концепт и положи в `.ai-notes/`. Сделай версионирование файлов в протоколе формата
> файла».

## Короткий ответ

1. **Схема — конверт.**
   - На каждый файл берётся новый случайный **ключ файла**: 256 бит из CSPRNG системы.
   - Им шифруется содержимое.
   - Сам ключ файла шифруется отдельно для каждого выбранного SSH-ключа пользователя. Каждая
     такая копия — запись получателя в заголовке.
   - Любой один закрытый ключ открывает свою запись и достаёт ключ файла. Дальше ключ файла
     открывает содержимое.
2. **Формат свой: `ucrypt`, файлы `*.ucrypt`, версия 1.0** (01).
   - Первые 84 байта — преамбула фиксированной формы. По ней сразу видно:
     - размер заголовка;
     - где начинается шифротекст и сколько в нём байт;
     - сколько байт будет после расшифровки;
     - размер куска;
     - алгоритмы;
     - длину ключа файла в битах.
   - Где лежит любой кусок, считается по формуле, без чтения файла целиком.
   - Весь заголовок, вместе с размерами, закрыт HMAC. Подмену любого байта видно до того, как
     размерам начнут верить.
3. **Версии в самом формате** (01 §5).
   - Мажорная версия меняется при несовместимых изменениях. Минорная — при добавлениях, которые
     старый читатель может пропустить.
   - В записях есть бит «критично»: незнакомую критичную запись читатель не пропускает, а
     отказывается от файла.
   - Писатель ставит минимальную версию, которой хватает содержимому файла.
   - Файлы каждой версии лежат в тестах навсегда.
4. **Стойкость ключа файла** (02).
   - Это 256 случайных бит из CSPRNG ОС, свежие для каждого файла. Ключ не выводится из пароля
     или содержимого и не хранится.
   - Напрямую он не используется: ключи содержимого, заголовка и метаданных выводятся из него
     через HKDF-SHA-256 с солью файла.
   - Обёртки для получателей — стандартные конструкции:
     - Ed25519 — HPKE (RFC 9180);
     - RSA — RSA-OAEP-SHA-256.
   - Своих конструкций нет.
   - Честное ограничение: файл не стойче самого слабого выбранного получателя. Поэтому список
     ключей показывает стойкость каждого в битах.
5. **Где код.**
   - Формат и криптография — в `unitool-kit` (`kit.crypt`), поверх примитивов, которые и так
     переезжают туда из `services/ssh` (cli/02 §3.1).
   - В CLI — приложение `crypt` с командами `keys`, `encrypt`, `decrypt`, `inspect` и меню (03).
   - Закрытая операция вынесена наружу. Поэтому тот же формат сможет открыть и связка ключей
     телефона, в том числе ключом из чипа.

## Решения

| № | Решение |
|---|---|
| D295 | Свой формат `ucrypt`, а не age. Файл `*.ucrypt` не открывается `age -d`. Экспорт 2FA и бэкап телефона остаются age. Формат age и его рецепты — образец, но разбор, версии и размеры свои (01) |
| D296 | Раскладка: преамбула в 84 байта → записи TLV (`u16 type`, `u32 size`) → HMAC-SHA-256 заголовка (32 байта) → содержимое кусками STREAM. Все числа big-endian. В преамбуле есть `header_size`, `payload_offset`, `payload_size`, `plaintext_size`, `chunk_size`, `kdf`, `aead` и `key_bits` (01 §1–§2) |
| D297 | Версии (01 §5):<br>• магия и байты 8–15 (`major`, `minor`, `flags`, `header_size`) не меняются никогда;<br>• `major` — несовместимое изменение, `minor` — совместимое добавление;<br>• бит 15 типа записи означает «критично»;<br>• писатель ставит минимальную достаточную версию;<br>• эталонные файлы каждой версии остаются в тестах навсегда;<br>• метки HKDF содержат мажорную версию |
| D298 | Ключ файла (02 §1):<br>• 32 байта из CSPRNG ОС (`getrandom` на Linux, `SecureRandom`, `SecRandomCopyBytes`, `crypto.getRandomValues`), новый на каждый файл;<br>• не выводится из пароля или содержимого и не записывается открытым;<br>• используется только как IKM для HKDF-SHA-256 с солью файла (32 байта), из которого выводятся `payload_key`, `mac_key` и `meta_key`;<br>• обнуляется сразу после работы |
| D299 | Получатель `ssh-ed25519`: HPKE base mode (RFC 9180) с DHKEM(X25519, HKDF-SHA256), HKDF-SHA256 и ChaCha20-Poly1305. Ключ Ed25519 переводится в X25519 так же, как в age. `info` привязывает обёртку к версии, соли файла и отпечатку ключа. Закрытая операция — одна X25519, как у age. Значит, её умеют и `SoftwareOps`, и X25519-близнец в Keystore (02 §2.1) |
| D300 | Получатель `ssh-rsa`: RSA-OAEP с SHA-256 и MGF1-SHA-256, а метка привязывает обёртку к версии, соли и отпечатку. RSA короче 2048 бит не берётся никогда. Закрытая операция — «сырая» RSA, OAEP снимается в общем коде, как у age (02 §2.2) |
| D301 | В 1.0 не поддерживаются: `ecdsa-*` (в kit нет ECDH P-256 своими руками), `sk-*` (ключи FIDO не умеют согласование ключей), DSA. В списке ключей они видны с причиной. Типы записей для P-256, пароля и постквантового гибрида зарезервированы на будущие минорные версии (01 §3) |
| D302 | Чтение (01 §6):<br>• размерам и метаданным верят только после проверки HMAC заголовка;<br>• лишние байты после содержимого — ошибка;<br>• расшифровка пишет в `ИМЯ.part` с правами 0600 и переименовывает только после последнего куска;<br>• при любой ошибке `.part` удаляется |
| D303 | Код в `unitool-kit`:<br>• `kit.crypt` — формат, HPKE и разбор;<br>• `kit.github` — правила логина и разбор ответа GitHub, без сети.<br>Kit опирается на перенос cli/02 §3.1, а копии `GitHubKeys` в twofa и backup переходят на kit. Закрытый шаг — интерфейс `SshDecryptionKey`, общий с age (03 §1) |
| D304 | Приложение CLI `crypt`: `keys LOGIN`, `encrypt`, `decrypt`, `inspect`. В меню — пользователь GitHub, затем нумерованный список его ключей со стойкостью, затем выбор. Без терминала и без `-k` шифрование идёт всем подходящим ключам, и они перечисляются в stderr (03 §2) |
| D305 | Каркасу CLI добавляются:<br>• `io.secret()` без эха, через `/dev/tty` (уже обещано в D272);<br>• потоковые файлы (`openRead`, `openWrite` с 0600, `rename`, `size`);<br>• повторяемые параметры;<br>• интерфейс `Http`. Как он устроен в бинаре — вопрос 143 |
| D306 | Тесты (03 §3):<br>• векторы RFC 9180 A.2, RFC 7748, RFC 8439 и RFC 5869;<br>• эталонные файлы 1.0;<br>• перебор подмены каждого байта заголовка;<br>• обрезка и перестановка кусков;<br>• независимый читатель на JCA;<br>• нативный бинарь против JVM;<br>• команды на `FakeIo` |
