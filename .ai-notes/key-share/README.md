# Ключ на другое устройство и проверка ключа

> Версия 0.1, 2026-10-29. Решения D624–D628, вопросы 265–268. Следующие номера — D629 / Q269.
> Всё в этом репозитории: Superizer 0.7.1 не меняется. Что вышло — §«Сделано».

## Что просили

Две кнопки на карточке SSH-ключа:
- **«Отправить на другое устройство»** — ключ, зашифрованный на открытый ключ другого устройства;
- **«Проверить ключ»** — устройство спрашивает пароль или Face ID / отпечаток, шифрует проверочное
  значение на этот же ключ и открывает его им же: ключ и его замок действительно работают.

## Решения

- **D624. Пересматривает вопрос 73 и D140 для одного случая — ждёт подтверждения владельца.**
  В 73 записано «экспорта закрытого ключа нет, никогда», в D140 — «закрытая не покидает модуль».
  Теперь хост (только он) отдаёт файл ключа **уровня 2 или 3**, зашифрованный age на открытый ключ
  из книги других устройств (.ai-notes/public-keys). Остаётся в силе:
  - у дверей контракта (`SshKeyring`, `SshKeyAdmin`, `SshAgent`) экспорта нет: приложение его не
    получит никогда (тест I4 `theApiHasNoMethodThatReturnsPrivateMaterial`);
  - ни один публичный тип не содержит закрытого ключа: наружу уходит только шифртекст age;
  - уровень 1 не уходит никогда: ключ в чипе (`NotAllowed("in-chip")`, кнопки нет);
  - бэкап по-прежнему без ключей (D170).
- **D625. Что уходит.** Уровень 3 — файл как он хранится, байт в байт, под паролем ключа: ничего не
  расшифровывается, пароль не спрашивается. Уровень 2 — то, что распечатал чип: под паролем ключа,
  если он сохранён вторым замком (D244), иначе без пароля — тогда age единственный замок, экран
  предупреждает, а на другой стороне импорт сам потребует новый пароль (D167). Файл — armored age,
  как бэкап, через «Поделиться» (`application/octet-stream`), имя `<comment>.age`. Открывается
  `age -d -i ~/.ssh/id_ed25519` или cr-restore, потом «Добавить ключ → Из файла».
- **D626. Кто подтверждает и кому.** Уровень 2 — системный диалог распечатывания (на Android он
  показывается всегда, `CryptoObject`), отдельного листа нет. Уровень 3 — лист подтверждения, как
  удаление (D148), со словами «Отправить ключ «…» на «…»». Получатель — только из книги: строку,
  вставленную прямо здесь, мог подложить кто угодно; в книгу ключ попадает со сверкой отпечатка
  (D511). С пустой книгой экран ведёт в «Добавить открытый ключ».
- **D627. «Проверить ключ».** Для любого рабочего ключа любого уровня. 32 случайных байта → age на
  этот ключ → открыть им же; ключ, который только подписывает (ECDSA), подписывает их в namespace
  `verify@m42.cx`, и подпись проверяется. Открытый сеанс не отвечает за замок: спрашивается пароль
  или устройство, как при первом использовании, и после ничего не остаётся, какой бы ни была
  политика; чужой открытый сеанс не трогается. В браузере ECDSA не проверяется — ответ там то, что
  ключ подписал.
- **D628. Слова и журнал.** `KeyOperation` в Superizer 0.7.1 — закрытый enum, нового значения без
  релиза нет. Действие едет на ближайшей операции (`Decrypt` у отправки, `Decrypt`/`Sign` у
  проверки), а свои слова дают `UseReason.action` (`HostAction.Export(to)`, `HostAction.Verify`) —
  лист и системный диалог читают его первым — и в журнале namespace `export@m42.cx` /
  `verify@m42.cx`. Суффикс `@m42.cx` приложениям запрещён (I9), так что строку приложения за эти не
  примешь. Строки журнала: «отправлен на другое устройство», «проверка».

## Вопросы

- **265.** Подтверждает ли владелец D624 — экспорт с хоста вопреки 73? Если нет: убрать
  `export` из `Keyring`/`SshKeyringHost`/`KeysUi`, кнопку и `SendKeyScreen`; проверка (D627) от этого
  не зависит.
- **266.** Уровень 2 без сохранённого пароля: спрашивать пароль для копии (≥ 12, `NewPassphraseForm`)
  и отправлять файл под ним? Сейчас — без пароля внутри age и с предупреждением.
- **267.** На принимающем телефоне путь через cr-restore → «Сохранить как» → «Добавить ключ» оставляет
  открытый файл на диске. Принимать age прямо в «Добавить ключ» (открыть своим ключом, импортировать,
  не сохраняя)?
- **268.** Получатель QR-кодом или вставкой прямо на экране отправки — потом, если книга окажется
  лишним шагом.

## Сделано

- `services/ssh`: `Keyring.export`, `Keyring.verify`; `use(…, session = false)` — мимо открытого
  сеанса; `HostAction` в `Prompter.kt`; проброс в `SshKeyringHost`. Тесты `KeyShareTest`: уровень 3
  уходит как хранится и только после подтверждения, уровень 2 — по диалогу устройства, с паролем и
  без, уровень 1 — никогда и без вопросов; проверка мимо сеанса, через чип, для ключа только для
  подписи; журнал, канарейки.
- `composeApp`: `KeysUi.export`/`verify`, кнопки `key:verify` и `key:send` на карточке
  (`key:send` — уровень 2–3 и есть «Поделиться» или «Сохранить как»), `SendKeyScreen`, строки
  ru/en. Тесты: `KeysScreensTest.checkingAKeyAsksItsPassphraseAndSaysWhetherItOpens`,
  `PublicKeysScreensTest.aKeySentToTheOtherPhoneOpensThereAndIsAddedUnderItsPassphrase` — A
  отправляет, B открывает своим ключом и добавляет ключ A с его паролем.
