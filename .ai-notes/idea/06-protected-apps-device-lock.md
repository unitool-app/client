## 1. Что спросил владелец

«Что насчёт открытия приложения: надо, чтобы оно требовало FaceID, TouchID и все возможные
проверки, так же как в банковских приложениях. Это надо сделать на уровне Superizer, наверное, то
есть мы делаем защищённое приложение. Логично это вынести в общий механизм? Или не надо?»

## 2. Короткий ответ

**Да, в Superizer. Но в библиотеку уходит механизм, а не всё подряд.** Приложение только
*объявляет*, что оно защищённое, и само решает, какие действия внутри себя переспрашивать.
Запирает и отпирает хост.

Почему не внутри 2FA:

1. **Окно принадлежит хосту.** Запрет скриншотов, записи экрана и миниатюры в «Недавних» — это
   `FLAG_SECURE` на окне Activity. У приложения по правилу App Boundary есть только `AppRuntime`,
   до окна оно не дотянется. Так и задумано.
2. **Секрет уже утекает мимо любого замка, и течёт он через хост** (§6). Конфиг из deep link
   `2fa/add?uri=otpauth://…secret=…` хост пишет открытым текстом в снапшот сессии и в журнал
   событий Service Menu. Service Menu в релизе открывается промокодом `SERVICE`. Приложение это не
   исправит: оно этого кода даже не видит.
3. **Человек один, а защищённых приложений будет несколько.** Следующими будут серверные
   инструменты из 01–04 с учётными данными. Если каждое приложение запирается само, у каждого
   свой таймаут, и две защищённые плитки подряд спросят отпечаток дважды.
4. **Ловушки платформы лучше пройти один раз.** Например, на API 24–29 ввод PIN уходит в чужую
   Activity, и получается петля «ушли в фон → заперли → промпт → ушли в фон» (§5.3). Если замок
   пишет каждое приложение, каждое наступит на это заново.

Честный довод против: библиотеке нужен релиз, а контракту — поднять версию (§9). Пока
защищённое приложение одно, дешевле было бы поступить как со сканером QR: сервис в
`unitool/services` и занавес внутри 2FA. Но пункты 1 и 2 всё равно требуют правки библиотеки, а
сам занавес поверх них — меньшая часть работы.

## 5. Форма

### 5.1. Объявление

Политику выбирает **приложение** (ответ на 62). У одних приложений замок включается и
выключается в Settings, у других он зашит и не выключается. Для переключаемого замка приложение
задаёт и начальное положение переключателя. Поэтому значений четыре, а не «переключатель плюс
флаг по умолчанию»: так бессмысленное сочетание вроде «зашито, но по умолчанию выключено» нельзя
даже записать.

```kotlin
@Serializable
public data class AppProtection(
    val lock: LockPolicy = LockPolicy.Off,
    /** Keep the app's screen out of screenshots, recordings, casting and the recents thumbnail. */
    val secureWindow: Boolean = false,
)

@Serializable
public enum class LockPolicy {
    /** No lock, and no switch for one in Settings. */
    Off,
    /** A switch in Settings, off until the person turns it on. */
    OptionalOff,
    /** A switch in Settings, on until the person turns it off. */
    OptionalOn,
    /** Always on; Settings lists the app as locked and offers no switch. */
    Required,
}

// AppManifest gains: val protection: AppProtection = AppProtection()
```

Поле манифеста, а не вызов в `setup()`: защиту должно быть видно до запуска, в Service Menu и в
каталоге (замочек на плитке), и её должно быть можно проверить при регистрации (§9).

2FA объявляет `Required` и `secureWindow = true`. Будущий, скажем, конвертер с сохранёнными
суммами мог бы объявить `OptionalOff`.

### 5.2. Аутентификатор и порт

```kotlin
/** The platform's "is this the device's owner?". Implemented by the host; an app never sees it. */
public interface DeviceAuthenticator {
    public fun availability(strength: AuthStrength = AuthStrength.Any): AuthAvailability
    public suspend fun authenticate(
        title: String,
        subtitle: String?,
        strength: AuthStrength = AuthStrength.Any,
    ): AuthOutcome
}

/**
 * [Any]: whatever the device can do — Class 2 face included. [Strong]: only what the Keystore
 * accepts for a key bound to authentication (Class 3 biometric or the screen-lock credential).
 * Stage 1 uses [Any]; the parameter is here so stage 2 needs no new contract (D142).
 */
public enum class AuthStrength { Any, Strong }

public enum class AuthAvailability { Available, NoScreenLock, Unsupported }

public sealed interface AuthOutcome {
    public data object Success : AuthOutcome
    public data object Cancelled : AuthOutcome
    /** Too many tries; the system's own message, already localized. */
    public data class LockedOut(val message: String) : AuthOutcome
    public data class Error(val message: String) : AuthOutcome
}
```

Android: `androidx.biometric.BiometricPrompt` с `BIOMETRIC_WEAK or DEVICE_CREDENTIAL`, то есть
отпечаток, лицо или PIN, графический ключ, пароль экрана блокировки. Почему WEAK:

- На API 28–29 комбинация `STRONG | DEVICE_CREDENTIAL` не поддерживается.
- Разблокировка лицом на большинстве Android относится к Class 2 (weak). Со STRONG она бы
  молча не предлагалась, а «FaceID» из просьбы владельца — именно она.
- Для замка на экране класс биометрии не важен. Он важен только для криптографии (§8).

Своего PIN у Unitool нет (D129). Запасной способ входа — PIN экрана блокировки устройства: система
сама предлагает его, если лицо или отпечаток не сработали. Лимит попыток и задержки тоже её.

### 5.3. Когда запирать

Одна отметка «владелец подтверждён в момент T» на весь хост, а не на каждое приложение (D130).
Хранится только в памяти: после смерти процесса всё заперто.

```
Background ─┬─ экран погас (PowerManager.isInteractive == false)  → запереть сразу
            └─ ушли в другое приложение                            → запомнить время
Foreground ─── прошло больше grace (по умолчанию 60 с)             → запереть
Процесс умер ─ отметки нет                                         → заперто
Свой промпт открыт ─ Background/Foreground игнорируются (ловушка ниже)
```

Ловушки:

- **API 24–29 и PIN.** При `DEVICE_CREDENTIAL` androidx.biometric открывает системный
  `ConfirmDeviceCredential` как отдельную Activity. Для `ProcessLifecycleOwner` это выглядит как
  уход в фон (с задержкой 700 мс). Без флага «идёт свой промпт» получится петля: ушли в фон,
  заперли, снова промпт.
- **Share sheet экспорта и системные экраны настроек** — тоже уход в фон. Grace в 60 с
  нужен как раз для этого: отправили файл, вернулись, промпта нет. С `grace = 0` промпт будет
  после каждой отправки, и это честное следствие такой настройки.
- **Сканер QR** — наша же Activity в том же процессе, поэтому фона нет, всё в порядке. Диалог
  разрешения камеры — только `onPause`, тоже в порядке. Об этом уже написано в
  `Platform.android.kt`.

### 5.4. Занавес, а не шлагбаум (D128)

Замок стоит в `AppContainer` шелла. Это **единственное место, где рисуется `instance.Content()`**:

```kotlin
when {
    states[id] == AppState.Failed -> HostErrorScreen(…)
    lock.guards(id) && !lock.isOpen -> LockCurtain(app, lock)   // new
    open == null -> Box(Modifier.fillMaxSize())
    else -> … open.instance.Content()
}
```

Поэтому занавес одинаково закрывает все пути, которыми приложение попадает на экран, и ни один из
них не надо трогать:

- плитка;
- меню;
- deep link;
- активация;
- восстановление снапшота после смерти процесса;
- запуск из Service Menu;
- `NavigationService.open` из другого приложения;
- тап по пушу.

Повторное запирание живой сессии после фона — тот же механизм.

Отвергнутый вариант — «шлагбаум» в `AppHandler.launch`: не создавать экземпляр до разблокировки.
Потребуются новые `AppState.Locked`, отложенный запуск с его конфигом и снапшотом, особые ветки в
`restoreLastSession` (сейчас неудачный запуск стирает снапшот) и в `activation.apply(…).onSuccess`.
А промпт, пока запуск держит мьютекс `gate`, становится ожиданием пользователя под замком
обработчика. Кнопка «назад» в это время сама ждёт `close()` за тем же мьютексом. Ошибки этого
класса уже стоили времени: ловушка `collectLatest` в памяти 2FA.

Цена занавеса: код приложения выполняется до разблокировки. `onLaunch` читает хранилище и
расшифровывает список. На этапе 1 это ничего не теряет: ключ хранилища не привязан к
аутентификации, и код внутри процесса расшифрует его и без экрана. На этапе 2 `vault.open()`
сам дождётся разблокировки (§8), а 2FA и так грузится в `runtime.scope`, а не в `onLaunch`.

Как выглядит занавес: иконка и название приложения, «Заблокировано», кнопка «Разблокировать».
Промпт появляется сам один раз при показе. Если его отменить, занавес остаётся, а меню и «назад»
работают как обычно: можно уйти на Home. Заголовок и меню хоста не секретны и остаются видны.

Секции настроек (`ctx.settingsSection`) защищённого приложения рисуются на экране Settings хоста,
то есть вне занавеса. Правило: пока заперто, их не показываем. У 2FA таких секций сейчас нет.

### 5.5. Подтверждение действия (step-up)

```kotlin
/** Asks the person to prove they are the owner before one action. Optional service (D19). */
public interface UserPresence {
    /** True when confirmed now. [reason] is what the system sheet says the confirmation is for. */
    public suspend fun confirm(reason: String): Boolean
    public companion object { public val Key: ServiceKey<UserPresence> = ServiceKey("user-presence") }
}
```

В 2FA через него проходят три действия:

- **«Экспорт».** Главный путь кражи. Кто держит телефон минуту, вводит *свой* GitHub-логин и
  отправляет себе файл со всеми секретами. Такой файл хуже скриншота: в нём сразу всё.
- **«Показать ключ».** Ключ и есть аккаунт.
- **«Удалить».** Чужой может удалить аккаунт и так отрезать владельцу вход.

Копирование кода и добавление аккаунта подтверждения не требуют: коды — смысл приложения, а
добавление ничего не раскрывает. Без сервиса (desktop, web) `confirm()` недоступен и действие
выполняется как сейчас. Так же ведёт себя хранилище.

### 5.6. Окно

- `FLAG_SECURE` висит, пока на экране приложение с `secureWindow`, включая его занавес.
  Флаг снимается при уходе на Home. Ставит его хост через `AndroidHost.currentActivity()`,
  который уже есть. Compose-диалоги по умолчанию наследуют флаг (`SecureFlagPolicy.Inherit`), а
  диалог хоста рисуется в том же окне.
- `setHideOverlayWindows(true)` (API 31+) прячет чужие оверлеи. Его ставят банки, но он требует
  ещё одного разрешения `HIDE_OVERLAY_WINDOWS` (normal) в манифесте и строки в `PRIVACY.md`.
  Решает вопрос 67.

### 5.7. Настройки

Секция «Защита» на экране Settings хоста. Она видна, только если хоть одно зарегистрированное
приложение объявило `lock != Off`:

- «Блокировать после ухода из приложения»: сразу / 30 с / **1 мин** / 5 мин. При выключенном
  экране запирается сразу, всегда.
- Переключатель на каждое `OptionalOff`- и `OptionalOn`-приложение, в начальном положении,
  которое задало приложение. `Required` показаны строкой «всегда», без переключателя.
- «Заблокировать сейчас».

Хранится в `LockStore`, ключ `host.lock` в prefs хоста. Выбор человека записывается, только когда
он сам тронул переключатель. До этого действует значение приложения. Поэтому если обновление
приложения сменит `OptionalOff` на `OptionalOn`, это коснётся тех, кто не выбирал сам, а не тех,
кто выключил замок нарочно. Если обновление сделает приложение `Required`, записанный выбор
больше не действует.

Уровень проверки для всего хоста задаёт билдер: `lockStrength(AuthStrength.Any)` по умолчанию.
На этапе 1 Unitool его не трогает. Этап 2 переключает его на `Strong` (§8.5).

### 5.8. Когда спросить нечем

| Ситуация | `Required` | `OptionalOff` / `OptionalOn` |
|---|---|---|
| Android, блокировка экрана не настроена (`NoScreenLock`) | **открываем с предупреждением** (ответ на 64): над экраном приложения постоянная плашка хоста «Блокировка экрана не настроена — приложение не защищено» и кнопка «Настроить» (`ACTION_SECURITY_SETTINGS`) | переключатель недоступен, с той же подсказкой и кнопкой |
| Desktop, web (`Unsupported`) | открываем с плашкой «на этой платформе блокировки нет» | переключатель скрыт |
| Хост без аутентификатора (забыли `FragmentActivity`) | как `Unsupported` плюс `error` в логе и падение debug-сборки | то же |

Плашку рисует хост в `AppContainer`, в той же ветке, где стоит занавес, поэтому приложение про неё
не знает. Закрыть её нельзя: она исчезает сама, как только блокировку экрана включат. Проверяется
это при каждом `Foreground`, потому что включают её в системных настройках, то есть из фона.
Появилась блокировка — дальше действует обычный порядок §5.3, и при следующем открытии уже будет
промпт.

`FLAG_SECURE` висит и без блокировки экрана: против записи экрана и превью в «Недавних» он
помогает и тогда.

Подтверждение действия (§5.5) без блокировки экрана спросить нечем, и `confirm()` возвращает
true. Действие выполняется как сегодня: у удаления уже есть своё «Удалить навсегда», у экспорта
подтверждения нет. Предупреждением служит плашка над экраном.

Вторая строка — вопрос 65. По умолчанию она работает так же, как первая после ответа на 64:
открываем и предупреждаем. Хранилище ведёт себя так же: на desktop и web данные лежат открыто.

## 6. Утечки мимо любого замка — есть уже сегодня (шаг 0)

Всё ниже найдено чтением кода. На устройстве не проверялось.

1. **Снапшот сессии.** `AppHandler` пишет `SessionSnapshot(appId, config, state, …)` открытым
   текстом в `cx.m42.superizer.store` при каждом уходе в фон (`PrefsSnapshotStore`). Если 2FA
   открыли ссылкой `2fa/add?uri=otpauth://…secret=…`, `config` содержит секрет. `saveState()` у
   2FA секрет старательно не пишет, но хост кладёт рядом весь конфиг.
2. **Журнал событий.** `SuperizerEvent.Configured(appId, config)` — data class, и Service Menu
   рисует `event.toString()`, то есть секрет виден в списке последних событий. Service Menu в
   релизе открывается промокодом `SERVICE`, так что это путь к секрету для любого, кто держит
   телефон.
3. **`RouteDiscarded(appId, link)`.** Если человек отказался закрыть текущее приложение, в
   журнал попадает ссылка целиком, с `uri=otpauth…`.

Исправление (D134). Для приложения с `lock != Off` или с `secureWindow`:

- в событиях конфиг заменяется на `{"…": "redacted"}`, у ссылок отрезается query;
- в снапшоте `config` не сохраняется, `state` — по-прежнему (его приложение и так пишет без
  секретов).

Цена такого снапшота: после смерти процесса форма добавления, открытая ссылкой, вернётся пустой.
Это меньшее зло, и тёплый путь не страдает. Шаг 0 нужен **при любом решении по замку**: без
него замок обходится промокодом.

Ответ на 66: «не делать пока, только план написать». Ниже план, по которому этап делается,

Живёт этап в `services/vault` Unitool и в 2FA. Superizer ему нужен только в двух местах: параметр
`AuthStrength` у аутентификатора и `lockStrength` у билдера. Оба входят в контракт 2 уже на
этапе 1 (D142), поэтому **этапу 2 не нужен ни релиз Superizer, ни новая версия контракта**.

### 8.1. Что получаем и чем платим

Получаем: без свежей аутентификации человека секреты не расшифровать даже коду внутри процесса
(root, Frida, вредонос с правами). Ключ не выходит из Keystore и без аутентификации не работает.
Это уровень Aegis.

Платим:

- **Снял блокировку экрана — ключ пропал.** Android безвозвратно инвалидирует ключи,
  привязанные к аутентификации, когда пользователь выключает блокировку экрана. Без запасного
  слота это потеря всех 2FA-секретов разом. Поэтому запасной слот обязателен (D143).
- **Лицо Class 2 такой ключ не откроет.** Промпт хоста становится `Strong` (§8.5). У кого
  разблокировка лицом относится к Class 2 (у большинства Android), остаются отпечаток и PIN.
- **Код восстановления.** Человеку придётся его где-то хранить.

### 8.2. Схема ключей

Сейчас (v1) Keystore-ключ шифрует список напрямую. В v2 список шифруется случайным ключом данных
(DEK), а сам DEK лежит в нескольких «слотах», каждый завёрнут своим ключом:

```
accounts.sealed = "v2:" + Base64(JSON конверта)

{ "v": 2,
  "data":  "<b64: nonce | ChaCha20-Poly1305(DEK, accounts JSON) | tag>",
  "slots": [
    { "type": "device",       "alias": "cx.m42.services.vault.auth", "wrapped": "<b64>" },
    { "type": "recovery",     "kdf": "hkdf-sha256", "salt": "<b64>",  "wrapped": "<b64>" } ] }
```

- **DEK** — 32 случайных байта, создаётся один раз. Данные шифруются ChaCha20-Poly1305 в
  commonMain: он уже написан и сверен с JDK (Age). Keystore заворачивает только 32 байта.
- **Слот `device`** — AES-256-GCM-ключ Keystore `cx.m42.services.vault.auth`:
  - API 30+: `setUserAuthenticationRequired(true)` и
    `setUserAuthenticationParameters(30, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`;
  - API 24–29: `setUserAuthenticationValidityDurationSeconds(30)`;
  - API 28+: `setUnlockedDeviceRequired(true)`;
  - StrongBox, где он есть, с откатом на TEE.

  Окно в 30 с, а не подтверждение на каждую операцию (`CryptoObject`). Иначе промпт хоста должен
  знать про шифр хранилища. С окном хост просто отпирает, а хранилище сразу после этого
  разворачивает DEK.
- **Слот `device-plain`** — сегодняшний ключ `cx.m42.services.vault` без аутентификации. Нужен,
  когда блокировки экрана нет (ответ на 64: приложение всё равно открывается). Ключ под
  аутентификацией тогда создать нельзя, а данные где-то жить должны.
- **Слот `recovery`** — DEK, завёрнутый ключом `HKDF-SHA256(код восстановления, salt)`. Тип
  слота входит в AAD, чтобы слоты нельзя было подменить друг другом.

Почему DEK со слотами, а не просто другой Keystore-ключ: Keystore-ключ — единственное, что может
исчезнуть. DEK должен переживать его пропажу. Кроме того, слоты позволят позже добавить второй
способ входа, не перешифровывая данные.

### 8.3. Код восстановления

По умолчанию (вопрос 69) это случайные 128 бит, показанные один раз как 8 групп по 4 знака
base32. Так выглядят резервные коды, которые 2FA-пользователи уже знают. У кода высокая
энтропия, поэтому хватает HKDF: медленный KDF и защита от перебора не нужны.

Альтернативы:

- **Пароль, как в Aegis.** Его можно запомнить. Но нужен scrypt: HMAC-SHA256 уже есть, Salsa20/8
  придётся написать. И защита будет ровно такой, как пароль человека.
- **Только экспорт на GitHub-ключи.** Своего слота нет: восстановились из файла. Требует
  импорта экспорта, а его нет (в памяти 2FA он записан как «deliberately missing»).

### 8.4. Жизненный цикл

- **Включение.** По умолчанию человек включает это сам, переключателем «Усиленная защита» в 2FA
  (вопрос 70). Шаги:
  1. Отпирание уровня `Strong`.
  2. Хранилище открывает v1 старым ключом, создаёт DEK и код и показывает код.
  3. Человек вводит последнюю группу — так видно, что код записан.
  4. Запись v2.
  5. **Контрольное чтение v2 через оба слота.**
  6. Только после этого удаляется ключ v1 (если нет блокировки экрана, он остаётся слотом
     `device-plain`).

  Сбой на любом шаге оставляет v1 нетронутым.
- **Открытие.** Хост отпирается (§5.3), и в пределах 30 с хранилище разворачивает DEK. Пока хост
  отперт, DEK держится в памяти. Когда хост запирает по правилам D131, DEK затирается
  (`fill(0)`). Честно: копии в куче JVM так не гарантированно убрать, настоящий барьер здесь —
  Keystore-ключ.
- **Откуда хранилище знает о запирании.** Лямбда из `MainActivity`, как язык для сканера QR:
  `AndroidKeystoreVault(lock = { Holder.superizer?.lock?.state })`.
- **Блокировку экрана включили.** При следующем отпирании слот `device-plain` перезаворачивается
  в `device`, а `device-plain` удаляется.
- **Блокировку экрана сняли.** Приходит `KeyPermanentlyInvalidatedException`, хранилище
  переходит в состояние `NeedsRecovery`. 2FA показывает: «Ключ устройства утрачен —
  блокировка экрана снималась. Введите код восстановления». После ввода кода DEK
  перезаворачивается в `device-plain` или в новый `device`. Пока ждём код, конверт **не
  перезаписывается**. Это то же правило, что сегодня для нечитаемого блоба.
- **Код и ключ устройства потеряны одновременно** — данные потеряны. На экране включения это
  сказано прямо, без смягчений.
- **Новый код.** Отпирание `Strong`, затем перезаворачивается только слот `recovery`.
- **Новый телефон.** Keystore-ключи не переезжают. Бэкап сегодня ничего не сохраняет, и это
  оставляем. Переезд — через экспорт (и будущий импорт), а не через код.

### 8.5. Что меняется в контрактах

- **`SecretVault` 1.0 → 2.0.** Сейчас `open()` → `null` значит «не открыть», а в v2 надо отличать
  «заперто, подожди» от «испорчено». Иначе 2FA покажет запертый список как нечитаемый.

  ```kotlin
  public sealed interface Opened {
      public data class Text(val value: String) : Opened
      public data object Locked : Opened          // wait for the host to unlock
      public data object NeedsRecovery : Opened   // device key gone; ask for the code
      public data object Unreadable : Opened      // today's null
  }
  public suspend fun open(sealed: String): Opened
  public suspend fun recover(sealed: String, code: String): Opened
  ```

  Интерфейс принадлежит Unitool (`services/vault`), а не Superizer, так что меняется только
  Unitool.
- **`AccountStore`.** На `Locked` ждёт отпирания и не показывает заметку о порче. На
  `NeedsRecovery` показывает экран ввода кода. На `Unreadable` ведёт себя как сегодня.
- **Superizer** (уже в контракте 2, D142). Когда включена усиленная защита, Unitool вызывает
  `lockStrength(AuthStrength.Strong)`. Промпт хоста тогда `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`
  на API 30+. На API 24–29 ключ с окном отпирает и разблокировка самого устройства, так что
  промпт остаётся прежним.

  Отвергнутый вариант — хранилище само переспрашивает `Strong` после отпирания лицом. Тогда
  человек видит два промпта подряд: сначала лицо, потом палец.

## 10. Связь с 04

В модели кирпичей экран — это `ComposedApp` с производным манифестом. `protection` берётся из
кирпича. Документ сборки может её **повысить** (сервер требует замок для инструмента с
учётными данными), но не **понизить** ниже кирпича. Порядок:
`Off < OptionalOff < OptionalOn < Required`.
Больше ничего в 04 не меняется.

## 11. Приёмка

- **core и host** (FakeClock, фейковый жизненный цикл, `FakeDeviceAuthenticator`):
  - защищённое приложение при старте заперто, обычное — нет;
  - фон короче grace — открыто, длиннее — заперто;
  - при выключении экрана запирается сразу;
  - во время своего промпта фон игнорируется;
  - после перезапуска процесса заперто;
  - отмена оставляет запертым;
  - `LockedOut` показывает системный текст;
  - `OptionalOff` без выбора человека не заперто, `OptionalOn` заперто. Выбор человека
    переживает смену значения по умолчанию в обновлении, но не переход на `Required`;
  - при `NoScreenLock` у `Required` занавеса нет, а плашка есть. После появления блокировки
    экрана и `Foreground` плашки нет, и при следующем открытии будет промпт.
- **ui — главный тест:** ни один из восьми путей из §5.4 не рисует узел `2fa:root` без
  разблокировки. Проверка: виден `shell:lock`, а `2fa:root` отсутствует. Это и есть «все пути
  через одну точку».
- **§6:** в `recentEvents` и в сохранённом `SessionSnapshot` защищённого приложения нет
  подстроки `secret=`.
- **2FA:** «Экспорт», «Показать ключ» и «Удалить» без подтверждения не выполняются. При отмене
  подтверждения ничего не меняется.
- **Эмулятор `unitool35`:**
  - отпечаток через `adb -e emu finger touch 1`;
  - `adb shell screencap` при открытой 2FA даёт чёрный кадр;
  - в «Недавних» пустое превью.
- Скриншоты: занавес, плашка «Блокировка экрана не настроена» и секция «Защита» со всеми
  четырьмя видами политики.

## 13. Решения (продолжают нумерацию 05; там последнее — D126)

- **D127.** Защищённость — свойство, которое приложение **объявляет** в манифесте
  (`AppManifest.protection`). Исполняет его хост. Само приложение решает только, какие
  действия внутри себя переспрашивать.
- **D128.** Замок — занавес в `AppContainer`, а не шлагбаум в `AppHandler.launch`. Обработчик,
  его мьютекс, `Result` и восстановление снапшота не меняются.
- **D129.** Подтверждает устройство: биометрия (`BIOMETRIC_WEAK`) или PIN, ключ, пароль экрана
  блокировки через системный промпт. Своего PIN у Unitool нет.
- **D130.** Одна разблокировка на человека и на весь хост. Живёт только в памяти, после смерти
  процесса всё заперто.
- **D131.** При выключении экрана запирается сразу. После ухода в другое приложение — по
  истечении grace, по умолчанию 60 с. Пока открыт свой промпт, переходы жизненного цикла
  игнорируются.
- **D132.** `FLAG_SECURE` висит, пока на экране приложение с `secureWindow`, включая занавес.
- **D133.** Подтверждение отдельного действия — необязательный сервис `UserPresence` (D19). В 2FA
  через него проходят «Экспорт», «Показать ключ» и «Удалить».
- **D134.** Конфиг защищённого приложения секретен: в событиях он скрыт, из ссылок отрезается
  query, в снапшот не пишется. Это делается первым, при любом решении по замку.
- **D135.** ~~`Required` без блокировки экрана — не открываем, ведём в настройки.~~ *(Первая
  половина пересмотрена в 1.1 ответом на 64 → D140.)* На платформе без аутентификатора открываем
  с плашкой. Это значение по умолчанию, окончательно его решает вопрос 65.
- **D136.** Детекторы root, эмулятора, отладчика и Frida, Play Integrity и свой PIN не делаем.
  Выход по бездействию тоже не делаем.
- **D137.** Ключ хранилища, привязанный к аутентификации, — отдельный этап 2 и только с
  запасным слотом восстановления.

### 15.2. Отличия от §5–§9

1. **`FLAG_SECURE` ставит `ui`, а не хост.** Это `SecureWindow(active)` в `AppContainer` через
   `LocalActivity`, со счётчиком. Пока идёт анимация перехода, скомпонованы два контейнера, и
   уходящий не должен снять флаг, который поставил пришедший.
2. **Экран погас — и из фона тоже.** Кроме проверки `isInteractive` при `Background` есть приёмник
   `ACTION_SCREEN_OFF` (`PlatformScreen`). Без него сценарий «ушёл в другое приложение, погасил
   экран, через 30 с телефон взял другой» оставлял замок открытым.
3. **Переходы во время своего промпта записываются, а не выбрасываются.** Время ухода
   запоминается. Если промпт закончился не успехом, отсутствие оценивается сразу (если уже
   вернулись) или при `Foreground`. Иначе промпт подтверждения стал бы способом держать замок
   открытым: открыл «Экспорт», ушёл на 10 минут, вернулся — и всё открыто.
4. **Промпт ждёт переднего плана.** Занавес может опуститься в фоне, когда погас экран.
   `unlock()` ждёт `Foreground`, а Android-аутентификатор дополнительно ждёт
   `lifecycle.withStarted`. Показ `BiometricPrompt` после `onSaveInstanceState` бросает
   исключение.
5. **Доступность на Android — `KeyguardManager.isDeviceSecure`, а не
   `BiometricManager.canAuthenticate`.** На API < 30 `canAuthenticate(DEVICE_CREDENTIAL)` не
   отвечает. Биометрию без блокировки экрана Android завести не даёт, так что одного keyguard
   достаточно.
6. **D138 усилено в регистре.** Манифест с `protection` и `minHostContract < 2` отклоняется и на
   новом хосте. Иначе забытая двойка обнаружилась бы только на старом хосте, где замка нет вообще.
7. **Плашка «не защищено» — над любым приложением из `guarded`, не только над `Required`.**
   Например, `OptionalOn` на телефоне без блокировки экрана.
8. **Ослабление в «Защите» спрашивает.** Если замок закрыт, выключение опционального замка и
   увеличение grace сначала показывают промпт. Иначе Settings стали бы обходом занавеса.
9. **Под занавесом заголовок бара — название приложения, а не `chrome.title`.** У 2FA на странице
   аккаунта заголовок — имя аккаунта.
10. **Причина `ConfigRejected`/`LaunchFailed` у защищённого приложения не цитируется.** Сообщение
    декодера kotlinx.serialization содержит сам payload. `cause` тоже не передаётся.
11. **`UserPresence` регистрирует хост сам,** если аутентификатор платформы не `Unsupported`.
    Регистрировать его в Unitool не нужно.
12. **В шелл вошёл `filterNotNull()` перед `collectLatest`** (ловушка из памяти 2FA), как и
    предлагал §9.

### 15.3. 2FA

- `minHostContract = 2`, `protection = AppProtection(Required, secureWindow = true)`.
- `UserPresence.confirm` стоит перед входом на страницу экспорта, перед показом ключа (скрытие
  ничего не спрашивает) и перед «Удалить навсегда». Отмена ничего не меняет.
- Показанный ключ живёт в `TwoFaInstance.shownSecret` и сбрасывается при любой смене страницы.
  Раньше он был в `remember`.
- **Буфер обмена (`CodeClipboard`).** Код кладётся с `android.content.extra.IS_SENSITIVE` и
  стирается через 60 с, если буфер всё ещё его. Свой клип узнаётся по label, а не по тексту: чтение
  текста на Android 12+ показывает тост «вставлено из буфера». Описание буфера Android отдаёт только
  приложению на переднем плане. Поэтому, если минута истекла в чужом приложении, попытка
  повторяется при возвращении в Unitool (`onForeground`). Если туда не вернулись, буфер чистит сам
  Android 13+ через час.
- Поле ключа: `KeyboardType.Password`, без автокоррекции. Поле ссылки: `KeyboardType.Uri`, без
  автокоррекции.
