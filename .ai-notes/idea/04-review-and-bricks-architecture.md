## 0. Коротко

1. Заметки 01–03 верно решили **транспорт** (привязка, тикль, синк, провенанс, состояния) и неверно —
   **предмет**: у них тулза = приложение, а приложение = его сервер. Кирпич, приваренный к бэкенду,
   нельзя переиспользовать, а сервер может только *включать* то, что есть в сборке, но не *собирать*.
2. Новая модель: **кирпич** (типизированный нативный экран с абстрактными хендлерами — портами) не
   знает сервера; **коннектор** реализует порты для одного протокола; **сборка** (документ с сервера
   или DSL в хосте) соединяет кирпичи с коннекторами, даёт каждому экрану иконку, цвет, подпись и
   связывает экраны между собой. Сервер собирает тулзы из кирпичей, а не включает приложения.
3. Порт — это уже существующий `ServiceKey` (D19). Кирпич объявляет порты в `manifest.requires`,
   хост подставляет их через `runtime.service(key)`. **Контракт приложения остаётся 1.**
4. Каждая сборка регистрируется в `AppRegistry` как **собранное приложение** со своим `AppId`.
   Изоляция хранилища, темы пушей, Home, разблокировка, снимок, deep link — всё работает как
   сегодня, без перевода хоста на `InstanceId` (02 §6 отменяется целиком).
5. «Апишку предоставляем мы»: v1-коннектор — `superizer-http`, где сервер реализует протокол
   кирпича, а не кирпич — протокол сервера. Кодовые коннекторы под чужие API — когда понадобятся.
   Скриптовый коннектор (QuickJS) — заметка 05, отложен и обоснован.

## 1. Ревью заметок 01–03

Формулировка владельца, из которой выросло ревью: «проблемы возникают, когда мы хотим библиотеку
эпов привязать к конкретному приложению. Надо внутри Unitool разделять понятие эппы и группировку
делать как кирпичики, связывая через конфиг. Форма инвентаризации — абстрактная: абстрактный
конфиг, абстрактные хендлеры, хендлеры ходят куда-то вовне. Если у неё зашитое поведение — значит,
мы с другой стороны предоставляем апишку; это легче, чем держать внутри приложения JS-компилятор.
Типизация — для определённого экрана, а экраны между собой собираем: каждому экрану иконку, цвет.
Внутри экрана — форма, жёстко запрограммированная в приложении. Из кирпичиков собираем тулзы для
сервака. Версионирование тулов, конфигов и разные версии тулов — нужны.»

### 1.1. Что в 01–03 правильно и остаётся без изменений

Это не формальность: ниже переписывается модель предмета, и важно не выбросить транспорт, который
её везёт.

- **Пуш — тикль, конфиг — по HTTPS** (01 D65–D66). Шесть причин в 01 §5 не зависят от того, что
  именно едет в документе.
- **Документ — желаемое состояние, применяется как diff, монотонная версия** (01 D67–D68).
- **Провенанс `source`** и правило «отвязка снимает ровно то, что выдала привязка» (01 D70), а
  также «привязка не экспортируется» (D79) и «согласие — это экран с доменом» (D80).
- **Тикет в QR, идентичность при обмене**, `installId` ≠ `deviceId` ≠ FCM-токен (01 D63–D64).
- **Секции на одном экране, без вложенности, заголовки только при двух и более секциях**
  (02 D83–D85); пуш адресован `bindingId` (D88); правила снятия неоднозначности ссылок (D89).
- **Состояния доступа `active | expired | suspended`, просрочка не удаляет данные, возврат без
  нового QR, клиентский отзыв — UX, а не защита** (03 D92–D94).
- **Частичные изменения — полный документ по умолчанию, патч с `baseVersion` опционально**
  (03 D95); **синк не заставляет ждать** (D99); **пользовательские настройки — в `runtime.storage`,
  не в конфиге** (D101).
- Стенд на фейковом сервере и список тестов (01 §15, 03 §10) — переиспользуются, меняются имена
  сущностей.

## 2. Принцип

Четыре стороны, и каждая знает ровно одну соседнюю:

```
  сервер ──(документ сборки)──► хост ──(порты)──► кирпич
     ▲                            │
     └────(протокол порта)────── коннектор
```

- **Кирпич не знает сервера.** Он объявляет, *что ему нужно снаружи* (порты), и рисует форму.
- **Сервер не знает кода.** Он знает кирпичи по инвентарю (имя, версия, порты, схема конфига) и
  собирает из них тулзы документом.
- **Коннектор — единственное место, где есть адрес, ключ и формат.** Один коннектор обслуживает
  все кирпичи аккаунта, которые ему назначены.
- **Хост исполняет сборку**: соединяет, изолирует, показывает, версионирует. Содержимое конфига
  кирпича для него по-прежнему непрозрачно (D2 не тронут); структура сборки — его язык.

Отличие от 01–03 в одной фразе: **раньше документ говорил «включи приложение X с конфигом Y»,
теперь — «собери экран из кирпича X, подключи его порты к коннектору Z, покажи так-то».**

## 4. Кирпич

Кирпич — это сегодняшний `SuperizerApp<C>` с тремя уточнениями, ни одно из которых не меняет
контракт.

```kotlin
// apps/inventory-form/src/commonMain/kotlin/cx/m42/bricks/inventory/InventoryFormBrick.kt
public class InventoryFormBrick : SuperizerApp<InventoryFormConfig>() {

    override val manifest = AppManifest(
        id = AppId("inventory-form"),
        version = "1.2.0",
        metadata = AppMetadata(
            title = localized("ru" to "Инвентаризация", "en" to "Inventory"),
            icon = AppIcon.Named("clipboard"),
            // По умолчанию кирпич — шаблон: сам по себе плиткой не является (D8, hidden).
            // Плиткой его делает сборка. Калькулятор — не шаблон: он сам себе сборка (§11).
            hidden = true,
        ),
        // 1. Порты — это requires. Хост подставит их через runtime.service(key), иначе не соберёт.
        requires = setOf(RecordsPort.Key, SubmitPort.Key, LookupPort.Key),
        // 2. Выходы: что кирпич умеет «отдать наружу» после работы. Сборка решает, куда они ведут.
        exits = setOf("submitted", "cancelled"),
        // 3. networkHosts пуст: кирпич с портами в сеть напрямую не ходит. Хосты объявляет коннектор.
    )

    override val configSpec = AppConfigSpec(InventoryFormConfig.serializer(), InventoryFormConfig(), schemaVersion = 2)

    override fun launch(runtime: InstanceRuntime, config: InventoryFormConfig): AppInstance =
        InventoryFormInstance(
            records = runtime.require(RecordsPort.Key),
            submit = runtime.require(SubmitPort.Key),
            lookup = runtime.require(LookupPort.Key),
            links = runtime.service(LinksService.Key),   // необязателен: без сборки выходов нет
            config = config,
        )
}

/** Конфиг кирпича — язык кирпича. Хост его не читает (D2). */
@Serializable
public data class InventoryFormConfig(
    val collection: String = "inventories",
    val fields: List<FieldSpec> = defaultFields,
    val requirePhoto: Boolean = false,
    val lookupKind: String = "item",
)
```

Правила кирпича (это правила ревью, не рантайма):

- **Кирпич с портами не использует `runtime.network` напрямую.** Всё внешнее — через порты.
  Исключение — кирпич без портов (калькулятор) и кирпич, который сам себе коннектор в
  локальной сборке (§11, конвертер сегодня). Проверяется тестом: `FakeAppRuntime` с
  `network = null` не должен ломать кирпич с портами.
- **Кирпич не знает ни ключа, ни адреса.** Если в его конфиге появилось `baseUrl` или `apiKey` —
  это И2, и ревью не пропускает.
- **Форма жёстко запрограммирована** (формулировка владельца). Конфиг задаёт, *что* показать
  (поля, обязательность, подписи), а не *как* рисовать. Никакого UI-DSL с сервера: это Tier 3 из
  заметки 10, и это отдельный продукт.
- **Выходы вместо навигации.** Кирпич не открывает другие приложения по `AppId` — он не знает,
  с кем его собрали. Он говорит `links.follow("submitted")`, а сборка решает, куда это ведёт (§7.3).
- **Пользовательские настройки — в `runtime.storage`** (03 D101). Конфиг перезаписывается сборкой.

Новое в `core`, всё аддитивно с дефолтами: `AppManifest.exits: Set<String> = emptySet()`,
`AppMetadata.accent: String? = null` (цвет плитки, hex). ABI-дамп обновляется, контракт остаётся 1
(вопрос 51 — подтвердить правилом проекта, что аддитивное поле с дефолтом не поднимает контракт).

## 5. Порты

### 5.1. Форма порта

Порт — Kotlin-интерфейс, у которого три свойства, и все три — ради коннекторов, которых ещё нет:

1. **На границе — JSON и строки.** `JsonObject`, `JsonArray`, `String`, `ByteArray` для файлов.
   То же правило, что у `AppRuntime` (Services.kt, «nothing here takes a type that cannot be
   JSON»): порт можно замостить (10), подделать в тесте двадцатью строками и реализовать скриптом
   (05). Типизацию кирпич делает у себя — `decode<T>()` уже есть.
2. **`Result`, не исключения.** Кирпич показывает ошибку, а не падает.
3. **Версия в имени ключа.** `records@1`. Несовместимое изменение — `records@2`, новый интерфейс,
   старый живёт, пока есть коннектор, который его реализует.

```kotlin
// superizer:ports — cx.m42.superizer.ports (новый модуль: зависит только от core)

/** Ключ порта: ServiceKey, в имени которого — версия контракта. */
public fun <T : Any> portKey(name: String, version: Int): ServiceKey<T> = ServiceKey("$name@$version")

/** Коллекции записей: то, что нужно любому списку и любой форме редактирования. */
public interface RecordsPort {
    public suspend fun query(collection: String, query: JsonObject): Result<JsonArray>
    public suspend fun get(collection: String, id: String): Result<JsonObject?>
    public suspend fun create(collection: String, record: JsonObject): Result<JsonObject>
    public suspend fun update(collection: String, id: String, patch: JsonObject): Result<JsonObject>
    public companion object { public val Key: ServiceKey<RecordsPort> = portKey("records", 1) }
}

/** Отправка документа. Идемпотентна по [clientId]: та же форма дважды — одна отправка (И7). */
public interface SubmitPort {
    public suspend fun submit(form: String, clientId: String, document: JsonObject): Result<JsonObject>
    public companion object { public val Key: ServiceKey<SubmitPort> = portKey("submit", 1) }
}

/** Справочник по коду: штрихкод → товар, табельный номер → сотрудник. */
public interface LookupPort {
    public suspend fun lookup(kind: String, code: String): Result<JsonObject?>
    public companion object { public val Key: ServiceKey<LookupPort> = portKey("lookup", 1) }
}

/** Файлы: фото к акту. Возвращает id, по которому сервер их найдёт в документе. */
public interface FilesPort {
    public suspend fun upload(purpose: String, bytes: ByteArray, mime: String): Result<String>
    public companion object { public val Key: ServiceKey<FilesPort> = portKey("files", 1) }
}
```

### 5.2. Общие и частные порты

Четыре порта выше — **общие**: с ними собирается большинство форм, списков и сканеров, и именно
они делают кирпич переносимым между серверами. **Частный** порт (`InventoryPort` с методом
`closeShift`) допускается, живёт в модуле кирпича в пакете `api`, и коннектор для него пишется
рядом. Правило: сначала попытаться выразить через общие порты; частный — когда общие искажают
смысл, а не когда лень.

### 5.3. Протокол порта — это и есть «апишка, которую предоставляем мы»

У каждого порта есть **эталонное HTTP-отображение** — протокол `superizer-http`, версия 1:

| Порт | Метод | Путь | Тело / ответ |
|---|---|---|---|
| `records.query` | POST | `{base}/records/{collection}/query` | query → `200 [record…]` |
| `records.get` | GET | `{base}/records/{collection}/{id}` | → `200 record` / `404` |
| `records.create` | POST | `{base}/records/{collection}` | record → `201 record` |
| `records.update` | PATCH | `{base}/records/{collection}/{id}` | patch → `200 record` |
| `submit` | POST | `{base}/submit/{form}` + `Idempotency-Key: {clientId}` | document → `201 receipt`; `409` = уже принято, считается успехом |
| `lookup` | GET | `{base}/lookup/{kind}?code=…` | → `200 record` / `404` |
| `files.upload` | POST | `{base}/files/{purpose}` multipart | → `201 {id, url}` |
| авторизация | — | `Authorization: Bearer <секрет коннектора>` | `401` → привязка `Unauthorized` (01 §13); `403` → тулза `suspended` с `reason` |
| ошибки | — | `application/problem+json` (RFC 9457) | `title` показывается человеку, `detail` — в лог |

Это ровно то, что сказал владелец: «если у кирпича зашитое поведение — мы с другой стороны
предоставляем апишку». Сервер, который хочет использовать кирпич, реализует эти семь маршрутов
поверх своих моделей (для Adminizer — один тонкий слой, §12). Ни одной строчки на устройстве
для нового сервера писать не надо.

**Честное ограничение.** В `commonMain` нет рефлексии и `Proxy`, поэтому «универсальный»
коннектор не может реализовать произвольный Kotlin-интерфейс по описанию. Каждый порт приносит
свою HTTP-реализацию — класс `RecordsHttp(client, base, auth) : RecordsPort` рядом с интерфейсом,
тридцать строк. Коннектор `superizer-http` — это **семейство** таких классов, зарегистрированное
по ключу порта. Динамическое отображение «любой порт на любой API без кода» даёт только
скриптовый коннектор (05) — и это главный аргумент за него, когда он понадобится.

### 5.4. Что порт не делает

- Не навигирует (это `LinksService`, §7.3).
- Не знает про пуши: контентный пуш приходит кирпичу как сегодня, через `runtime.push`.
- Не кэширует и не ставит в очередь сам — это декораторы коннектора (§6.4), чтобы форма без сети
  вела себя одинаково на любом бэкенде.

## 6. Коннекторы

### 6.1. Что это

Коннектор — реализация одного или нескольких портов для одного протокола, со своими настройками
и своими секретами. Он **объявляет хосты**, в которые ходит, и **не отдаёт** секреты никому.

```kotlin
// superizer:host — cx.m42.superizer.host.connectors

/** Вид коннектора: имя, версия и фабрики портов, которые он умеет. Регистрируется в сборке хоста. */
public interface ConnectorKind {
    public val name: String                 // "superizer-http", "local", "dailyscope-v2"
    public val version: Int
    public val ports: Set<ServiceKey<*>>    // что умеет: records@1, submit@1, …
    public fun <T : Any> open(port: ServiceKey<T>, ctx: ConnectorContext): T
}

/** Что коннектор получает при сборке. Секрет — по ссылке, не значением: он никогда не в конфиге. */
public class ConnectorContext(
    val settings: JsonObject,               // baseUrl, paths-переопределения, timeouts — язык коннектора
    val secret: suspend () -> String?,      // из BindingStore.secret(bindingId, connectorName)
    val network: NetworkService,            // уже ограниченный allowlist-ом этого коннектора (§13)
    val storage: StorageService,            // пространство коннектора (кэш, outbox), не кирпича
    val logger: Logger,
)
```

### 6.2. Виды коннекторов, по очереди появления

| Вид | Реализует | Когда | Стоимость |
|---|---|---|---|
| **`superizer-http`** | все общие порты по протоколу §5.3, `paths` переопределяются в настройках | **v1.** Сервер реализует протокол кирпича | по классу на порт, ~30 строк каждый |
| **`local`** | `records`/`submit`/`lookup` поверх `runtime.storage`: коллекции в JSON | **v1.** Демо, стенд, офлайн-тулза без сервера, тесты | небольшой |
| **кодовый** (`dailyscope-v2`, `iiko`…) | порты поверх чужого API, который менять нельзя | когда появится такой API. Модуль в сборке Unitool, регистрируется как кирпич | зависит от API; релиз в Play |
| **`script`** | порты, реализованные JS-кодом из документа | заметка 05; по критериям оттуда | движок + песочница + ревью |

Настройка коннектора в документе — **язык коннектора**, хост читает из неё только `kind`,
`version`, `hosts`, `auth`:

```json
"api": { "kind": "superizer-http", "version": 1,
         "baseUrl": "https://api.dailyscope.example/superizer",
         "hosts": ["api.dailyscope.example"],
         "auth": { "ref": "account" },
         "paths": { "submit": "/v2/acts/{form}" } }
```

### 6.3. Секреты

- `auth.ref: "account"` — секрет коннектора = device-токен привязки (01 §6.2). Достаточно для
  сервера, который сам и выдал документ.
- `auth.ref: "secret:<name>"` — отдельный секрет, который сервер отдал **в ответе `enroll`** или
  в отдельном ответе `GET /secrets` с `Cache-Control: no-store`, и который хост положил в
  `BindingStore.saveSecret(bindingId, name)`. В документе конфигурации секретов **нет** —
  документ кэшируется, логируется в Service Menu и сравнивается по ETag; секрет в нём — это
  секрет в трёх местах.
- Кирпич не имеет пути к секрету: у `ConnectorContext` он есть, у `AppRuntime` — нет. И2 закрыт
  конструкцией, а не маскированием.

### 6.4. Декораторы

Поведение, одинаковое для всех бэкендов, реализуется один раз как обёртка над портом:

| Декоратор | Над чем | Что делает |
|---|---|---|
| `outbox` | `SubmitPort` | без сети — в очередь в `storage` коннектора, `Result.success({queued:true, clientId})`; отправка при `online`/foreground/старте; повтор безопасен благодаря `Idempotency-Key`. Кирпич показывает «отправлено, ждёт сети» — по полю `queued` |
| `cache` | `RecordsPort.query/get`, `LookupPort` | последний ответ в `storage`, отдаётся при офлайне (та же логика, что у `RatesRepository` конвертера, но написанная один раз) |
| `log` | любой | вызовы в кольцевой буфер Service Menu с маскированием тела |

Включаются настройкой коннектора (`"outbox": true`), не кодом кирпича. В v1 — `log`; `outbox` и
`cache` — этап 4 (§15), но интерфейсы портов с самого начала таковы, чтобы декоратор был
возможен (идемпотентный `clientId` — именно поэтому он в сигнатуре, а не в теле).

## 7. Сборка: экран, тулза, собранное приложение

### 7.1. Экран

Экран = кирпич × привязка портов × конфиг × оформление. Это то, что видит человек как плитку.

```kotlin
// core — cx.m42.superizer.composition

@Serializable
public data class Composition(
    /** Производный AppId собранного приложения (§7.4). Ключ всего. */
    val id: AppId,
    val brick: AppId,
    /** Что попросил документ (">=1.2") и что резолвилось из сборки ("1.2.0"). Обе — для Service Menu. */
    val brickRequired: String?, val brickVersion: String,
    val source: ProvisioningSource,         // build | qr | bundle | binding:<bindingId>   (01 D70 + build)
    val section: SectionId,
    val tool: ToolRef?,                     // toolId, toolVersion, screenId — null у одиночного экрана
    val presentation: Presentation,         // label, icon, accent, order
    /** имя порта → имя коннектора аккаунта (или встроенное определение для local/qr). */
    val ports: Map<String, ConnectorRef>,
    val config: AppConfig,                  // язык кирпича, непрозрачен
    val exits: Map<String, String> = emptyMap(),   // exit кирпича → screenId той же тулзы
    val state: AccessState = AccessState.Active, val reason: String? = null,
    val documentVersion: Long, val appliedAt: Long,
)
```

Реестр сборок (`CompositionStore` в `core` — протокол, `PrefsCompositionStore` в `host`) — это
`ProvisioningStore` из 16 (D49) с другой записью. Всё, что 16 планировала про сохранение,
`overlaidWith`, экспорт и импорт, остаётся — единица теперь `Composition`.

### 7.2. Тулза

Тулза — набор экранов с версией, `state` и `reason`. Это единица **выдачи** (грант), **отзыва**
(нет в документе — уходят все её экраны) и **версионирования** (`toolVersion`). На Home она —
подпись под секцией, если у аккаунта тулз больше одной; при одной тулзе подписи нет (тот же
принцип, что 02 D85).

Ограничение, которое надо озвучить: **тулза не является уровнем навигации** (02 D84). Плитки —
экраны. Если у тулзы шесть экранов, на Home шесть плиток под её подписью; хотеть «одну плитку,
внутри меню» — это вопрос 52, и ответ «нет» дешевле.

### 7.3. Экраны собираются через выходы

Кирпич объявил `exits = {submitted, cancelled}`. Сборка написала `"exits": {"submitted": "history"}`.
Хост даёт собранному приложению необязательный сервис:

```kotlin
/** Есть только у собранного приложения, у которого есть выходы. Обычный ServiceKey (D19). */
public interface LinksService {
    public val exits: Set<String>
    /** Закрывает текущий экран и открывает тот, куда ведёт выход; payload — transient-конфиг адресата. */
    public suspend fun follow(exit: String, payload: JsonObject? = null): Result<Unit>
    public companion object { public val Key: ServiceKey<LinksService> = ServiceKey("links") }
}
```

Реализация — `navigation.openApp(composedIdOf(screenId), payload.asConfig())`: тот же
`OpenApp`, что сегодня, кирпич просто не знает адреса. Выход без назначения → `Result.failure`,
кирпич показывает «готово» и остаётся. Это и есть «экраны между собой собираем»: связи живут в
документе, а не в коде.

### 7.4. Собранное приложение — запись в `AppRegistry`, а не новый ключ

Ключевое упрощение относительно 02. Вместо второго ключа `InstanceId` во всём хосте — обёртка:

```kotlin
// host — cx.m42.superizer.host.composition

/** Кирпич + сборка = приложение, каким его видит весь остальной хост. Делегирует всё кирпичу. */
internal class ComposedApp<C : Any>(
    private val brick: SuperizerApp<C>,
    private val composition: Composition,
    private val boundPorts: Set<ServiceKey<*>>,
) : SuperizerApp<C>() {
    override val manifest = brick.manifest.copy(
        id = composition.id,
        metadata = brick.manifest.metadata.copy(
            title = composition.presentation.label?.let { localized("und" to it) } ?: brick.manifest.metadata.title,
            icon = composition.presentation.icon ?: brick.manifest.metadata.icon,
            accent = composition.presentation.accent,
            hidden = false,
        ),
        // Порты, которые сборка подставит сама, для регистрации «предоставлены». Остальные requires
        // (камера и т. п.) проверяются против HostInfo.services как сегодня.
        requires = brick.manifest.requires - boundPorts,
        networkHosts = emptySet(),     // хосты — у коннекторов (§13)
    )
    override val configSpec = brick.configSpec
    override fun setup(ctx: AppSetupContext) = brick.setup(ctx)
    override fun launch(runtime: InstanceRuntime, config: C) = brick.launch(runtime, config)
}
```

`AppId` собранного приложения — **детерминированный и читаемый**:
`"<toolId>-<screenId>-<h6>"`, где `h6` — шесть hex-символов некриптографического хэша
(FNV-1a) от `bindingId`. Одиночный экран без тулзы — `"<brick>-<h6>"`. Все экраны одного
аккаунта делят суффикс — в логах их видно группой: `inventory-new-3f9a1c`,
`inventory-history-3f9a1c`. Коллизия при регистрации (теоретическая) → суффикс удлиняется до 8;
детерминизм сохраняется, потому что вход тот же. Локальная сборка из QR уровня A: первая —
`<brick>` (сегодняшнее поведение, старые установки читаются как есть), вторая — `<brick>-2`.

Что из этого следует — таблица 02 §6, переписанная:

| Что | Было в 02 | Стало |
|---|---|---|
| Префикс хранилища `app.<id>.` | новый ключ `InstanceId` | **не меняется**: `id` собранного приложения уже уникален |
| `TopicStore`, `UnlockStore`, `HomeStore`, `SnapshotStore` | перевод на `InstanceId` | **не меняются** |
| `AppHandler` | `enabled/states/appRuntime/deepLinkHandler` на `InstanceId` | **не меняется**, кроме одного: конфиг запуска = `composition.config ⊕ transient` (это и так план 16 D50) и `createApp` получает порты |
| `RoutedPush`, deep link `unitool://app/<id>/…` | поле `instance`, экран выбора | **не меняются**: сервер знает `id` и пишет его в ссылку. Экран выбора нужен только для ссылки, назвавшей **кирпич** (`unitool://app/inventory-form/…`) при нескольких сборках — 02 D89 остаётся для этого случая |
| `AppRuntime.appId` | остаётся типом | = `id` собранного приложения. Кирпич видит его в логах и в `require()`; на поведение не влияет |
| `setup(ctx)` | «на экземпляр» — смена семантики | на собранное приложение, то есть **ровно как сегодня** — на запись реестра |
| Шелл, Home, каталог | `ShellDestination.App(InstanceId)` | без изменений; группировка по секции — `compositions[id].section` |
| `AppRegistry` | без изменений | **+ `unregister(id)`** (отзыв), `register` после старта уже допустим (10, п. 1) |
| `HostRuntimeFactory.createApp` | без изменений | + `provides: Map<ServiceKey<*>, Any>` с дефолтом `emptyMap()` — порты и `LinksService` |
| Контракт | «1, формально» | **1**: ни один тип, который видит кирпич, не изменился несовместимо |

Цена перевода из 02 §14 («полтора дня до синка») исчезает; вместо неё — обёртка, `unregister` и
параметр фабрики.

### 8.2. Три слоя вместо четырёх

```
AppConfigSpec.default   ⊕   screen.config   ⊕   transient (deep link, payload выхода, «Run with config»)
```

`account.shared` исчез: адрес, ключ и тенант — свойства коннектора, а не конфига. Слияние
поверхностное, по той же причине, что и раньше (16 D50). Цель G6 из 03 («сменить ключ на весь
аккаунт») достигается **лучше**: ключ меняется в одном коннекторе, и ни один кирпич даже не
перезапускается — коннектор читает секрет лениво при каждом вызове.

По нему админка **знает, что можно собрать**, и не выдаёт то, что устройство не соберёт. Опционально
— `configSchemaJson` на кирпич (JSON Schema, выведенная из дескриптора `kotlinx.serialization`), чтобы
админка рисовала форму конфига кирпича, не зная его кода. Это удобство, не требование; вопрос 53.

## 9. Применение документа

Алгоритм `ConfigSyncService.apply(document)` — продолжение 01 §6.4 и §13, с новыми исходами:

1. **Разбор** — всё или ничего. Не парсится → `SyncFailed(Malformed)`, состояние живо.
2. **Версия** — `version ≤ applied` → игнор (01 D68). `mode: patch` → 03 D95.
3. **Коннекторы аккаунта** — для каждого: вид есть в сборке и версия совместима → определение
   сохраняется в `BindingStore`; иначе коннектор помечен `unsupported`, и все экраны, которые на
   него ссылаются, получают `needs_update(connector_missing)`.
4. **Экраны** — для каждого `tools[].screens[]`:
   - кирпич есть в реестре, версия в диапазоне → иначе `needs_update(brick_missing | brick_too_old)`;
   - каждый порт из `brick.requires` привязан к коннектору **и** коннектор его умеет → иначе
     `needs_update(port_unbound | port_unsupported)`;
   - `exits` ссылаются на существующие `screenId` той же тулзы → иначе выход без назначения (не
     ошибка, но в отчёт);
   - вычислить `id`; собрать `Composition`.
5. **Diff с реестром сборок** по `id` внутри `source = binding:<bindingId>`:
   - новая → `register(ComposedApp)`, `unlock`, на Home если в `home` (01 §6.4 правила Home
     сохраняются: добавляет, чужое не убирает);
   - изменилась (конфиг, порты, оформление, версия кирпича) → `unregister` + `register`; если она
     открыта сейчас — плашка «перезапустить» (01 D72);
   - пропала → `disable` + `unregister` + `lock` + с Home; хранилище цело, если не `wipeOnRevoke`;
   - изменилось `state` → пометка плитки, открытая закрывается с экраном состояния (03 §3).
6. **Отчёт**: `SyncOutcome` из 01 §7.1 + `unsupported: List<Unsupported(id, reason)>` с причинами
   из шага 3–4 — ровно то, что нужно экрану «Обновите Unitool» и админке (`POST /device/ack`).

Всё это — над сегодняшними `AppRegistry`, `AppHandler`, `UnlockStore`, `HomeStore`. Ни одного
нового ключа.

## 10. Версии: шесть осей

| Ось | Где живёт | Вопрос | Кто проверяет | Не совпало |
|---|---|---|---|---|
| **Документа** `version` | документ, на привязку | «это новее применённого?» | синк | игнор (01 D68) |
| **Тулзы** `tools[].version` | документ | «какую редакцию сборки выдали» | никто; хранится и показывается | — |
| **Кирпича** `AppManifest.version` ↔ `brickVersion: ">=1.2"` | сборка Unitool ↔ документ | «достаточно ли нов код экрана» | шаг 4 применения | `needs_update(brick_too_old)` |
| **Порта** `records@1` | ключ порта; `requires` кирпича ↔ `ports` коннектора | «поймут ли друг друга кирпич и бэкенд» | шаг 4 | `needs_update(port_unsupported)` |
| **Коннектора** `kind@version` | сборка Unitool ↔ документ | «умеет ли эта сборка такой протокол» | шаг 3 | `needs_update(connector_missing)` |
| **Схемы конфига** `AppConfigSpec.schemaVersion` + `schemaVersion` внутри `config` | кирпич ↔ `screens[].config` | «поймёт ли кирпич эти ключи» | `AppConfigSpec.decode` — **уже реализовано** | `migrate` / `ignoreUnknownKeys` / `ConfigRejected` (D18) |

Плюс уже существующая **версия контракта хоста** (`minHostContract`, D14) — не трогается.
`configSchema` в конверте (03 §2) убран: один источник правды — `schemaVersion` внутри конфига.

**Ответы на вопросы владельца о версиях:**

- *«Если есть две разные версии тула — мы должны знать, какая используется».* Тулза — это сборка.
  Две версии = две сборки (у двух аккаунтов, или у одного до и после синка); реестр хранит на
  каждый экран `toolVersion`, `brickRequired`/`brickVersion`, коннектор с версией, версию документа
  и время применения; Service Menu показывает строку на экран. Это и есть «какая используется».
- *«Разные версии тулов тоже нужны».* Совместимые (minor) версии кирпича — один `AppId`, диапазон
  в документе. **Несовместимая (major) версия кирпича — новый `AppId`** (`inventory-form-2`): в
  одной сборке Unitool они сосуществуют, реестр это уже допускает, и документ явно говорит, какой
  из них собрать. То же с портами (`records@2`) и коннекторами. Это дороже «числа в манифесте», но
  единственный способ, при котором старый аккаунт не ломается в день релиза нового кирпича.

## 11. Уровни провижининга — один реестр сборок

Уровни A/B/C из 01 §1.1 остаются и получают общую единицу — сборку:

| Уровень | Источник сборки | `source` | Коннекторы |
|---|---|---|---|
| **0. Сборка Unitool** | DSL в `buildUnitool { compose(...) }` | `build` | объявлены там же |
| **A. QR с конфигом** | `app_activation` + необязательные `ports`/`connector` | `qr` | встроенный `local` или указанный в QR (`superizer-http` с адресом — без привязки) |
| **B. Файл-бандл** (16) | список сборок | `bundle` | из файла |
| **C. Сервер** | документ §8 | `binding:<id>` | из `account.connectors` |

Уровень 0 — новый и важный: **встроенные приложения Unitool тоже сборки**, той же формы. Калькулятор
— кирпич без портов, сборка тривиальна. Конвертер — первый кандидат на перевод на порт
(`RatesPort@1` + коннектор `http-json` с адресом Frankfurter в DSL): не ради него самого, а как
доказательство, что механизм работает **до** появления сервера (§15, этап 1). Пока не переведён —
живёт как сегодня, механизм его не трогает.

```kotlin
// Unitool — UnitoolHost.kt, эскиз
register(CalculatorApp())                                     // кирпич = сборка, как сегодня
register(ConverterApp())
connectors(SuperizerHttpConnector, LocalConnector)            // виды, доступные сборкам
compose(ConverterApp(), id = "currency-converter") {          // сборка уровня 0
    port(RatesPort.Key) to HttpJson(url = ConverterConfig.DEFAULT_RATES_URL)
}
```

## 12. Серверная сторона: «апишку предоставляем мы»

К 01 §11 (тикеты, устройства, документ, ack, gateway) добавляется ровно одно: **реализация
протокола `superizer-http`** поверх моделей сервера. Для Adminizer это слой с семью маршрутами
из §5.3, где `{collection}` и `{form}` отображаются на модели и права учётки (`access-graph`),
а `{kind}` для `lookup` — на справочники. Это и есть «мы с другой стороны предоставляем апишку»:
сервер адаптируется к кирпичу один раз и получает **все** кирпичи, которые есть и будут.

Админка получает **конструктор тулз**: список кирпичей из инвентаря устройств (§8.3), у каждого —
порты (нужно назначить коннектор), схема конфига (форма), выходы (куда ведут). Сборка сохраняется
как грант аккаунта и рендерится в документ. Обратная связь через `ack`: каких экранов устройство
не собрало и почему — админ видит `brick_too_old` и понимает, что нужен апдейт Unitool, а не
правка сборки.

## 13. Безопасность и приватность — что меняется относительно 01 §12

- **Allowlist по коннектору.** `NetworkService` собранного приложения — обёртка над хостовым с
  проверкой хоста запроса против объединения `hosts` его коннекторов (плюс `networkHosts` кирпича,
  если он без портов). Запрос мимо списка → `NetworkException(null, "host not allowed")` +
  событие. Политика приватности получает точную формулировку: «плитка X говорит с хостами Y —
  теми, что назвал сервер, к которому вы подключились».
- **Секрет не в конфиге и не в документе** (§6.3). Кирпич не имеет пути к нему по типам.
- **Документ подделан → худшее, что можно**: увести коннектор на чужой хост. Закрывается тем же
  TLS + device-токеном, что в 01, плюс (опционально, корпоративная сборка) allowlist доменов
  коннекторов в `SuperizerBuilder`. Подпись документа — по-прежнему D78, зарезервировано.
- **Кирпич стороннего автора** больше не риск для ключа аккаунта: он видит порты и свой конфиг.
- Play Data Safety: список хостов теперь **выводится из реестра сборок**, а не пишется по памяти —
  тот же урок, что с разрешениями из APK (`.ai-notes/push/01-fcm-implementation.md`).

## 16. Решения (продолжают нумерацию 03; там последнее — D101)

- **D102. Кирпич не знает сервера.** Всё внешнее — через порты, объявленные в `manifest.requires`.
  Кирпич с портами не использует `runtime.network` напрямую; адресов и ключей в его конфиге нет.
- **D103. Порт — это `ServiceKey` с версией в имени** (`records@1`). На границе порта — JSON,
  строки и `ByteArray`; результат — `Result`. Несовместимое изменение — новое имя.
- **D104. Четыре общих порта** (`records`, `submit`, `lookup`, `files`) в модуле `superizer:ports`;
  частные порты допускаются в модуле кирпича и приносят свой HTTP-класс.
- **D105. Коннектор — единственный владелец адреса, ключа и формата.** Объявляет `hosts`;
  секрет получает по ссылке из `BindingStore`, в документе и конфиге секретов нет.
- **D106. v1-коннектор — `superizer-http`: сервер реализует протокол кирпича.** Кодовые
  коннекторы под чужие API — по мере появления; скриптовый — по критериям 05.
- **D107. Экран — единица сборки и плитка.** Экран = кирпич × порты→коннекторы × конфиг ×
  оформление (`label`, `icon`, `accent`, `order`).
- **D108. Тулза — набор экранов с версией и состоянием**; единица выдачи и отзыва; подпись под
  секцией, не уровень навигации.
- **D109. Экраны связываются выходами.** Кирпич объявляет `exits`, сборка отображает их на
  `screenId`, хост даёт `LinksService` (необязательный `ServiceKey`). Кирпич не открывает
  приложения по `AppId`.
- **D110. Сборка регистрируется как приложение** (`ComposedApp`) с детерминированным читаемым
  `AppId` `<toolId>-<screenId>-<h6(bindingId)>`. Перевод хоста на `InstanceId` (02 D81–D82,
  D86–D87) **отменён**: хранилища, шелл, роутер, Home, разблокировка не меняются.
- **D111. Три слоя конфига:** `default ⊕ screen.config ⊕ transient`. Слоя `account.shared` нет
  (03 D91 отменён).
- **D112. Хост читает структуру сборки и не читает конфиг кирпича.** Уточнение D2 для документа v2.
- **D113. Шесть осей версий** (§10). `configSchema` в конверте убран (03 D96–D98 заменены).
  Несовместимая версия кирпича/порта/коннектора — новое имя, а не число.
- **D114. `needs_update` с причиной:** `brick_missing | brick_too_old | connector_missing |
  port_unbound | port_unsupported`. Причина едет в `ack` и показывается админу.
- **D115. `NetworkService` собранного приложения ограничен хостами его коннекторов.** Мимо списка
  — отказ и событие.
- **D116. Встроенные приложения — сборки уровня 0** через `compose {}` в DSL хоста; калькулятор —
  кирпич без портов; конвертер переводится на `RatesPort` как доказательство механизма.
- **D117. Идемпотентность записи — в сигнатуре порта** (`clientId`), чтобы декоратор `outbox`
  был возможен без участия кирпича.
- **D118. Реестр сборок (`CompositionStore`) — это `ProvisioningStore` из 16 с записью
  `Composition`.** Экспорт/импорт бандла — списком сборок с `source ≠ binding` (01 D79 в силе).
- **D119. Инвентарь при привязке — кирпичи с портами, схемами и выходами плюс коннекторы**
  (01 §6.2 заменён).
- **D120. Заметки 01–03 не удаляются и не переписываются**: 01 — справочник транспорта, 02/03 —
  история решений с пометкой статуса в шапке (правило версионирования — README).

## 19. Резюме в пяти строках

1. Кирпич — типизированный нативный экран с **портами** (абстрактными хендлерами) и без знания
   о сервере; порт — это уже существующий `ServiceKey`, контракт остаётся 1.
2. Коннектор — единственный владелец адреса, ключа и формата; v1 — `superizer-http`, где **сервер
   реализует протокол кирпича**.
