## 1. Вопрос владельца

«Положим, пользователь завёл на первом эпе один QR-код, а на втором эпе завёл второй QR-код, и
получается, что у него два разных эпа под разными аккаунтами на этом сервере. Это нормально — он
может на одном аккаунте быть в одном, на другом в другом. Тогда пуш приедет только в один аккаунт,
а второй окажется без изменений… Может быть, вообще всё переделать так: дать возможность
авторизации по QR-коду — авторизовался на сервере, и внутри приложения эта авторизация. Тогда у
тебя, например, приложение Daily Scope, ты заходишь, и там у тебя ещё разные тулзы. Ну то есть тоже
как-то неудобно, лучше экран один иметь наверху. Тогда получается, надо ввести новый параметр — это
секция: в секции Daily Scope юзер 1 вот эти тулзы, в секции Daily Scope юзер 2 вот эти тулзы. Они
должны иметь возможность выбирать между разными этими. Я бы сделал через то, что разрешить это
добавлять, но группировать их в одну с подписью, что вот это из этого сервера, а это из этого.»

Три отдельных утверждения, и все три принимаются:

1. **Две привязки к одному серверу под разными аккаунтами — законная ситуация**, а не ошибка.
2. **Пуш адресован конкретному аккаунту**; второй аккаунт от этого не меняется — и это правильно.
3. **Плоский экран с группировкой**, а не вложенность «приложение-учётка → внутри тулзы».

## 2. Ответ в одном абзаце

Сегодня всё в хосте ключуется одним `AppId`: Home, разблокировка, темы пушей, каталог, префикс
хранилища, снимок сессии, состояние в `AppHandler`. Этого больше не хватает: один и тот же тип
приложения может присутствовать на устройстве **дважды** — от двух учётных записей. Значит,
появляется второй ключ: **`InstanceId`** — одна выданная активация. Реестр активаций — это список
записей `ActivationRecord(instanceId, appId, section, config, audience, source, label, …)`, а
`AppId` остаётся тем, чем был: именем типа приложения в сборке. Записи группируются в **секции**:
одна секция на привязку (сервер + аккаунт) плюс одна локальная. Home показывает все плитки на
одном экране, под заголовками секций; заголовки появляются только тогда, когда секций больше
одной. Пуш несёт `bindingId`, поэтому обновление доезжает ровно в ту секцию, которой оно
адресовано.

```
Home
├─ (без заголовка, если секция одна)
│   Калькулятор   Конвертер
├─ ── Daily Scope · Иван Петров ─────────────
│   Задачи   Отчёты   Сканер
└─ ── Daily Scope · ООО «Ромашка» ───────────
    Задачи   Склад
```

Две плитки «Задачи» — это два `InstanceId` одного `AppId`, с разными конфигами, разными токенами и
разным хранилищем. Ничего общего, кроме кода.

## 3. Реестр активаций: из чего он состоит

```kotlin
// core/src/commonMain/kotlin/cx/m42/superizer/provisioning/ActivationRecord.kt

/** One *granted* app on this device. The registry is a list of these, keyed by [instanceId]. */
@Serializable
public data class ActivationRecord(
    val instanceId: InstanceId,
    /** Which app type in the build serves it. Several records may share one. */
    val appId: AppId,
    /** Which group it is shown under (§5). `SectionId.Local` for anything not from a server. */
    val section: SectionId,
    val config: AppConfig,
    val audience: String? = null,
    /** qr | bundle | binding:<bindingId> — who put it here, and therefore who may take it away (01, D70). */
    val source: ProvisioningSource,
    /** The server's name for this tile, when it has one; the manifest's otherwise. */
    val label: String? = null,
    val at: Long,
)

/**
 * One activation, not one app.
 *
 * A plain string, and deliberately derivable: `InstanceId(appId.value)` is what every single-tile
 * install has, so today's stored `["calculator"]` reads back unchanged and there is no migration.
 */
@JvmInline @Serializable
public value class InstanceId(public val value: String)

@Serializable
public sealed interface ProvisioningSource {
    @Serializable public data object Qr : ProvisioningSource
    @Serializable public data object Bundle : ProvisioningSource
    @Serializable public data class Binding(val bindingId: String) : ProvisioningSource
}

/** A group of tiles with one caption. One per binding, plus the local one. */
@Serializable
public data class Section(
    val id: SectionId,
    /** The product: "Daily Scope". From the binding's `serverLabel`. */
    val title: String,
    /** The account: "Иван Петров". Shown whenever two sections share a title — which is the case. */
    val subtitle: String? = null,
    val order: Int,
)
```

`ProvisioningStore` из заметки 16 (D49) становится реестром: `save/load/all/clear` работают по
`InstanceId`, плюс `byApp(appId): List<ActivationRecord>` и `bySection(id)`. Протокол по-прежнему в
`core`, реализация — в хосте (D49 не меняется, меняется только ключ).

## 4. Откуда берётся `InstanceId`

Детерминированно, потому что синк повторяется, а плодить дубликаты при каждом повторе нельзя.

| Источник | `instanceId` | Почему так |
|---|---|---|
| привязка (01) | `"<bindingId>.<appId>"` | синк идемпотентен: второй раз тот же документ даёт тот же ключ и перезаписывает ту же запись |
| QR уровня A, первая активация этого приложения | `appId.value` | совместимость: существующие установки не мигрируют, а «одно приложение — одна плитка» остаётся нормой |
| QR уровня A, приложение уже настроено | по умолчанию **заменяет** (16, D51); «Добавить как отдельную» в диалоге → `"<appId>.2"` | замена — то, чего человек ждёт, когда пересканирует обновлённый код; добавление — осознанный выбор |
| QR/бандл с явным `instance` в payload | это значение | сервер приложения может сам разделить «тестовый» и «боевой» контуры |
| бандл (16) | `instanceId` из файла | экспорт/импорт сохраняет раскладку целиком |

`bindingId` — локальный ключ привязки: `"<serverId>:<accountId>"`, где `accountId` приходит из
ответа `POST /enroll`. Это и есть ответ на «два QR одного сервера»: `serverId` совпадает,
`accountId` — нет, значит `bindingId` разный, значит секции две.

## 5. Секции на экране

- **Заголовок секции** = `title` привязки (продукт, например «Daily Scope»), **подпись** =
  `subtitle` (аккаунт: «Иван Петров», «ООО Ромашка»). Подпись обязательна к показу, когда два
  заголовка совпадают — а в сценарии владельца они совпадают всегда.
- **Локальная секция** («На устройстве») — всё, что не от сервера: встроенные приложения и
  настроенные вручную QR-ом. Всегда первая.
- **Если секция одна** (типичный Unitool: калькулятор и конвертер) — **заголовков нет вообще**.
  Человек, который никогда не сканировал привязку, не должен платить за существование секций
  ни одной строкой интерфейса.
- **Порядок**: локальная, затем привязки по времени подключения. Внутри секции — порядок Home
  (D48: человек добавляет плитки, долгое нажатие убирает).
- **Долгое нажатие** убирает плитку с Home, но запись в реестре остаётся — как сегодня. Вернуть —
  из каталога, и в каталоге плитки тоже сгруппированы по секциям.
- **Плитка**: имя приложения (или `label` от сервера), и подпись секции под ней **только тогда,
  когда тот же `appId` встречается больше одного раза** — иначе это шум.
- **Свернуть секцию** — стоит заложить в вёрстку (список из трёх секций по пять плиток длинный),
  но состояние «свёрнуто» хранить локально, не в реестре.

Отвергнутая альтернатива — прямо та, которую владелец назвал и сам забраковал: «приложение-учётка,
внутри которого тулзы». Причины записаны в §10.

## 6. Что становится «на экземпляр», а что остаётся «на тип»

Это и есть настоящая цена решения. Таблица — карта работ.

| Что | Ключ сегодня | Ключ после | Почему |
|---|---|---|---|
| `PrefsStorageService` префикс | `app.<appId>.` | `app.<instanceId>.` | **Главное.** Токен сессии Ивана не должен попасть в приложение «Ромашки» |
| `TopicStore` | `Map<appId, topics>`, тема `<appId>.<topic>` | `Map<instanceId, …>`, тема `<instanceId>.<topic>` | иначе оба экземпляра получают чужие темы |
| `UnlockStore` | `Set<AppId>` | `Set<InstanceId>` | право выдано аккаунту, а не типу приложения |
| `HomeStore` | `List<AppId>` | `List<InstanceId>` | две плитки одного типа |
| `SnapshotStore` (D16) | один ключ, один открытый | один ключ + `instanceId` внутри | восстанавливать надо тот же экземпляр |
| `AppHandler.enabled`, `states`, `appRuntime(id)`, `deepLinkHandler` | `AppId` | `InstanceId` | рантайм уровня приложения теперь на экземпляр (потоки пушей, фоновые подписки) |
| `RoutedPush` | на `AppId` | на `InstanceId` | адресация пуша (§7) |
| `settingsSections` | `List<Pair<AppId, …>>` | `List<Pair<InstanceId, …>>` | у двух учёток два блока настроек, и это правильно |
| `ShellDestination.App`, `HomeScreen.onOpen/onRemove`, `ShellCommand.OpenApp` | `AppId` | `InstanceId` | шелл открывает экземпляр |
| `AppRegistry`, `AppManifest`, `SuperizerApp`, `AppInstance`, `launch(runtime, config)` | `AppId` | **`AppId`, без изменений** | тип приложения — это код в сборке, экземпляров у него сколько угодно |
| `AppRuntime.appId` | `AppId` | **остаётся `AppId`** | приложение по-прежнему не знает, что оно одно из двух: оно видит свой `storage`, свой `push`, свой `config` — уже изолированные. Контракт остаётся **1** |

`setup(ctx)` начинает выполняться **на экземпляр**, а не на тип: он и сегодня вызывается один раз
на хост, приложение не может на это опираться, а подписки на темы и слушатели нужны каждому
экземпляру свои. `AppSetupContext` при этом не меняется ни на строку — меняется только то, сколько
раз хост его зовёт.

Оценка честно: это **самая инвазивная часть** всей затеи — правки в `AppHandler`, четырёх
хранилищах, роутере, шелле и двух экранах. Но она механическая (переименование ключа + расширение
там, где раньше было одно значение), и `InstanceId(appId.value)` для существующих данных делает её
безмиграционной.

## 7. Кому приезжает пуш

Ровно то, что сказал владелец: **в один аккаунт, второй не меняется.**

- Системный тикль несёт `bindingId` (а не только `serverId`): `{kind:host, type:config_changed,
  bindingId:"romashka-prod:acc-17", version:"18"}`. Хост синкает **только эту привязку**; вторая
  остаётся на своей версии и синкнется по своему расписанию.
- FCM-токен на устройстве один на все привязки — это свойство платформы, не наш выбор. Поэтому
  разделение обязательно делается полем в payload, а не «разными токенами».
- Тикль для неизвестного `bindingId` дропается (`UnknownBinding`, 01 §6.5). Это же защищает от
  ситуации «человек отвязался, а сервер ещё шлёт».
- Контентный пуш приложения (13) получает необязательное поле `instance`: есть — доставляется
  одному экземпляру; нет и экземпляр один — ему; нет и экземпляров несколько — **всем экземплярам
  этого типа по дороге данных**, а дорога экрана (тап) требует явного `instance`, иначе хост
  открывает выбор. Молча открыть «какой-нибудь» аккаунт — худшее, что можно сделать с двумя
  учётками.
- Отсюда следствие для сервера: `POST /apps/<appId>/push` (01 §11.3) принимает `audience`, и сервер
  Unitool сам разворачивает его в `(deviceToken, bindingId, instanceId)`. Сервер приложения об
  экземплярах не знает.

## 8. Ссылки и открытие: как снимается неоднозначность

`unitool://app/orders/returns` при двух экземплярах «Заказов» — неоднозначен. Правила, по убыванию
приоритета:

1. **Явный экземпляр** — `unitool://app/orders/returns?i=<instanceId>`. Так делают все ссылки,
   которые генерит сервер: он знает, кому шлёт.
2. **Открыт сейчас один из них** — ссылка идёт в него (человек в контексте этой учётки).
3. **Экземпляр один** — в него, без вопросов (обычный случай, ничего не меняется).
4. **Иначе** — экран выбора: «В какой учётной записи открыть «Заказы»?» со списком секций.

`apps.openApp(appId)` из другого приложения: экземпляр той же секции, если есть; иначе правило 3–4.
Приложение по-прежнему не знает слова «экземпляр» — оно просит тип, хост выбирает.

## 9. Что меняется на сервере

- Документ конфигурации (01 §6.4) — **на привязку**, то есть на аккаунт. `version` у каждой свой.
- В `enroll`-ответе добавляются `accountId`, `serverLabel` («Daily Scope») и `accountLabel`
  («Иван Петров») — из них строится подпись секции. Без них подпись — домен, что хуже, но работает.
- Повторная привязка **того же аккаунта** на том же устройстве — не вторая секция, а обновление
  существующей (дедуп по `bindingId`); сервер при этом выпускает новый `deviceToken` и гасит старый.
- «Запретить аккаунту получать два разных тула» — это **политика сервера**, и на устройстве её
  реализовывать не надо: даже при таком запрете два *разных аккаунта* на одном устройстве остаются
  законными, а значит, секции нужны в любом случае. Если владелец захочет запрет — он живёт в
  админке рядом с грантами и ничего не меняет в этой заметке.

## 10. Рассмотренные альтернативы и почему не они

| Вариант | Почему нет |
|---|---|
| **Вложенность: «приложение-учётка», внутри которого тулзы** (владелец назвал и сам забраковал) | лишний уровень навигации на каждом открытии; ломает D4 (один активный экземпляр) и всю модель плиток; тулза перестаёт быть приложением Superizer — становится экраном внутри чужого приложения, то есть теряет и deep link, и пуш, и Service Menu |
| **Переключатель аккаунта вверху (как в почте): один активный контекст** | прячет половину приложений за неочевидным меню; «хочу Задачи Ромашки и Отчёты Ивана рядом» становится невозможным; при этом переключатель всегда можно добавить **поверх** секций позже, если их станет много |
| **Запретить вторую привязку к тому же серверу** | не решает задачу (два *разных* сервера дают ту же неоднозначность), а живой сценарий — «я подрядчик у двух клиентов на одной платформе» — ломает |
| **Разделять по `audience` без понятия секции** | `audience` непрозрачен для хоста (01/16, D60) и сервер вправе его не присылать; подписи для человека из него не сделать |
| **Отдельные профили хоста (как профили браузера)** | переключение профиля = перезапуск всего; данные, язык, тема дублируются; для «двух учёток одного продукта» это из пушки по воробьям |

## 11. Крайние случаи

| Ситуация | Поведение |
|---|---|
| один и тот же аккаунт, второй QR | обновление привязки, не вторая секция (дедуп по `bindingId`) |
| два аккаунта, одинаковый `appId`, одинаковый конфиг | всё равно два экземпляра: права и отзыв у них разные |
| секция отозвана (01 §9.4) | уходят все её экземпляры и плитки; локальные и чужие — не тронуты |
| в секции не осталось ни одного экземпляра | секция скрыта с Home, но привязка жива (сервер может выдать снова); в Settings карточка остаётся |
| осталась одна секция | заголовки исчезают — экран возвращается к сегодняшнему виду |
| приложение открыто, его экземпляр отозван | закрывается с «доступ отозван» (01 §13) — закрывается именно экземпляр, соседний продолжает работать |
| `reset` в Service Menu | стирает **экземпляр**: его хранилище, темы, снимок, запись реестра. Второй экземпляр того же типа цел |
| лимит | не больше 10 экземпляров одного типа и 16 секций; превышение — `UnsupportedApp`-подобное событие и строка в логе, а не молчаливый рост |
| старая установка (данные до этой работы) | читается как есть: `InstanceId == appId`, локальная секция, `source = Qr` |
| экспорт бандла (16) | экспортируются только `source = Qr/Bundle`; выданное сервером — нет (01, D79), и экран об этом говорит: «Приложения, выданные сервером, не переносятся — подключите второе устройство QR-кодом» |

## 12. Решения (продолжают нумерацию 01; там последнее — D80)

- **D81. Реестр активаций ключуется `InstanceId`, а не `AppId`.** `AppId` — тип приложения в
  сборке; `InstanceId` — одна выданная активация. Одному типу может соответствовать несколько
  экземпляров.
- **D82. `InstanceId` детерминирован**: `"<bindingId>.<toolId>"` для серверных (уточнено в заметке
  03, D100: единица выдачи — тулза, а не тип приложения; до неё здесь было `<appId>`), `appId` для
  первой локальной активации. Повторный синк перезаписывает, а не плодит.
- **D83. Секция — единица группировки**: одна на привязку (сервер + аккаунт) плюс локальная.
  Заголовок = продукт, подпись = аккаунт; подпись обязательна при совпадении заголовков.
- **D84. Один экран, никакой вложенности.** Плитки всех секций живут на Home; секции — это
  заголовки, а не уровни навигации.
- **D85. Заголовки секций не показываются, когда секция одна.** Сегодняшний Unitool выглядит ровно
  как сегодня.
- **D86. Изоляция данных — по экземпляру**: префикс хранилища, темы пушей, снимок сессии,
  разблокировка, Home, рантайм уровня приложения.
- **D87. Контракт приложения не меняется** (`VERSION = 1`): `AppRuntime.appId` остаётся типом,
  приложение не знает, что оно одно из двух. `setup(ctx)` вызывается на экземпляр.
- **D88. Адресация пуша — по `bindingId`** для системных и по необязательному `instance` для
  контентных. Без `instance`: данные — всем экземплярам, экран — выбор.
- **D89. Разрешение ссылок**: явный `?i=`, затем открытый сейчас, затем единственный, затем экран
  выбора. Молча выбирать учётку нельзя.
- **D90. Ограничение «два тула на аккаунт» — политика сервера**, не устройства: разные аккаунты на
  одном устройстве законны в любом случае.

## 13. Тесты, которые это доказывают

- `twoBindingsToOneServerAreTwoSections` — два `enroll` на один `serverId` с разными `accountId`.
- `theSameAccountEnrolledTwiceIsOneSection`.
- `twoInstancesOfOneAppKeepSeparateStorage` — запись через `runtime.storage` в одном не видна в
  другом (самый важный тест: это утечка кредов, если он красный).
- `aTickleUpdatesOnlyItsBinding` — вторая привязка остаётся на прежней версии.
- `resetErasesOneInstanceAndLeavesTheOther`.
- `revokingASectionLeavesLocalAppsAlone` (вместе с 01 `aRevokeLeavesQrProvisionedAppsAlone`).
- `aLinkWithoutAnInstanceAsksWhenThereAreTwo`, `aLinkWithoutAnInstanceJustOpensWhenThereIsOne`.
- `homeShowsNoSectionHeadersWithOneSection` — скриншот сегодняшнего вида без изменений.
- `anOldInstallReadsAsOneLocalSection` — миграции нет: старые ключи парсятся как `InstanceId`.
- `aSecondSyncDoesNotDuplicateTiles` — детерминированность D82.

## 14. Влияние на план из заметки 01

Шаг 1 (`core`) вырастает: `InstanceId`, `ActivationRecord`, `Section`, переключение
`ProvisioningStore` на новый ключ. Появляется новый шаг между 1 и 2 — **«перевести хост на
`InstanceId`»** (`AppHandler`, четыре хранилища, `RoutedPush`, шелл): день-полтора, и его лучше
сделать **до** синка, потому что применять документ в мир, где ключ ещё `AppId`, — значит написать
код, который потом выбрасывается. Шаг 5 (UI) вырастает на секции в Home и каталоге и на экран
выбора экземпляра: плюс полдня.

Итог: то, что в 01 оценивалось как «~3 дня без сервера», становится «~4,5 дня». Это честная цена
двух аккаунтов на одном устройстве, и платить её надо **до** первого релиза с привязкой: сменить
ключ реестра, когда на устройствах уже лежат записи, заметно дороже.
