>

Дата: 2026-09-22. Третья заметка того же дня, после четвёртого уточнения владельца. Читать после
`01-server-binding-and-config-push.md` и `02-activation-registry-and-sections.md`. **Идея, не план.**

Она делает две вещи: собирает **цели** (что должно получиться, и по какому признаку мы это
узнаем) и правит модель конфига из 01 — теперь первичен **конфиг аккаунта на внешнем сервере**, а
не конфиг отдельного приложения. Это прямо из формулировки владельца: «вообще конфиг одного app не
нужен; нужен конфиг типа внешнего приложения, а функции эппы — то, что есть в наличии у этого
приложения; Unitool может прочитать этот конфиг и сказать: ага, у меня есть такая тулза».

## 1. Цели и признак готовности

Восемь целей. Для каждой — что делает оператор, что видит человек, и **чем мы проверяем**, что
работает (это же список ручных проверок перед первым релизом).

| # | Цель | Оператор делает | Человек видит | Проверяем |
|---|---|---|---|---|
| **G1** | Отозвать / просрочить один аккаунт | ставит `expired` (или истекает срок) | плитки этой секции помечены «Доступ истёк», внутрь не пускает, данные целы | плитка серая через ≤10 с после тикля; API возвращает 401 независимо; после `active` доступ вернулся **без нового QR** |
| **G2** | Выкатить новую фичу тем, кто уже есть | поднимает флаг в конфиге аккаунта/тулзы | фича появилась при следующем открытии тулзы (или сразу с плашкой «Настройки обновлены») | флаг `returns:true` → кнопка «Возвраты»; версия документа в Service Menu выросла |
| **G3** | Догнать тех, кого пуш не разбудил | ничего | при открытии Unitool догоняет молча | выгрузить процесс, изменить конфиг, запустить — новая версия применилась без пуша |
| **G4** | Поменять конфиг уже выданных тулз позже | правит гранты | адрес/ключ/настройки поменялись | тулза ходит на новый адрес после перезапуска экземпляра |
| **G5** | Поменять **часть** конфига | правит одно поле | остальное не тронуто | правка одного ключа не сбрасывает остальные и не трогает соседние тулзы |
| **G6** | Сменить то, что общее для всего аккаунта (ключ API, адрес, срок) | правит аккаунт | **все** тулзы аккаунта поехали на новый ключ | один ключ в одном месте — три тулзы обновились |
| **G7** | Выдать человеку сразу набор тулз одним QR | добавляет гранты аккаунту | после одного сканирования появилась секция с несколькими плитками | один QR → 3 плитки; добавили четвёртую на сервере → приехала без сканирования |
| **G8** | Понимать, какая версия тулзы и конфига используется | смотрит в админке | — | Service Menu показывает по каждому экземпляру: версия документа, версия тулзы, схема конфига, версия приложения в сборке |

Две вещи, которые **не** являются целями и это надо проговорить: (а) клиентский отзыв не является
защитой — настоящая защита в том, что API отвечает 401 (D94); (б) «выкатить новую фичу» здесь
всегда означает *включить* то, что уже есть в сборке, — код не доставляется (01 §9.1).

## 2. Сдвиг модели: конфиг аккаунта первичен

В 01 §6.4 документ был плоским: `apps[]`, у каждого — полный конфиг с адресом сервера и кредами
внутри. При двух-трёх тулзах одного аккаунта это означает три копии одного ключа API, и цель G6
(«истёк ключ на весь сервер») превращается в «не забудь поправить в трёх местах».

**Новая форма — два уровня:**

```json
{ "schemaVersion": 1, "type": "host_config", "version": 42, "mode": "full",
  "bindingId": "dailyscope-prod:acc-17",

  "account": {
    "label": "Daily Scope",
    "userLabel": "Иван Петров",
    "state": "active",                       // active | expired | suspended
    "expiresAt": 1761000000000,
    "shared": {                              // общее для всех тулз аккаунта
      "baseUrl": "https://api.dailyscope.example",
      "apiKey": "ds_live_…",
      "tenant": "acc-17"
    }
  },

  "tools": [
    { "toolId": "tasks",  "appId": "ds-tasks",  "version": "1.4.0", "configSchema": 2,
      "state": "active", "visible": true, "label": "Задачи",
      "requiresAppVersion": "0.4.0",
      "config": { "features": { "returns": true }, "defaultProject": "p-9" } },

    { "toolId": "reports", "appId": "ds-reports", "version": "1.1.0", "configSchema": 1,
      "state": "expired", "visible": true, "label": "Отчёты",
      "reason": "Оплата не поступила" },

    { "toolId": "scanner", "appId": "ds-scanner", "version": "2.0.0", "configSchema": 1,
      "state": "active", "visible": true, "requiresAppVersion": "0.9.0" }   // нет в этой сборке → needs_update
  ],

  "home": ["tasks"],
  "notice": { "title": "Появился раздел «Возвраты»", "body": "Откройте «Задачи»" }
}
```

**Конфиг, который получает приложение, собирается хостом из четырёх слоёв:**

```
AppConfigSpec.default   ⊕   account.shared   ⊕   tool.config   ⊕   transient (deep link / «Run with config»)
      что умеет код          что общее у аккаунта   что своё у тулзы        что разово
```

Слияние поверхностное — то же правило и по той же причине, что `AppConfigSpec.mergeWithDefault`
в сегодняшнем коде и `overlaidWith` из 16 (D50): при глубоком слиянии вложенный объект невозможно
очистить. Хост при этом **по-прежнему не читает содержимое**: он склеивает JSON-объекты, не
понимая ни одного ключа. Читает он только конверт — `appId`, `state`, `visible`, `label`,
`version`, `requiresAppVersion`. Это и есть точная формулировка «Unitool читает конфиг и понимает,
какие у него есть тулзы»: **конверт — хосту, содержимое — приложению**, и D2 остаётся целым.

`toolId` ≠ `appId`: первое — имя тулзы у продукта (может быть выдано дважды с разными настройками),
второе — тип приложения в сборке Unitool. `InstanceId` из заметки 02 строится как
`"<bindingId>.<toolId>"` — по тулзе, а не по приложению, иначе «две тулзы на одном коде» не
различить.

## 3. Состояния доступа: G1 целиком

**Состояние — поле конверта, а не ключ внутри конфига (D92).** Внутри конфига хост его не увидел
бы, а решение «пускать или нет» принимает именно хост.

| Состояние | Что с записью | Что с плиткой | Что при открытии |
|---|---|---|---|
| `active` | есть | обычная | открывается |
| `expired` | есть, конфиг сохранён | помечена «Доступ истёк» | **не открывается**: экран хоста с `reason` от сервера и кнопкой «Проверить снова» (синк) |
| `suspended` | есть | помечена «Приостановлено» | то же, другой текст |
| нет в документе (revoked) | удаляется (01, D70) | исчезает | — |

Почему именно так, а не «пускать внутрь и пусть приложение показывает ошибку от API»: приложение
с просроченным ключом получит 401 на каждом экране, нарисует три разных сообщения об ошибке, а
человек так и не поймёт, что дело в подписке. Один экран хоста с текстом сервера — честнее. (Есть
и обратный довод: тулза с офлайн-кэшем полезна и без сети — это вопрос 45.)

**Возврат доступа — без нового QR.** Запись, конфиг, хранилище и подписки остаются на месте; новый
документ со `state: active` возвращает всё в строй. Это ровно то, что просил владелец: «дать
возможность заходить надо потом». Отдельная кнопка «Проверить снова» на экране просрочки нужна для
случая «оплатил только что и не хочет ждать следующего синка».

**Срок без сети.** `expiresAt` даёт хосту право пометить тулзу просроченной **самостоятельно**,
когда время вышло, а сервер недоступен. Без этого отключённое от сети устройство живёт с
бессрочным доступом. Но часы на устройстве — не доверенный источник, поэтому: локальная
экспирация лишь помечает плитку и пускает в «Проверить снова», а настоящая точка отказа — API.

## 4. Частичные изменения: G4 и G5

«Поменять часть конфига» бывает трёх видов, и только один из них требует кода на устройстве.

1. **Оператор меняет одно поле** — сервер пересобирает документ целиком, устройство заменяет
   целиком. Никакой «частичности» на клиенте не нужно, и это **режим по умолчанию** (`mode: "full"`).
   Цель G5 достигается здесь, без единой строчки про патчи.
2. **Документ-патч** (`mode: "patch"`, D95) — для больших аккаунтов, где гонять весь документ
   дорого. Семантика — JSON Merge Patch (RFC 7386): объект сливается поверх, `null` **удаляет**
   ключ. Обязателен `baseVersion`: применяем, только если он равен применённой версии, иначе —
   игнорируем патч и делаем полный синк. Так потерянный промежуточный патч не даёт тихо
   разъехавшееся состояние.
3. **Микро-патч прямо в пуше** — **не делаем** (01, D65): 4 КБ, порядок, холодный старт, доверие.

Отдельный слой «устройство-специфичного» конфига (человек сам что-то настроил внутри тулзы) —
не в конфиге вообще, а в `runtime.storage` приложения: конфиг принадлежит серверу и переписывается,
пользовательские настройки принадлежат приложению и переживают обновление. Это разграничение стоит
написать в документации для авторов приложений одной строкой, иначе первый же автор положит
пользовательский выбор в конфиг и потеряет его на первом синке.

## 5. Версионирование: четыре независимые оси (G8)

Путаница здесь дороже всего, поэтому — таблица, кто на какой вопрос отвечает.

| Ось | Где живёт | На какой вопрос отвечает | Что делает хост |
|---|---|---|---|
| **Версия документа** `version` | документ, на привязку (01, D68) | «это состояние новее применённого?» | монотонно; `≤ applied` — игнор |
| **Версия тулзы** `tool.version` | документ, на тулзу | «какую редакцию тулзы нам выдали» | хранит в реестре, показывает; **не** интерпретирует |
| **Требование к сборке** `requiresAppVersion`, `minHostVersion` | документ, на тулзу | «потянет ли эта сборка Unitool» | сравнивает с `AppManifest.version` и `HostInfo.version`; не тянет → состояние `needs_update` |
| **Схема конфига** `configSchema` / `schemaVersion` внутри `config` | документ + сам конфиг | «поймёт ли приложение эти ключи» | ничего: это дело `AppConfigSpec.decode` — **уже реализовано** (`schemaVersion` + `migrate` + `ignoreUnknownKeys`) |

Матрица совместимости, построчно:

| Ситуация | Поведение |
|---|---|
| сервер требует `0.4.0`, в сборке `0.3.1` | тулза в состоянии `needs_update`, плитка с бейджем «Обновите Unitool», событие `UnsupportedApp`; **не запускается** — тулза, запущенная на слишком старом коде, ломается посреди работы, а не на входе |
| сервер требует `0.4.0`, в сборке `0.5.0` | работает; старший код обязан читать младший конфиг |
| `configSchema: 2`, приложение знает 1 | незнакомые ключи игнорируются (`ignoreUnknownKeys = true` уже стоит) → работает в урезанном виде; событие в лог |
| `configSchema: 1`, приложение знает 2 | `AppConfigSpec.migrate(from = 1, raw)` — механизм есть, ничего нового не нужно |
| конфиг не декодируется | `ConfigRejected` + `fallbackToDefault` (D18) — как сегодня, молчания нет |
| две версии одной тулзы у двух аккаунтов | это два экземпляра (02): у каждого своя `tool.version` в реестре; работают независимо |
| `appId` вообще нет в сборке | `needs_update` для всей тулзы, в отчёте синка — в `unsupported` (01, D71) |

**Что хранит реестр на экземпляр** (и показывает Service Menu — это и есть ответ на «какая версия
сейчас используется»): `appliedDocumentVersion`, `toolVersion`, `configSchema`, `appVersion`
(из манифеста сборки), `lastAppliedAt`, `state`. Одна строка на экземпляр в Service Menu и в
карточке привязки в Settings.

## 6. Цикл целиком, по шагам

**G1 — истёк ключ аккаунта.**
```
админ: аккаунту acc-17 → expired (или наступил expiresAt)
 → документ v42 → v43, account.state = expired
 → тикль {kind:host, type:config_changed, bindingId:"dailyscope-prod:acc-17", version:"43"}
 → синк → все тулзы секции переводятся в expired (конфиг и данные не трогаются)
 → плитки помечены; открытая тулза закрывается с экраном «Доступ истёк: <reason>»
 → API продолжает отвечать 401 независимо от всего этого (настоящая защита)
 …позже: админ → active → v44 → тикль → плитки снова обычные, конфиг тот же, QR не нужен
```

**G2 + G3 — новая фича, с пушем и без.**
```
админ: features.returns = true у тулзы tasks → v44
 ├─ процесс жив: тикль → синк → конфиг обновлён
 │    ├─ тулза закрыта → появится при следующем открытии (D72)
 │    └─ тулза открыта → плашка «Настройки обновлены — перезапустить»
 └─ процесс выгружен (тикль потерян): при следующем запуске Unitool — синк на старте → то же самое
```

**G6 — сменился ключ API на весь аккаунт.**
```
админ: account.shared.apiKey = новый → v45 → тикль → синк
 → хост пересобирает конфиг КАЖДОЙ тулзы секции (слой account.shared) → три экземпляра получили новый ключ
 → открытые — плашка; закрытые — при следующем открытии
```

**G7 — один QR, набор тулз, потом ещё одна.**
```
QR привязки → enroll → первый синк → секция «Daily Scope · Иван Петров» с тремя плитками
 …через неделю админ добавил грант «Склад» → v46 → тикль → четвёртая плитка. Сканировать нечего.
```

## 7. Синк при открытии: что именно считается «открытием» (G3)

- **Старт процесса** — синк всегда, в фоне, не блокируя первый экран.
- **Возврат в foreground** — если с последнего синка прошло больше `syncMinIntervalSec` (по
  умолчанию 300).
- **Тап по плитке** — синк **только** если TTL истёк, с коротким таймаутом (≈1,5 с) и **не
  блокируя открытие**: тулза открывается на том конфиге, что есть, а приехавший следом новый даёт
  плашку. Единственное исключение — известное состояние `expired`/`needs_update`: тогда открытия
  нет вовсе, показывается экран состояния.
- **Кнопка «Обновить»** в карточке привязки — всегда.

Правило, которое стоит защищать: **синк никогда не заставляет человека ждать.** Приложение,
которое «думает» три секунды при каждом тапе из-за сети, люди перестают открывать.

## 8. Что из этого меняет заметки 01 и 02

- **01 §6.4** (плоский `apps[]`) заменяется двухуровневым документом из §2 этой заметки.
- **01 D67** (документ — желаемое состояние) остаётся, но получает `mode: full|patch` (D95).
- **01 §9.4**: к «нет в документе → отзыв» добавляются состояния `expired`/`suspended`, при которых
  запись **не** удаляется.
- **02 D82**: `InstanceId` строится по `toolId`, а не по `appId`.
- Оценка растёт примерно на день: слияние слоёв, состояния, экран состояния, четыре версии в
  реестре и их показ.

## 9. Решения (продолжают нумерацию 02; там последнее — D90)

- **D91.** Первичен **конфиг аккаунта**; документ = `account` + `tools[]`. Конфиг приложения
  собирается хостом как `default ⊕ account.shared ⊕ tool.config ⊕ transient`, поверхностным
  слиянием, без чтения содержимого.
- **D92.** Доступ — **поле конверта** (`state: active | expired | suspended`), а не ключ конфига.
  Хост не пускает в неактивную тулзу и показывает экран с `reason` от сервера.
- **D93.** `expired` не удаляет ни запись, ни конфиг, ни данные: возврат доступа — новый документ,
  без нового QR.
- **D94.** Клиентский отзыв — UX, а не безопасность. Точка отказа — API сервера.
- **D95.** По умолчанию документ полный; `mode:"patch"` — JSON Merge Patch с обязательным
  `baseVersion`, несовпадение → полный синк. Патчей в пуше нет.
- **D96.** Четыре оси версий (§5), каждая отвечает на свой вопрос; смешивать их в одно число
  нельзя.
- **D97.** `requiresAppVersion` / `minHostVersion` не выполняется → `needs_update`, запуска нет.
- **D98.** Реестр хранит на экземпляр: версию документа, версию тулзы, схему конфига, версию
  приложения в сборке, состояние и время применения; Service Menu их показывает.
- **D99.** Синк не блокирует открытие; блокирует только известное неактивное состояние.
- **D100.** `toolId` — единица выдачи, `appId` — тип кода. `InstanceId = "<bindingId>.<toolId>"`.
- **D101.** Пользовательские настройки внутри тулзы живут в `runtime.storage`, а не в конфиге:
  конфиг принадлежит серверу и перезаписывается.

## 10. Чем проверяем (стенд)

Минимум, чтобы всё восемь целей можно было пощупать руками до релиза:

- **Фейковый сервер в `testing`** с переключателями: `expire(account)`, `grant(tool)`,
  `revoke(tool)`, `setFeature(tool, key, value)`, `bumpVersion()`, `patch(...)`, `requireAppVersion(...)`.
  Все сценарии §6 прогоняются как тесты, без сети и без Firebase.
- **Тесты:** `anExpiredAccountBlocksLaunchAndKeepsData`, `reactivationNeedsNoNewQr`,
  `sharedKeyChangeReachesEveryToolOfTheAccount`, `aPatchWithAStaleBaseVersionFallsBackToFullSync`,
  `aToolRequiringANewerBuildIsNeedsUpdateNotACrash`, `anOlderConfigSchemaIsMigrated`,
  `anUnknownConfigKeyDoesNotBreakLaunch`, `openingSyncsButNeverBlocks`,
  `theRegistryReportsFourVersionsPerInstance`, `aLostTickleIsCaughtUpOnNextStart`.
- **Ручной чек-лист** — таблица §1, колонка «Проверяем», на настоящем телефоне: с пушем, без пуша
  (выключить Google Play Services), в самолётном режиме, после `force stop`.

## 11. Вопросы владельцу (продолжают нумерацию 02; там последний — 44)

45. **Просроченная тулза — совсем не открывается или открывается «только чтение»** на кэше? По
    умолчанию — не открывается (§3); read-only требует участия приложения и контрактного поля.
46. **Кто задаёт срок** — сервер присылает `expiresAt`, или только состояние? По умолчанию — и то,
    и другое: состояние авторитетно, `expiresAt` даёт офлайн-пометку.
47. **Нужен ли `mode:"patch"` в v1** — или полного документа хватит? По умолчанию — хватит (D95,
    пункт 1), патч добавим, когда документ перестанет быть маленьким.
48. **Может ли одна тулза быть выдана дважды одному аккаунту** (например, два проекта Daily Scope)?
    Модель это позволяет (`toolId` разный, `appId` один); нужно ли — вопрос.
49. **Что делает `needs_update`-плитка при тапе** — ведёт в Play/на страницу обновления или просто
    показывает текст? По умолчанию — текст + кнопка «Обновить приложение» со ссылкой от сервера.
50. **Показывать ли версии человеку** (в Settings) или только в Service Menu? По умолчанию — только
    в Service Menu; в Settings — «обновлено 5 минут назад».
