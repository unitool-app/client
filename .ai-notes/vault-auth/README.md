## 1. Что сейчас и почему это слабо

«Мастер-пароль» из вопроса владельца — это код-пароль iPhone. Своего пароля у Unitool нет (D129).

Сегодня две независимые слабости:

1. **Код-пароль открывает всё.** Замок хоста на iOS — `LAPolicyDeviceOwnerAuthentication`
   (`superizer/host/.../IosDeviceAuthenticator.kt`): Face ID, а при неудаче — код-пароль. На
   Android — `BIOMETRIC_WEAK | DEVICE_CREDENTIAL`. Кто подсмотрел код (классическая кража
   iPhone в баре), тот открывает 2FA и «Пароли». Более того, с кодом он заходит в Настройки и
   добавляет **своё** лицо в Face ID.
2. **Замок — занавес, а не шифрование (D128).** Ключ хранилища:
   - iOS — P-256 в Secure Enclave только с `kSecAccessControlPrivateKeyUsage`
     (`services/vault/.../IosKeychainVault.kt`);
   - Android — AES-GCM в Keystore без `setUserAuthenticationRequired`
     (`AndroidKeystoreVault.kt`).

   Оба расшифровывают молча, пока телефон разблокирован. Face ID только решает, показать ли
   экран. Код внутри процесса (jailbreak/root, Frida, вредонос) зовёт `vault.open()` мимо занавеса.

## 2. Короткий ответ

1. **Два яруса секретов в хосте** (D569). Обычный — как сейчас, молчаливый ключ. **Охраняемый** — для
   приложений с `LockPolicy.Required` (2FA, «Пароли»): их `runtime.secrets` шифрует отдельный
   ключ данных (DEK), а DEK заперт ключом чипа, который **без свежей биометрии не работает вообще**.
2. **Только биометрия, код-пароль не открывает** (D570). iOS — `.biometryCurrentSet`, Android —
   `AUTH_BIOMETRIC_STRONG` без `DEVICE_CREDENTIAL`.
3. **Сменили набор лиц/пальцев — ключ уничтожен** (D571). Это закрывает сценарий «знаю код →
   добавил своё лицо → открыл»: ключ чипа исчезает, остаётся только слот восстановления.
4. **Слот восстановления обязателен** (D137, D575). По умолчанию — случайный код 128 бит, показанный
   один раз (вопрос 243).
5. **Одна биометрия на открытие, не две** (D572). Промпт замка хоста и есть разрешение ключу:
   на iOS — тот же `LAContext`, на Android — `CryptoObject`.
6. **Приложения не меняются** (D574). Ни 2FA, ни «Пароли» не знают о ярусах: хост решает по
   манифесту, хост показывает экран восстановления.

## 3. От чего защищает

| Кто | Сегодня | После |
|---|---|---|
| Подсмотрел код-пароль, украл телефон | открывает 2FA и «Пароли» кодом | не открывает: код ключу не подходит |
| То же + добавил своё лицо/палец | открывает | ключ чипа уничтожен; нужен код восстановления, которого у вора нет |
| Root/jailbreak/Frida в процессе, телефон разблокирован | `vault.open()` мимо занавеса | охраняемые секреты не расшифровать без живой биометрии владельца |
| Копия файлов, бэкап | закрыто (ключ в чипе) | закрыто |
| Взял телефон, когда 2FA открыта | видит | видит, пока не сработает запирание (D131, idle 1 мин) — не меняется |
| Принуждение («приложи лицо») | открывает | открывает. Биометрия не защищает от принуждения; честно пишем это |

## 4. Устройство

### 4.1. Ярусы в `HostSecrets` (Superizer)

- `HostSecrets(ordinary: SecretVault?, guarded: GuardedVault?)`. `forApp(appId)` выбирает ярус по
  манифесту: `protection.lock == Required` → охраняемый, иначе обычный (D569).
- Хост по-прежнему не знает шифров (D181): `GuardedVault` — интерфейс в core, реализация в
  `services/vault` Unitool.
- Префиксы в prefs не меняются (`secret.<id>.`), меняется только формат значения: `g1:` —
  запечатано DEK. `reseal`/`counts`/сброс (D35) работают по-прежнему.
- `HostKeys.HEARTBEAT` и прочие секреты хоста остаются в обычном ярусе: хост должен читать их без
  человека.

### 4.2. Конверт (Unitool, `services/vault`)

```
prefs "vault.guarded" = JSON {
  "v": 1,
  "slots": [
    { "type": "device",   "wrapped": "<b64>" },                      // DEK под ключом чипа
    { "type": "recovery", "kdf": "hkdf-sha256", "salt": "<b64>",
      "wrapped": "<b64>" } ] }                                       // DEK под кодом

значение секрета = "g1:" + Base64(nonce | ChaCha20-Poly1305(DEK, plaintext, aad = "g1:" + key) | tag)
```

- DEK — 32 случайных байта, один на хост, не на приложение. ChaCha20-Poly1305 уже есть в
  `kit.crypto` и сверен с JDK.
- Тип слота входит в AAD обёртки, имя ключа prefs — в AAD значения: слоты и значения нельзя
  переставить друг с другом.
- Почему DEK со слотами, а не ключ чипа напрямую: ключ чипа — единственное, что может пропасть
  (D571). DEK переживает его пропажу через `recovery`.

### 4.3. iOS

- Ключ: P-256 в Secure Enclave, `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`, флаги
  `.privateKeyUsage | .biometryCurrentSet`. Тег `cx.m42.services.vault.guarded` — отдельный от
  нынешнего ключа.
- Обёртка DEK — ECIES тем же алгоритмом, что сейчас (`…CofactorVariableIVX963SHA256AESGCM`).
  Запечатать может кто угодно (публичный ключ), открыть — только с биометрией.
- Одна биометрия (D572): замок хоста для охраняемого приложения вызывает
  `LAContext.evaluatePolicy(LAPolicyDeviceOwnerAuthenticationWithBiometrics)`, и **этот же**
  `LAContext` уходит в `SecKeyCreateDecryptedData` через `kSecUseAuthenticationContext`. Keychain
  принимает уже оценённый контекст без второго запроса. Проверить на живом iPhone — риск R1.
- `localizedFallbackTitle = ""` — кнопки «Ввести код-пароль» на листе нет.
- Блокировка Face ID после 5 неудач (`LAErrorBiometryLockout`): пишем «Face ID заблокирован.
  Разблокируйте iPhone кодом-паролем и попробуйте снова». Код снимает блокировку **биометрии**, но
  ключ сам по-прежнему ждёт лицо. Это не дыра: код открывает возможность попробовать лицо ещё раз,
  а не ключ.
- Сняли код-пароль на iPhone — iOS сама удаляет элементы `WhenPasscodeSet`. Это та же ветка, что
  смена лиц: `NeedsRecovery`.

### 4.4. Android

- Ключ: AES-256-GCM, `setUserAuthenticationRequired(true)`, `setInvalidatedByBiometricEnrollment(true)`,
  `setUnlockedDeviceRequired(true)` (API 28+), StrongBox где есть, иначе TEE.
  - API 30+: `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)`;
  - API 24–29: `setUserAuthenticationValidityDurationSeconds(-1)` — то же «на каждую операцию».
- Окна в 30 с из §8 нет: на каждое отпирание `CryptoObject(cipher)` в `BiometricPrompt` хоста
  (D572). Окно разрешило бы и разблокировку экрана PIN-ом, если та случилась в пределах окна.
- Промпт — `BIOMETRIC_STRONG`. Лицо Class 2 (большинство Android) **не подходит**, остаётся
  отпечаток. На экране включения это сказано.
- `KeyPermanentlyInvalidatedException` (новый палец, снятая блокировка экрана) → `NeedsRecovery`.

### 4.5. Superizer: что меняется в контракте

- `AuthStrength.BiometricOnly` — новое значение. На iOS — политика `…WithBiometrics`, на Android —
  `BIOMETRIC_STRONG` без `DEVICE_CREDENTIAL` (D570).
- `DeviceAuthenticator.authenticate(…, binding: AuthBinding?)`. `AuthBinding` — платформенная
  обёртка: на iOS `LAContext`, на Android `BiometricPrompt.CryptoObject`. Хост берёт её у
  `GuardedVault.binding()` перед промптом и отдаёт обратно в `GuardedVault.unlock(binding)` после
  успеха. Библиотека её не разглядывает.
- `GuardedVault`:

  ```kotlin
  public interface GuardedVault {
      public val state: StateFlow<GuardedState>          // Off, Locked, Open, NeedsRecovery, Unavailable
      public suspend fun binding(): AuthBinding?          // null: state is not Locked
      public suspend fun unlock(binding: AuthBinding): Boolean
      public fun lock()                                   // zero the DEK
      public suspend fun recover(code: String): Boolean   // rewrap DEK under a fresh device key
      public suspend fun seal(plaintext: String, aad: String): String
      public suspend fun open(sealed: String, aad: String): String?   // null unless Open
  }
  ```

- Контракт **6**, минорный релиз Superizer. `minHostContract` у 2FA и «Паролей» **не** поднимаем:
  старый хост просто держит их в обычном ярусе, как сейчас (D576).

### 4.6. Состояния и экраны (всё в хосте, D574)

- **Locked** — занавес как сейчас, только промпт `BiometricOnly` с binding. Успех → `unlock` →
  **Open**.
- **Open** — DEK в памяти. Запирание по D131 и закрытие по бездействию (0.6.1) зовут `lock()`:
  DEK затирается `fill(0)`. Честно: копии в куче JVM/K-N так не убрать, барьер — ключ чипа.
- **NeedsRecovery** — экран хоста вместо занавеса: «Ключ устройства уничтожен: изменились лица или
  отпечатки, либо сняли блокировку экрана. Введите код восстановления». Пока ждём код, конверт и
  `g1:`-значения **не перезаписываются** (D144). Код верный → новый ключ чипа, слот `device`
  перезаворачивается, **Open**.
- **Unavailable** — биометрия не заведена или устройство её не умеет: охраняемый ярус включить
  нельзя. Работает как сегодня, обычный ярус. В «Защите» строка: «Без Face ID / отпечатка
  секреты защищены только экраном блокировки».
- `UserPresence.confirm` у охраняемых приложений («Экспорт», «Показать ключ», «Показать пароль»,
  «Удалить», запрос пароля из браузера) тоже `BiometricOnly` (D573). Иначе код-пароль открывал бы
  экспорт всех секретов на свой GitHub.

### 4.7. Жизненный цикл

- **Включение** (переключатель «Только биометрия» в «Защите», вопрос 244):
  1. Промпт `BiometricOnly`.
  2. Создать DEK, ключ чипа, код; показать код (8 групп по 4 знака base32).
  3. Человек вводит последнюю группу — код записан.
  4. Записать конверт; открыть охраняемые секреты обычным ярусом, запечатать в `g1:`.
  5. **Контрольное чтение через оба слота.**
  6. Только после этого стереть старые значения. Сбой на любом шаге — всё как было.
- **Выключение:** промпт `BiometricOnly`, перезапечатать в обычный ярус, удалить ключ чипа и конверт.
- **Новый код:** промпт, перезаворачивается только `recovery`.
- **Потеряны и ключ чипа, и код** — данные потеряны. На экране включения так и написано, без
  смягчений. Спасает только экспорт на GitHub-ключи, который у 2FA и «Паролей» уже есть.
- **Новый телефон:** ключ чипа не переезжает, бэкап ничего не несёт (как сейчас). Переезд — экспорт
  и импорт.

- Принуждение, спящий владелец, лицо на фото для Android Class 2 (Class 2 мы и не принимаем).
- Открытое приложение в чужих руках до запирания.
- Desktop и web: там хранилище — `AgeVault` с парольной фразой SSH-ключа, эта заметка их не трогает.
- Секреты хоста и необязательно-запертых приложений остаются в обычном ярусе.

## 6. Риски

- **R1.** Принимает ли Keychain уже оценённый `LAContext` для ключа Secure Enclave с
  `.biometryCurrentSet` без второго листа. По документации да; проверить на живом iPhone первым
  делом (шаг 1). Если нет — замок для охраняемого приложения на iOS делает сама расшифровка
  (`SecKeyCreateDecryptedData` с `LAContext` и `localizedReason`), а `DeviceAuthenticator` для
  этого случая не зовётся.
- **R2.** Связь «Паролей» с браузером (`passwords-browser`): ключ привязки компьютеров лежит в
  `runtime.secrets` «Паролей» и станет охраняемым. Если сервис связи читает его, пока «Пароли»
  заперты, он получит `SecretsUnavailableException`. Каждый запрос и так спрашивает биометрию, так
  что правильное поведение — отпереть по тому же промпту. Проверить при постройке.
- **R3.** API 24–29 и `CryptoObject` с `BIOMETRIC_STRONG`: проверить на эмуляторе API 28.

## 9. Решения

- **D569.** Секреты хоста — два яруса. Приложения с `LockPolicy.Required` в охраняемом, остальные
  и сам хост в обычном. Выбирает хост по манифесту.
- **D570.** Охраняемый ярус открывает только биометрия: iOS `…WithBiometrics`, Android
  `BIOMETRIC_STRONG`. Код-пароль/PIN устройства его не открывает. Заменяет D129 для охраняемого
  яруса; для остального D129 в силе.
- **D571.** Ключ чипа уничтожается при смене набора биометрии (iOS `.biometryCurrentSet`, Android
  `setInvalidatedByBiometricEnrollment(true)`).
- **D572.** Одна биометрия на открытие: промпт замка хоста несёт binding ключа (`LAContext` /
  `CryptoObject`). Окна в 30 с из §8 нет.
- **D573.** `UserPresence.confirm` охраняемого приложения — тоже `BiometricOnly`.
- **D574.** Приложения не меняются; экран восстановления и включение — в хосте.
- **D575.** Без слота `recovery` охраняемый ярус не включается (подтверждает D137/D143).
- **D576.** Контракт 6; `minHostContract` 2FA и «Паролей» не поднимается: старый хост — обычный ярус.
- **D577.** DEK один на хост; значения `g1:` с именем ключа в AAD.
- **D578.** Где биометрии нет — ярус `Unavailable`, работает как сегодня, со строкой в «Защите».
- **D579.** Пока `NeedsRecovery`, ничего охраняемого не перезаписывается (как D144).
- **D580.** Включение: показать код → проверка последней группы → запись → контрольное чтение через
  оба слота → стирание старого.
- **D581.** DEK затирается при каждом запирании хоста и закрытии по бездействию.
- **D582.** `localizedFallbackTitle = ""` на iOS: на листе нет кнопки кода-пароля.
- **D583.** Desktop/web не трогаем: там `AgeVault` и так требует парольную фразу.
- **D584.** `idea/06` §8 заменён этой заметкой; там оставлена ссылка.
