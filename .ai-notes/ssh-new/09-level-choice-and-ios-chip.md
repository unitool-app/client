# 09. Выбор уровня при импорте и создании, Secure Enclave на iPhone, P-256

> **Версия:** 1.3 · **Статус:** реализуется (§8, §9) · **Дата:** 2026-10-05
>
> **История:** 1.0 — 2026-10-04. Владелец спросил, нельзя ли держать SSH-ключи из QR-кода не в
> файлах приложения, а в защищённом месте устройства, по Face ID и без возможности достать их с
> устройства. Ответ «на Android так уже есть, на iPhone выключено по D175» его устроил с
> поправками: «старый вариант тоже оставить, но дать выбрать», «дать возможность создать P-256»,
> «а что для Android?».
>
> 1.1 — 2026-10-04. Ответы владельца на 118–121 (§6) и новое требование: на Android по умолчанию
> «в чипе + пароль ключа», отключать пароль — отдельно, с предупреждением (D244, §7). «Перенести в
> чип» снято (D241 переписано).
>
> 1.2 — 2026-10-05. Владелец ответил на 122: уровень 2 с паролем («да делай»). Реализация — §8.
>
> 1.3 — 2026-10-05. Владелец: «разрешим по сканеру отпечатка без пароля на Android, раз это высокий
> класс защиты». На вопрос, что делать с PIN, который тоже открывает ключ, выбрал «только отпечаток»
> (D245, §9). D244 сужено: пароль по умолчанию — только где отпечатка нет.
>
> Решения D237–D245, вопросы 118–123.

## 1. Что есть сейчас

| | Android | iPhone |
|---|---|---|
| Хост кольца | `SshKeyringHost.android` (чип) | `SshKeyringHost.passphraseOnly` — уровень 3 (D175) |
| Импорт из QR/файла | уровень выбирает кольцо само: лучший из возможных (`Keyring.placement`) | всегда уровень 3: `openssh-key-v1` под паролем ключа в `FileRecordStore` |
| «Создать ключ» | Ed25519 и P-256 (P-256 — только если в `device.levels` есть 1) | только Ed25519, уровень 3 |
| Самопроверка enclave | — | зелёная на iPhone владельца 2026-09-27 (TestFlight 1.0 (11)) |

Человек уровень не выбирает. Ни в `ImportOptions`, ни в мастере такого поля нет.

## 2. Что меняется

**D237. Уровень выбирает человек.** В мастере импорта и в «Создать ключ» появляется секция
«Где хранить». Варианты берутся из пересечения `device.levels` и того, что возможно для этого типа
ключа (`ChipBackend.placement`). Подписи — коды каталога 06 §6.1, а не новые фразы:

| Вариант | Уровень | Чем открывается | Когда показывается |
|---|---|---|---|
| **В чипе устройства** (по умолчанию) | 1 или 2, что даёт `placement` | Face ID / отпечаток / код устройства на каждое использование (или сессия по `UsePolicy`) | есть чип и блокировка экрана |
| **В чипе + пароль ключа** | 2, `keepPassphrase = true` | и то и другое | только когда `placement` даёт 2 (уже есть, 01 §5.4) |
| **Только пароль ключа** | 3 | пароль ключа (≥ 12, D167/D169) | всегда |

Если чипа нет (desktop, web, эмулятор, iPhone без кода-пароля), секции нет: вариант один, как
сейчас. «Только пароль ключа» на устройстве с чипом — осознанный выбор, поэтому строка защиты у
ключа говорит именно это (D240), а не «чипа нет».

**D238. Контракт.** В `ImportOptions` (Superizer `core`, контракт 3, ветка `contract-3`, не
опубликован) добавляется поле:

```kotlin
/** The level the person chose (D237); null takes the best this device offers, as before. */
val level: Int? = null,
```

`generate` уже принимает `ImportOptions`, так что одно поле покрывает и импорт, и создание.
Значение по умолчанию сохраняет поведение, поэтому это не новый контракт, а правка 0.4.0 до
публикации. Если 0.4.0 к моменту реализации опубликован, это становится 0.4.1 с тем же номером
контракта (поле с умолчанием, бинарно совместимо для Kotlin-вызывающих по именам).

Кольцо проверяет выбор: уровень, которого нет в `device.levels` или который невозможен для типа
ключа (например, 1 для импортированного Ed25519 на iPhone), даёт
`ImportOutcome.Failed("level.unavailable")`. Мастер такой вариант просто не показывает.

**D239. iPhone переходит на Secure Enclave.** В `UnitoolIos.host()` строка
`SshKeyringHost.passphraseOnly(...)` становится `SshKeyringHost.ios(::promptText, records,
prompts, SystemClock, scope)`. Тексты Face ID те же, что у `MainActivity.promptText`: операция,
приложение, ключ и отпечаток. Это закрывает D175.

На iPhone получается:

| Ключ | Уровень по умолчанию | Что это значит |
|---|---|---|
| Импортированный Ed25519 / RSA / ECDSA (QR, файл, вставка) | 2 | файл ключа запечатан ECIES ключом из Secure Enclave с `UserPresence`, `WhenPasscodeSetThisDeviceOnly`. Без Face ID / кода не открывается, с другого устройства не открывается, не попадает в бэкап, исчезает при снятии кода-пароля. На время операции ключ есть в памяти приложения (обнуляется, I6) |
| Созданный на телефоне P-256 | 1 | ключ рождается в Secure Enclave и не выходит из него никогда, даже в память приложения. Наружу — только открытый ключ |

**D240. Создание P-256 на iPhone.** Отдельной работы не нужно: `CreateStep` показывает P-256,
когда `1 in device.levels`, а `SecureEnclaveBackend.generate` уже написан и прогнан
самопроверкой. После D239 вариант появится сам. В мастере у P-256 строка-подсказка из каталога:
«Только подпись: вход по SSH, подписи. Не расшифровывает age, не может быть ключом для секретов и
бэкапа» (это уже так по 05 §4.3 и Б5; нужен код каталога, если его ещё нет).

**D241 (1.1, ответ на 119). Переноса нет.** Ключи, уже импортированные на iPhone на уровне 3,
остаются как есть и открываются `PassphraseBackend`. Чтобы ключ попал в чип, человек удаляет его и
импортирует заново. Обратного переноса (1/2 → 3) тоже нет (ответ на 120). Оценка шага 2 — минус
0,25 дня.

**D242. Строки защиты.** Каталог 06 §6.1 получает различие «уровень 3, потому что чипа нет» и
«уровень 3 по выбору человека» (`KeyFindings.placement` смотрит на `device.levels`). Баннер на Home
не ругается на выбранный уровень 3 так же громко, как на отсутствие чипа: человек это решил сам.

**D243. Android.** Меняется секция «Где хранить» (с другим умолчанием, D244). Остальное уже
работает:

| Ключ | Уровень | Где |
|---|---|---|
| Импортированный RSA | 1 | TEE, сам ключ внутри Keystore |
| Импортированный ECDSA P-256 | 1 | StrongBox, если есть, иначе TEE |
| Импортированный Ed25519 | 1, если Keystore принимает Curve25519 (пробный импорт, 01 §4.1 impl); иначе 2 | TEE |
| Созданный P-256 | 1 | StrongBox/TEE, рождается в чипе |
| Созданный Ed25519 | как импортированный | — |

То есть на Android импортированный ключ на уровне 1 после импорта живёт **внутри** чипа, а не
обёрнутым в файле — это сильнее, чем на iPhone, где Secure Enclave не принимает чужие ключи.
Подтверждение — системный `BiometricPrompt` с `CryptoObject` (API 30+): отпечаток, лицо — только
если оно класса 3 (Pixel 8 и новее; на большинстве телефонов лицо класса 2 и для ключей не
годится), иначе PIN/графический ключ. Ниже API 30 — только уровень 3 (04 шаг 5).

## 3. Честная граница «нельзя достать с устройства»

- **Уровень 1, созданный на устройстве** (P-256 на iPhone, P-256 и др. на Android): закрытого
  ключа нигде, кроме чипа, нет и не было. Единственный вариант, где «нельзя достать вообще» —
  буквально правда.
- **Уровень 1, импортированный** (Android): внутри чипа не извлекается, но ключ существовал до
  импорта — на компьютере, в QR-коде. С телефона его не достать, а копия у человека есть.
- **Уровень 2** (импорт на iPhone, Ed25519 на части Android): файл без чипа этого устройства
  бесполезен, но на время операции ключ в памяти процесса. Защита от кражи файла и бэкапа — да;
  от кода, исполняемого внутри процесса на взломанном телефоне — нет.
- **Уровень 3**: файл под паролем ключа; держится на длине пароля и bcrypt.

Мастер говорит это словами каталога у каждого варианта, а не одной общей фразой.

## 7. Android: по умолчанию «в чипе + пароль ключа» (1.1)

Требование владельца: «на андроиде по умолчанию в чипе пусть будет запароленный ключ, чтобы это
надо было отключать отдельно, с предупреждением о безопасности».

**D244.** На Android секция «Где хранить» выглядит так:

- выбран «В чипе», под ним включён переключатель «И каждый раз спрашивать пароль ключа»;
- выключить переключатель можно, но сначала появляется диалог-предупреждение (код каталога, en/ru):
  «Без пароля ключом может воспользоваться любой, кто знает PIN этого телефона или разблокирует его
  отпечатком. Пароль ключа — второй замок, которого нет у телефона.» Кнопки «Оставить пароль» (по
  умолчанию) и «Всё равно без пароля»;
- «Только пароль ключа» (уровень 3) — третий вариант, как везде.

На iPhone умолчание остаётся «В чипе» без пароля ключа (118); переключатель тот же, но без диалога.

**Тонкость, из-за которой вопрос 122.** Пароль ключа может быть вторым замком только криптографически
— когда сам файл ключа зашифрован паролем, а чип оборачивает уже зашифрованный файл. Это уровень 2.
У ключа уровня 1 (сам ключ внутри Keystore) файла нет: чип не умеет требовать пароль ключа, и
«пароль» был бы проверкой в коде приложения — её обходит любой, кто исполняет код в процессе.
Значит, умолчание «в чипе + пароль» на Android переводит импортированные RSA, ECDSA и Ed25519 с
уровня 1 на уровень 2:

| | Уровень 1 (сейчас, без пароля) | Уровень 2 + пароль (новое умолчание) |
|---|---|---|
| Украли телефон и знают PIN | могут подписывать, не могут достать ключ | без пароля ключа ничего не могут |
| Чужой код внутри процесса (взломанный телефон) | ключ не достать — он в чипе | после Face ID + пароля ключ на миг в памяти |
| Копия файлов приложения | бесполезна | бесполезна (без чипа и пароля) |

Оба варианта честные; первый лучше против взлома телефона, второй — против того, кто знает PIN.
Требование владельца прямо выбирает второй. Ключ, выключивший пароль после предупреждения, идёт
на уровень 1, как сейчас.

Созданный на телефоне P-256 рождается в чипе (уровень 1) и файла не имеет — пароль к нему
неприменим; переключателя у него нет, строка каталога объясняет почему. Созданный Ed25519 при
включённом пароле получает пароль на шаге «Задать пароль» и ложится на уровень 2 с
`keepPassphrase` (сейчас `generate` для него пароль сбрасывает — `Keyring.kt:604`, правится).

## 9. Только отпечаток (D245, 1.3)

**Почему не «просто без пароля».** Ключ в Keystore был привязан к `AUTH_BIOMETRIC_STRONG |
AUTH_DEVICE_CREDENTIAL`: отпечаток открывал его, но и PIN тоже. Отпечаток класса 3 ничего не даёт,
пока есть обход через PIN, а знающий PIN к тому же может добавить свой палец.

**D245.** Новый флаг ключа «только сильная биометрия»:

- контракт (Superizer 0.4.1): `ImportOptions.biometricOnly`, `SshKeyInfo.biometricOnly`,
  `KeyringDevice.strongBiometric` (Android: `BiometricManager.canAuthenticate(BIOMETRIC_STRONG)`),
  код каталога `key.biometric-only` (Ok);
- Keystore: `setUserAuthenticationParameters(…, AUTH_BIOMETRIC_STRONG)` и
  `setInvalidatedByBiometricEnrollment(true)` — новый отпечаток или удаление всех делают ключ
  непригодным (`KeyPermanentlyInvalidatedException` → `Unusable` → «импортируйте заново»). Это
  отменяет D144 только для таких ключей;
- системный запрос: только `BIOMETRIC_STRONG`, обязательная кнопка «Отмена» (`PromptText.cancel`);
  `BIOMETRIC_ERROR_NEGATIVE_BUTTON` — отмена, `BIOMETRIC_ERROR_NO_BIOMETRICS` — ключ непригоден;
- кольцо: флаг возможен только на уровнях 1–2 и при `strongBiometric`, иначе
  `Failed("biometric.unavailable")` до записи; чип узнаёт о флаге из `reason.key.biometricOnly`
  при импорте, создании и каждом использовании.

**Умолчания на Android (сужает D244):**

| На телефоне | Умолчание в «В чипе» | Можно |
|---|---|---|
| Есть отпечаток (класс 3) | «Только мой отпечаток» вкл., пароль ключа выкл. → уровень 1, `biometricOnly` | добавить пароль (уровень 2 + оба замка); выключить отпечаток — предупреждение, если не остаётся ни отпечатка, ни пароля |
| Отпечатка нет | пароль ключа вкл. (D244) | выключить — предупреждение |

Предупреждение `key.no-second-lock` появляется ровно тогда, когда у ключа не остаётся своего замка
(ни «только отпечаток», ни пароля), и ничего не меняет до ответа. P-256, созданный в чипе, получает
тот же переключатель отпечатка, без пароля.

Лицо класса 3 (Pixel 8 и новее) — тоже `BIOMETRIC_STRONG`, Android их не различает; так и сказано в
тексте каталога.
