## 1. Что значит «не утечёт»: инварианты

Каждый инвариант — это тест или группа тестов. Работа не считается сделанной, пока все они не
зелёные в `verify.sh` (кроме помеченных «вручную»).

| # | Инвариант | Где проверяем |
|---|---|---|
| **I1** | Закрытая половина не лежит ни в одном файле приложения: ни байтами, ни в Base64, hex, PEM, ни кусками | JVM: всё хранилище после импорта. Android: обход `dataDir` целиком |
| **I2** | У резидентного ключа после импорта закрытой половины нет нигде вне Keystore: `encoded == null`, экспорт через `KeyFactory.getKeySpec` бросает исключение | Android |
| **I3** | Запечатанный блоб не открывается без подтверждения устройства, после удаления ключа-обёртки и другим ключом | Android |
| **I4** | Ни один публичный метод `SshKeyring`, `SshAgent`, `SshKeyAdmin` не возвращает закрытый материал | JVM: белый список сигнатур плюс дамп BCV |
| **I5** | Закрытый материал и пароль не попадают в логи (`Logger`, logcat), события `SuperizerEvent` и Service Menu, аналитику, снапшоты, `AppConfig`, deep links, `toString()` объектов и `message` исключений | JVM и Android |
| **I6** | Буферы с закрытым материалом и пароль обнулены после импорта, подписи и расшифровки, **в том числе** при ошибке и исключении | JVM |
| **I7** | Без человека операции нет: без подтверждения Keystore отказывает | Android. «С подтверждением получается» — вручную или UiAutomator (§6.4) |
| **I8** | Приложение без разрешения ключом не пользуется. Разрешение — на (приложение, ключ, цель). Конфиг, пуш, deep link его не создают | JVM |
| **I9** | Подпись приложения нельзя выдать за подпись входа по SSH: только SSHSIG, namespace проверяется, `SshAgent` не в реестре | JVM |
| **I10** | Бэкап и перенос устройства не уносят записей кольца | JVM: правила бэкапа Unitool. Android: Keystore не бэкапится по определению |
| **I11** | Удаление ключа не оставляет ничего: ни записи, ни разрешений, ни alias в Keystore | Android и JVM |
| **I12** | После импорта и сборки мусора seed Ed25519 не находится в дампе кучи | Android. Для RSA и ECDSA отчёт без падения (01 §4.5) |
| **I13** | Мастер импорта не снимается скриншотом, поле пароля не учит клавиатуру | Android: флаг окна; `screencap` вручную |
| **I14** | Совместимость: подписанное нами проверяет `ssh-keygen`; зашифрованное `age` открываем мы; наш агент понимает `ssh-add` | JVM с настоящими утилитами |
| I-сеть | Модуль `ssh` не зависит от сети | `verify.sh`: в `ssh` нет зависимости от `ktor` |

## 2. Хранилище записей (D159)

Отдельный prefs-файл `cx.m42.superizer.ssh`, а не общий `cx.m42.superizer.store`. Так можно:

- исключить из бэкапа ровно его и знать, что сканер ищет в нужном месте;
- стереть его целиком при удалении последнего ключа, не трогая хост;
- не зависеть от будущих изменений общего файла (idea/06 §6 нашла там утечку через снапшот).

Содержимое:

```json
{ "v": 1,
  "keys": [ { "id": "SHA256:…", "public": "ssh-ed25519 AAAA…", "comment": "work",
              "storage": "tee", "policy": { "every": true }, "origin": "imported",
              "alias": "cx.m42.superizer.ssh.3f9ac21e", "sealed": null, "usable": true, "at": 1790000000000 } ],
  "grants":  [ { "app": "2fa", "key": "SHA256:…", "purpose": "decrypt", "brick": null, "at": … } ],
  "journal": [ { "at": …, "app": "2fa", "key": "SHA256:…", "op": "decrypt", "ns": null, "digest": "3f9ac21e", "outcome": "ok" } ] }
```

`sealed` непуст только у запечатанного ключа, и это шифртекст. В обоих правилах бэкапа Unitool
(`backup_rules.xml`, `data_extraction_rules.xml`) файл стоит в `exclude`. Правила сейчас
перечисляют только `include`, а в `include` стоит чужой файл, как записано в памяти 2FA. Поэтому
явный `exclude` — страховка на случай, если правила когда-нибудь поменяют на «всё, кроме».

## 3. Канарейки и сканер

### 3.1. Канарейки

Утечку найти легко, если секрет узнаваем.

| Канарейка | Значение | Как получается файл ключа |
|---|---|---|
| seed Ed25519 | 32 байта ASCII `SUPERIZER-CANARY-ED25519-SEED-01` | наш писатель `openssh-key-v1` делает незашифрованный файл, затем **настоящий** `ssh-keygen -p -N <пароль> -a 24 -f` шифрует его. Импортируем то, что сделал OpenSSH |
| пароль | `canary-pass-Ω-7f3a` (не-ASCII — проверка UTF-8) | он же |
| RSA-3072 | постоянный тестовый ключ в `testFixtures`, канарейки — первые 24 байта `d`, `p`, `q`, `dp` | `ssh-keygen -t rsa`, один раз; в файле пометка «только для тестов» |
| ECDSA P-256 | постоянный тестовый ключ, канарейка — `d` | так же |
| открытый текст age | `CANARY-PLAINTEXT-otpauth://totp/…` | `age -R` |

**Канарейка в куче самого теста.** Инструментальный тест выполняется в процессе приложения. Если
тест держит канарейку константой, дамп кучи найдёт её в классе теста. Поэтому канарейка
хранится замаскированной (XOR `0x5A`) и в памяти целиком не собирается. Сканер сравнивает
побайтно: `heap[i + k] xor 0x5A == masked[k]`. Вход импорта — зашифрованный файл из
`assets`, и в нём канарейки нет. В открытом виде она появляется только в буферах нашего
парсера, а их мы обнуляем. Это и проверяем.

### 3.2. Сканер

`LeakScanner.scan(haystack: ByteArray, canaries: List<Canary>): List<Finding>` ищет каждую
канарейку в кодировках:

- сырые байты;
- Base64 (стандартный и URL-safe, с `=` и без) при трёх выравниваниях: канарейка внутри
  длинного Base64 начинается с любого из трёх байтов тройки;
- hex в нижнем и верхнем регистре;
- UTF-16LE для ASCII-канареек: так `String` лежит в куче JVM, если в нём есть не-Latin-1
  символ;
- любые **16-байтовые окна** секрета, в сыром виде и в Base64: частичная утечка — тоже
  утечка.

`Finding` называет канарейку, кодировку и смещение, но **не** содержимое вокруг: отчёт теста
сам не должен стать утечкой.

Сканер — в `superizer:testing`: им пользуются и тесты библиотеки, и тесты Unitool.

### 3.3. Где сканируем

| Где | JVM | Android |
|---|---|---|
| хранилище | `InMemoryStorage` всё целиком | обход `context.dataDir`: `shared_prefs`, `files`, `databases`, `cache`, `no_backup`, `code_cache`; плюс `getExternalFilesDir`, `externalCacheDir` |
| логи | `RecordingLogger` (всё, что прошло через `Logger`) | `logcat -d --pid=<свой pid>`: тот же UID, читать можно |
| события | всё, что пришло в `superizer.events`, и их `toString()` | то же |
| снапшоты | `PrefsSnapshotStore` в памяти | входит в `dataDir` |
| исключения | `message` и `stackTrace` всех исключений из модуля за прогон | то же |
| куча | — | `Debug.dumpHprofData` после трёх `Runtime.gc()`; файл удаляется после скана |

## 4. Совместимость с настоящими инструментами (I14)

Правило из памяти 2FA: опечатка в лестнице X25519 прошла круговые тесты и упала только на
векторах RFC. Поэтому каждый примитив проверяется векторами **и** независимой реализацией, а
каждый формат — настоящей утилитой.

| Тест | Что делает |
|---|---|
| `OpenSshKeyFileInteropTest` | `ssh-keygen -t ed25519 / rsa -b 2048,3072,4096 / ecdsa -b 256,384,521`, `-N '' / пароль`, `-a 16 / 24 / 100`, `-Z aes256-ctr / aes128-ctr / aes256-gcm@openssh.com`. Наш разбор даёт тот же открытый ключ, что `ssh-keygen -y`, и тот же комментарий. Неверный пароль → `WrongPassphrase`. `-Z chacha20-poly1305@openssh.com` и `-m PEM` → отказ с командой |
| `SshSigInteropTest` | наша подпись → `ssh-keygen -Y verify -f allowed_signers -I me -n ns -s sig`. Чужой namespace → отказ. Подпись `ssh-keygen -Y sign` → наш `SshSig.verify` принимает. Изменённый бит → отклоняет |
| `AgeDecryptInteropTest` | `age -R key.pub` (ed25519, rsa; несколько получателей; `-a`; больше 64 КиБ, то есть несколько чанков) → наш `decrypt` открывает. Изменённый байт в заголовке и в теле → отказ, не мусор |
| `AgentInteropTest` | наш `AgentServer` на UNIX-сокете поверх программного бэкенда. `SSH_AUTH_SOCK=…`: `ssh-add -l` и `-L` видят ключи; `ssh-add key` импортирует (пароль через `SSH_ASKPASS` и `SSH_ASKPASS_REQUIRE=force`); `ssh-add -d`, `-D`; `ssh-add -x` / `-X`; `ssh-add -t 60 -c`; `ssh-keygen -Y sign -f key.pub` подписывает **через агента**, и `ssh-keygen -Y verify` это проверяет; RSA с флагом `rsa-sha2-512` |
| `AgentSshdTest` (ночной, необязательный) | `sshd` на `127.0.0.1:<случайный порт>` от имени пользователя, `ssh -o IdentityAgent=<наш сокет> localhost true`. Это настоящий вход через нашего агента, включая `session-bind` |
| `BcryptPbkdfTest` | векторы OpenBSD `regress/lib/libutil/bcrypt_pbkdf` и `golang.org/x/crypto/bcrypt_pbkdf` |
| `Ed25519Test` | векторы RFC 8032 §7.1 и 1000 случайных пар «seed, сообщение» против `Signature.getInstance("Ed25519")` JDK 21: подпись совпадает байт в байт, проверка взаимная |
| `AesTest` | AES-128/192/256, CTR и GCM против `Cipher` JDK, векторы NIST SP 800-38A и GCM |
| `RsaOaepDecodeTest` | снятие OAEP с меткой age против `OAEPWithSHA-256AndMGF1Padding` и `PSource.PSpecified(label)` JDK |

Утилиты на этой машине есть: OpenSSH 9.6p1, `age`, `qrencode`, JDK 21. В `verify.sh` каждый
такой тест при отсутствии утилиты пропускается **по имени** (`SKIP interop: no ssh-add`), как
принято. В CI утилиты ставятся: `apt-get install openssh-client openssh-server age`.

## 5. JVM-тесты модуля (`ssh/src/desktopTest`)

Всё, кроме Keystore, проверяется на JVM. Для этого есть программный бэкенд с тем же
интерфейсом, что у Android: `SoftwareBackend`. Его «Keystore» — AES-ключ в памяти, а «промпт»
управляется сценарием (`approveNext()`, `cancelNext()`, `refuseGrantNext()`). Он же лежит в
`FakeSshKeyring` в `superizer:testing`, чтобы 2FA тестировала свой импорт.

| Тест | Инварианты | Что проверяет |
|---|---|---|
| `NoSecretAtRestTest` | I1 | импорт канареечного ключа всеми путями (резидентный-фейк, запечатанный, с `keepPassphrase`), подпись, расшифровка, удаление → сканер по всему хранилищу пуст |
| `NoSecretInLogsTest` | I5 | тот же сценарий плюс все ошибки (неверный пароль, повреждённый файл, отмена, отказ) → `RecordingLogger`, события, `toString()` всех возвращённых объектов, `message` исключений — пусто |
| `ApiSurfaceTest` | I4 | рефлексией перечисляет публичные методы трёх интерфейсов и сверяет с белым списком «имя + сигнатура». Новый метод — красный тест, пока его не внесут в список с причиной. Отдельно: ни один публичный тип модуля не содержит поле типа `SecretBytes` (обход свойств возвращаемых типов) |
| `ZeroizationTest` | I6 | после `import`/`add` входные `ByteArray` и `CharArray` целиком нули — при успехе, `WrongPassphrase`, `Corrupted`, отказе по формату и исключении, которое бэкенд бросает посреди. `SecretBytes` после `use {}` обнулён. Буфер запечатанного ключа после подписи обнулён (внутренний крючок теста) |
| `SessionTest` | I6, I7 | `Session(60)`: второе использование без промпта; через 61 с по `FakeClock` — снова промпт, буфер обнулён; `lockAll()` обнуляет сразу |
| `GrantTest` | I8 | нет разрешения → лист разрешения; отказ → `Refused`, разрешение не записано; разрешение для `2fa` не действует для `calculator`; `Sign("a@superizer")` не даёт `Sign("git")`; сменился `brick` → разрешения нет. `AppConfig`, deep link, пуш с полем «grants» ничего не меняют |
| `NamespaceTest` | I9 | `x@m42.cx` от приложения → `NotAllowed`; недопустимые символы → `NotAllowed`; подписанные данные начинаются с `"SSHSIG"`; в реестре сервисов хоста Unitool нет `SshAgent` и `SshKeyAdmin` |
| `DeleteTest` | I11 | после `delete` нет записи, разрешений, журнала ключа, а сканер пуст |
| `ImportFormatTest` | — | каждый отказ §8 заметки 02 даёт свою причину и свою команду; дубликат → «уже есть» |
| `BackupRulesTest` (в Unitool) | I10 | разбирает оба XML правил: `cx.m42.superizer.ssh.xml` есть в `exclude` и нет в `include` |

## 6. Инструментальные тесты (`ssh/src/androidInstrumentedTest`)

Запускаются `connectedAndroidTest` на эмуляторе `unitool35` (API 35) или на телефоне.
`verify.sh` их запускает, если устройство подключено (как `AndroidKeystoreVaultTest`). Каждый
тест работает со своими alias и удаляет их в `@After`, как тест vault. Не забывать
`runBlocking<Unit>`.

### 6.1. Подготовка устройства из теста

`UiAutomation.executeShellCommand` выполняется с правами shell, поэтому тест может сам:

- поставить PIN: `locksettings set-pin 1111` — без него Keystore не создаст ключ с
  аутентификацией;
- в конце снять его: `locksettings clear --old 1111`. Это заодно тест §5.7 заметки 01:
  после снятия ключ должен стать `usable = false`.

### 6.2. Тесты

| Тест | Инварианты | Что проверяет |
|---|---|---|
| `KeystorePropertiesTest` | I2, I7 | для каждого типа из 01 §4.1: `encoded == null`; `KeyFactory.getKeySpec(key, RSAPrivateCrtKeySpec / ECPrivateKeySpec)` бросает; `KeyInfo`: `isUserAuthenticationRequired`, таймаут по политике, `isInvalidatedByBiometricEnrollment == false`, `securityLevel` (на телефоне ≥ TEE — утверждение, на эмуляторе — отчёт в лог) |
| `RequiresUserTest` | I7 | `initSign` + `update` + `sign` без промпта → отказ; расшифровка конверта без промпта → отказ. Точный тип исключения записывает шаг 0, тест его закрепляет |
| `NoSecretOnDiskTest` | I1, I5 | импорт канареек (ed25519, rsa, ecdsa) → обход `dataDir` и `logcat --pid` сканером пусты |
| `HeapTest` | I12 | импорт Ed25519 из `assets` → три `gc()` → `dumpHprofData` → сканер. Ed25519: 0 находок, иначе красный. RSA и ECDSA: находки в отчёт, не красный (`BigInteger`, 01 §4.5) |
| `SealedTest` | I3 | конверт не открывается другим alias, после `deleteEntry` обёртки и после изменения любого бита |
| `InvalidationTest` | 01 §5.7 | снятие PIN → следующая операция `Invalidated`, запись `usable = false`, открытый ключ виден |
| `DeleteTest` | I11 | после удаления `keystore.aliases()` пуст по префиксу `cx.m42.superizer.ssh.` |
| `NoScreenLockTest` | 01 §5.6 | без PIN `import` → `NoScreenLock`, ничего не записано |
| `SecureWindowTest` | I13 | пока открыт мастер импорта, у окна стоит `FLAG_SECURE` |

### 6.3. Шаг 0 — это тоже тест

`KeystoreProbeTest` из 04 §2 остаётся в наборе. Он не проверяет наш код, а записывает в лог, что
умеет устройство: Curve25519, StrongBox, «сырое» RSA, OAEP с меткой, проверка сертификата при
импорте. На новом телефоне его прогон за минуту отвечает, какой ключ там будет резидентным.

### 6.4. «С подтверждением получается»

Автоматически это хрупко: UiAutomator должен набрать PIN в системном экране, а его разметка
меняется между версиями Android. План такой:

1. попробовать UiAutomator на `unitool35` (`By.res("com.android.systemui:id/lockPassword")`);
2. если устойчиво — это тест;
3. если нет — ручная приёмка §7, а в автоматике остаются отказы без подтверждения (I7) и
   успешный путь на JVM через `SoftwareBackend`.

## 7. Ручная приёмка на `unitool35` и на телефоне

```
sudo setfacl -m u:dev0:rw /dev/kvm                  # и вернуть после (память 2FA)
adb shell locksettings set-pin 1111
# Settings → Security → Fingerprint, при запросе пальца: adb -e emu finger touch 1
adb push canary_ed25519 /sdcard/Download/           # зашифрован ssh-keygen, пароль известен
```

1. Settings → «SSH-ключи» → «Добавить» → файл. Видно тип, отпечаток и «где будет жить» до
   пароля. Ввести пароль → ключ в списке с верным значком.
2. `adb shell screencap -p /sdcard/s.png` во время мастера → чёрный кадр.
3. Bench test-app → «Подписать» → в листе приложение, namespace и хеш → `adb -e emu finger
   touch 1` → подпись. На компьютере `ssh-keygen -Y verify` принимает её.
4. 2FA → «Импорт из файла» → экспорт, сделанный на этот же ключ → лист «Расшифровать…» →
   аккаунты на экране проверки.
5. `adb shell run-as cx.m42.unitool sh -c 'find . -type f -exec grep -l SUPERIZER-CANARY {} +'`
   → пусто (debug-сборка).
6. `adb shell locksettings clear --old 1111` → ключ «непригоден», открытая половина видна.
7. На телефоне с StrongBox: созданный P-256 показывает «чип (StrongBox)», аттестация
   разбирается.

## 8. Чего тесты не докажут

- Что TEE или StrongBox конкретного производителя реализованы правильно. Мы проверяем, что
  *просим* правильного и что Keystore *отвечает* правильно.
- Что `BigInteger` RSA и ECDSA исчезли из кучи сразу: сборщик мусора не обязан спешить. Тест
  кучи для них — отчёт.
- Что текст, **вставленный** человеком, не остался в `String` поля ввода и в истории
  клавиатуры (T11). Поэтому вставка — худший канал, и интерфейс это говорит.
- Что код внутри процесса не перехватит подтверждённую операцию (T8). От этого защищает только
  «каждое использование» и то, что лист показывает, *что* подписывается.

## 9. Решения

- **D157.** Утечку ищем по канарейкам: узнаваемый seed и пароль, маскированные в самом тесте.
  Сканер ищет их во всех кодировках и 16-байтовыми окнами в файлах, логах, событиях,
  снапшотах, исключениях и дампе кучи. Сканер лежит в `superizer:testing`.
- **D158.** Совместимость доказывают настоящие `ssh-keygen`, `ssh-add`, `sshd` и `age`. Каждый
  примитив проверяется векторами и независимой реализацией JDK. Без утилиты тест
